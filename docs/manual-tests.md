# Manual tests

The runners of GitHub have no WSL 2 on Windows and no nested virtualization on macOS, so CI cannot test the VM of Devspaces there. Each step that changes the VM on Windows or macOS has a list of manual tests here ([`R-VM-009`](requirements.md#r-vm-009)). Run them with a build of the branch (`npm run install-local`), and write the results into the pull request.

## The WSL distribution from the image of the VM

[`R-ENG-005`](requirements.md#r-eng-005), [`R-VM-002`](requirements.md#r-vm-002), [`R-VM-007`](requirements.md#r-vm-007), `src/core/docker/wslSetup.ts` and `src/vscode/wslSetupCommands.ts`. Before the tests: Windows 10 or 11 (Home too), on x64 and, when one is at hand, on Arm, a Windows user without administrator rights, WSL of the Microsoft Store, and no distribution `devspaces` (`wsl --list`).

1. **Setup without a question.** **Set Up Docker for Devspaces** in the view: no question of Devspaces and no prompt of Windows. The progress shows "Downloading the VM of Devspaces" with the megabytes, then "Creating the WSL distribution.", then "Starting the WSL distribution and Docker." The log names the version of the image, `ghcr.io/nimblescape/devspaces-vm`, the size of the file, and `Docker Engine` with its version at the end. Write down how long the first start took.
2. **The system of the image.** `wsl -d devspaces -u root -- cat /etc/os-release` names Debian 13, `wsl -d devspaces -u root -- systemctl is-active docker devspaces-upgrade.timer` says `active` twice, and `wsl -d devspaces -u root -- ls /mnt/c` fails, because no drive of Windows is mounted. The Start menu has no entry `devspaces`, and Windows Terminal has no profile for it.
3. **Not the default.** `wsl --list` does not mark `devspaces` as the default, also on a computer with no other distribution (then WSL has no default).
4. **A devspace.** Start a devspace and open it: it opens as on macOS and Linux, and `wsl -d devspaces -u root -- docker ps` lists its container.
5. **The upgrade in the VM.** Keep the distribution running for 2 minutes after its first start: `wsl -d devspaces -u root -- journalctl -u devspaces-upgrade --no-pager` shows a run of the service. It says `skipped` when the image is less than 20 hours old (the version of the image in the log is its build time in UTC), and otherwise it upgrades the packages. The devspace of test 4 still runs afterwards.
6. **The command again.** Run **Devspaces: Set Up Docker for Devspaces in WSL…** again: no question, no download, and the log says that the distribution exists and Devspaces uses it.
7. **Without a connection.** Remove the distribution (**Devspaces: Remove the WSL Distribution of Devspaces…**), turn off the network, and set it up again: the message says that the image of the VM could not be downloaded, and **Show details** names `ghcr.io`. Turn on the network, and set it up again.

## The choice of the Docker host

[`R-ENG-001`](requirements.md#r-eng-001), `src/vscode/remoteDockerCommands.ts`. Run it on Windows, macOS and Linux. Before the tests: the VM of Devspaces is not set up (on Windows no distribution `devspaces` in `wsl --list`; on macOS and Linux no folder `~/.nimblescape/devspaces/vm/devspaces`), and Devspaces uses a remote host (**Devspaces: Use a Remote Docker Host…**).

1. **No entry for the Docker of this computer.** The command palette has no **Devspaces: Use the Local Docker**. **Devspaces: Choose the Docker Host…** (also the first row of the view) lists the remote host, and in the group **WSL** (Windows) or **Lima** (macOS and Linux) the entry **Set Up Docker for Devspaces in WSL…** or **Set Up Docker for Devspaces in Its VM…**. It has no entry for Docker Desktop or for the Docker Engine of this computer, also when one of them runs.
2. **The setup from the choice.** Choose that entry: the setup of the VM runs as from the button of the view, and afterwards Devspaces uses the VM. **Choose the Docker Host…** then lists `wsl:devspaces` (Windows) or the Lima VM (macOS and Linux) in that group, and no setup entry.
3. **Back to the VM.** Choose the remote host, and then the VM again in **Choose the Docker Host…**: no setup runs, and the first row of the view names the VM.
4. **Removal of the current host.** While Devspaces uses the remote host, remove it with **Devspaces: Remove a Host from the List…**: the message says that Devspaces has no Docker host now, and the view shows the Docker setup, not the Docker of this computer.

## Windows with Docker Desktop

[`R-ENG-001`](requirements.md#r-eng-001), [`R-VM-008`](requirements.md#r-vm-008). Before the tests: Windows 10 or 11 with Docker Desktop on WSL 2, running, a Windows user without administrator rights for Devspaces, and no distribution `devspaces` (`wsl --list`). Write down the versions of Windows, WSL (`wsl --version`) and Docker Desktop, and `docker context show` in a terminal of Windows.

1. **The setup shows although Docker Desktop runs.** The view of Devspaces shows the Docker setup with **Set Up Docker for Devspaces**, not the repositories. **Devspaces: Choose the Docker Host…** has no entry for Docker Desktop.
2. **The setup next to Docker Desktop.** Run **Set Up Docker for Devspaces**: it runs as test 1 of [The WSL distribution from the image of the VM](#the-wsl-distribution-from-the-image-of-the-vm). Afterwards `wsl --list --verbose` shows `devspaces` and `docker-desktop` as running, and `docker context show` names the same context as before.
3. **Two engines.** `wsl -d devspaces -u root -- docker info --format "{{.Name}}"` names the distribution of Devspaces, and `docker info --format "{{.Name}}"` in a terminal of Windows names `docker-desktop`. `docker ps -a` in a terminal of Windows does not list the containers of Devspaces.
4. **No integration of Docker Desktop.** Docker Desktop, **Settings**, **Resources**, **WSL integration**: `devspaces` is not turned on. Write down whether Docker Desktop lists it.
5. **A devspace next to a container of Docker Desktop.** Start a devspace and open it. In a terminal of Windows, run `docker run -d --rm --name port-test -p 8080:80 nginx` on Docker Desktop, and `wsl -d devspaces -u root -- docker run -d --rm --name port-test -p 127.0.0.1:8080:80 nginx` in the distribution of Devspaces. Write down whether both start, and what `curl http://localhost:8080` in a terminal of Windows and `wsl -d devspaces -u root -- curl -s http://127.0.0.1:8080` answer. Then stop both containers (`docker stop port-test`, `wsl -d devspaces -u root -- docker stop port-test`).
6. **Docker Desktop quits.** Quit Docker Desktop (its icon in the notification area, **Quit Docker Desktop**): the devspace of test 5 keeps running, and its window stays connected. Start Docker Desktop again: the same.
7. **Devspaces of an older version.** On a computer where an older version of Devspaces made devspaces in Docker Desktop: they stay in Docker Desktop (`docker ps -a`), and Devspaces does not move or remove them. Write down what the view of Devspaces shows for them.

## The idle script in WSL

[`R-VM-004`](requirements.md#r-vm-004), `src/core/docker/wslKeeper.ts` and `src/core/docker/wslLifetime.ts`. Before the tests: the WSL distribution of Devspaces set up with this build, and no devspace running there. `wsl --list --running` shows whether the distribution runs without starting it; each `wsl -d devspaces …` below starts it when it does not run, and WSL stops it again 15 seconds after that command ended when nothing else holds it.

1. **One keeper, no window.** Start a devspace in the distribution and open it, and open a second VS Code window with the view of Devspaces. No console window appears. `wsl -d devspaces -u root --exec pgrep -c -x idle` says `1`. The log of Devspaces has "Devspaces starts the keeper of the WSL distribution devspaces (wslg.exe)".
2. **Runs after VS Code closed.** Choose **Keep Running When Closed** for the devspace of test 1, and close VS Code. 10 minutes later, `wsl --list --running` still names `devspaces`.
3. **Stops when nothing runs, also with a window open.** Open VS Code, choose **Stop When Closed** and **Stop** for the devspace, and leave the window open without using Devspaces. The Monitor ends 5 minutes after the stop, and the workers of Devspaces close 10 minutes after their last use; about 2 minutes after the last container stopped, `wsl --list --running` no longer names `devspaces`. Then `wsl -d devspaces -u root -- cat /var/log/devspaces-idle.log` shows "The keeper runs the idle script.", "Busy: a container runs.", "Nothing runs in the VM of Devspaces (1 of 2 checks).", "(2 of 2 checks)" and "The VM of Devspaces stops.".
4. **The background leaves it stopped.** After test 3, click into the view of Devspaces: the view shows the devspace as stopped, with **Start**, `wsl --list --running` still does not name `devspaces`, and the log of Devspaces says that the distribution does not run and that Devspaces does not start it for its work in the background.
5. **A start starts it.** Start the devspace again: the distribution runs, and `pgrep -c -x idle` of test 1 says `1` again.

## The scheduled task on Windows

[`R-VM-005`](requirements.md#r-vm-005), `src/core/docker/wslTask.ts`. Before the tests: Windows 10 or 11 (Home too), a Windows user without administrator rights, WSL of the Microsoft Store, the WSL distribution of Devspaces set up with this build, and one devspace started there once, so that the Monitor exists. `whoami /user` shows the SID of your user; below, `<task>` is `nimblescape Devspaces WSL <SID>`.

1. **Created after the setup, without a prompt.** No prompt of Windows appeared at the setup. The log of Devspaces has "Devspaces wrote its scheduled task". `schtasks /Query /TN "<task>" /V /FO LIST` shows the task: "Run As User" is your user, "Logon Mode" is "Interactive only", "Scheduled Type" is daily at 06:12 (the default schedule 06:07 plus 5 minutes). `%LOCALAPPDATA%\nimblescape\devspaces\task\task.xml` exists.
2. **The triggers follow the setting.** Set `devspaces.cacheUpdateSchedule` to `30 */3 * * 1-5`: Task Scheduler (`taskschd.msc`, root folder **Task Scheduler Library**) shows 8 weekly triggers, Monday to Friday, at 00:35, 03:35, … 21:35. Set it to `90`: one daily trigger at 00:05 that repeats every 1 hour 30 minutes for 1 day. Set it back to the default: one daily trigger at 06:12. Each change writes one line in the log.
3. **A new window changes nothing.** Reload the window: no new line "Devspaces wrote its scheduled task", and the time of `task.xml` stays.
4. **A run while VS Code is closed.** Set the schedule to a time 2 minutes from now (for example `40 14 * * *` at 14:38), close VS Code, and stop the distribution (`wsl --terminate devspaces`). 5 minutes after that time, no console window appears, and `wsl --list --verbose` shows `devspaces` as running. It stops by itself about 2 minutes after the Monitor ended (5 minutes after its background run). Then `wsl -d devspaces -u root -- cat /var/log/devspaces-task.log` shows "The task starts the Monitor" and "The Monitor runs", and `wsl -d devspaces -u root -- docker logs devspaces-monitor` shows the background run. Task Scheduler shows "The operation completed successfully. (0x0)" as the last run result.
5. **A missed time.** Put the computer to sleep before a time of the schedule and wake it after that time: the task starts about 10 minutes after the wake (the history of the task in Task Scheduler, and the log of the task).
6. **On battery.** On a laptop on battery, test 4 runs as well.
7. **After the registration.** Write down whether Task Scheduler starts the task once about 10 minutes after test 1 or test 2 (a start boundary in the past with "Run task as soon as possible after a scheduled start is missed"). That is harmless: the Monitor runs its background run only when it is due.
8. **Removal.** **Devspaces: Remove the WSL Distribution of Devspaces…**: `schtasks /Query /TN "<task>"` says that the task does not exist, `task.xml` is gone, and the log has "Devspaces removed its scheduled task".
9. **A distribution of your own.** With a distribution `devspaces` that you made yourself (not with the setup of Devspaces), no task is created.

## The scheduled task on macOS

[`R-VM-005`](requirements.md#r-vm-005), `src/core/vm/vmTask.ts` and `src/vmTask/main.ts`. Before the tests: a Mac with the VM of Devspaces set up with this build, and one devspace started there once.

1. **Created after the setup.** `launchctl print gui/$(id -u)/com.nimblescape.devspaces.vm` shows the agent, and `~/.nimblescape/devspaces/task` has `vmTask.js`, `task.json` and `last-start.json`.
2. **A run while VS Code is closed.** Set the schedule to a time 2 minutes from now, quit VS Code, and wait until the VM powered itself off (`LIMA_HOME="$HOME/.nimblescape/devspaces/vm" "$HOME"/.nimblescape/devspaces/lima/*/bin/limactl list`). 5 minutes after that time, the VM runs, and `~/.nimblescape/devspaces/task/task.log` says that the Monitor runs with the schedule. Later the VM powers itself off again.
3. **A missed time.** Put the Mac to sleep before a time of the schedule and wake it after that time: the VM starts 5 minutes after the wake. Log out before a time of the schedule and log in after it: the VM starts 5 minutes after the login.
4. **No start without a missed time.** Log out and in when no time of the schedule passed since the last start: `task.log` gets no new line, and the VM stays off.
5. **Removal.** Delete the VM with the commands of [Uninstall](guide.md#uninstall) and open a window of VS Code: the agent and `~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist` are gone.

## The uninstall hook

[`R-GEN-008`](requirements.md#r-gen-008), `src/uninstall/main.ts` and `src/core/devspacesFiles.ts`. Run it on Windows (the WSL distribution) and on macOS (the Lima VM), with this build installed from its VSIX, because VS Code runs the hook only for an installed extension. CI runs the unit tests and the bundle with Node.js on Linux. After each uninstall, quit VS Code, start it again, and wait one minute; the lines of the hook are in `sharedprocess.log` (**Developer: Open Logs Folder**).

1. **With the VM.** Set up the VM of Devspaces, start a devspace there once, and turn on `devspaces.createDockerContext`. The scheduled task exists (macOS: `launchctl print gui/$(id -u)/com.nimblescape.devspaces.vm`; Windows: `schtasks /Query /TN "nimblescape Devspaces WSL <SID>"`, with the SID of `whoami /user`). Uninstall Devspaces in the Extensions view. After the start of VS Code: the same command says that the task does not exist (macOS: also `~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist` is gone), `docker context ls` lists no `devspaces`, and the VM still exists with the devspace in it (`limactl list` as in [The scheduled task on macOS](#the-scheduled-task-on-macos), or `wsl --list --verbose`), with `~/.nimblescape/devspaces/lima` (macOS) or `%LOCALAPPDATA%\nimblescape\devspaces\wsl` (Windows). The log has "Devspaces removed its scheduled task" and "exists, so the folder … stays". The folder `globalStorage/nimblescape.nimblescape-devspaces-2` of VS Code is gone.
2. **Without the VM.** Install this build again, open a window (the task comes back), and remove the VM with **Remove the VM…** in the menu of its row in the view **Docker Hosts**. Uninstall Devspaces. After the start of VS Code: `~/.nimblescape` (macOS) or `%LOCALAPPDATA%\nimblescape` (Windows) is gone, and the log has "Devspaces removed its folder".
3. **The current Docker context.** Install this build again with the VM and the setting of test 1, run `docker context use devspaces`, and uninstall Devspaces. After the start of VS Code: `docker context ls` still lists `devspaces` as the current context, and the log names the commands that remove it. Run `docker context use default` (or `desktop-linux`) afterwards.

## Remove Devspaces from This Computer

[`R-GEN-009`](requirements.md#r-gen-009), `src/vscode/computerCleanup.ts` and `removeFromComputer` in `src/vscode/controller.ts`. Run it on Windows (the WSL distribution) and on macOS (the Lima VM), with this build installed from its VSIX, because the command uninstalls the extension at its end. CI runs the unit tests only. Before the tests: the VM of Devspaces set up with this build and one devspace started there once; a remote host in the list of Devspaces with a password login, **Use a Key** chosen in its question, and one devspace started there once; the setting `devspaces.createDockerContext` on; the log of Devspaces open.

1. **Refused while in use.** Open the devspace in the VM in another window and run **Devspaces: Remove Devspaces from This Computer…** in the empty window: the warning says to close the windows of the devspaces first, and no question appears. Close that window.
2. **The question.** Run the command: one question "Remove Devspaces from this computer?" names the remote host, the VM with one devspace, the SSH key with its line on the remote host, the scheduled task, the Docker context and the folder of Devspaces, the recorded changes of both devspaces, and that VS Code then uninstalls the extension. Close the question: nothing changed (the devspaces, the VM, `~/.ssh/devspaces_ed25519`, and the line that ends with `devspaces@` in `~/.ssh/authorized_keys` on the host are still there).
3. **A host that does not answer.** Stop the SSH server of the remote host (or take its network away), run the command again and choose **Remove Everything**: the VM, the scheduled task, the Docker context and the folder go, the warning says that 2 things stay (what Devspaces has on the host, and the SSH key on this computer with its line on the host), and its buttons are **Show Details** and **Uninstall Anyway**. **Show Details** opens the log with a line "Stays on this computer: …" for each, and shows the warning again. Close it. The extension stays installed, and `~/.ssh/devspaces_ed25519` is still there.
4. **Everything.** Start the SSH server again, run the command again and choose **Remove Everything**: on the host, `docker ps -a`, `docker image ls` and `docker volume ls` list nothing of Devspaces and not the devspace, and `~/.ssh/authorized_keys` has no line of the key (other lines are unchanged, with the same mode). On this computer, `~/.ssh/devspaces_ed25519` and `devspaces_ed25519.pub` are gone, `docker context ls` lists no `devspaces`, the scheduled task does not exist (as in [The uninstall hook](#the-uninstall-hook)), and `~/.nimblescape` (macOS) or `%LOCALAPPDATA%\nimblescape` (Windows) is gone. The message says that VS Code uninstalls the extension, and the Extensions view no longer lists Devspaces. After the next start of VS Code, `sharedprocess.log` has the lines of the uninstall hook, which found nothing to remove.
5. **Cancel.** Install this build again, start a devspace on the remote host, run the command, choose **Remove Everything**, and click **Cancel** in the progress notification while the devspace is deleted: the warning says that the removal stopped before the end, the VM, the key and the folder of Devspaces are still there, and the extension stays installed.

## The view Docker Hosts and the VM

[`R-ENG-008`](requirements.md#r-eng-008), [`R-VM-010`](requirements.md#r-vm-010), `src/vscode/dockerHostsView.ts`, `src/vscode/vmCommands.ts` and `src/core/vm/vmState.ts`. Run it on Windows (the WSL distribution) and on macOS (the Lima VM); CI runs the unit tests only. Before the tests: the VM of Devspaces set up with this build, one devspace started there once, a remote host in the list of Devspaces, and the log of Devspaces open.

1. **The rows.** The view **Docker Hosts** is below the repositories. Its first row is `wsl:devspaces` (Windows) or `lima:devspaces` (macOS) with "Local VM of Devspaces" and its state, then the remote host. The Docker host of Devspaces has a check mark. No other WSL distribution and no other Lima VM is listed. The tooltip of the VM row names the space of its disk (on macOS also its memory and CPUs).
2. **No read without an open host.** Reload the window and wait one minute: the log has no line "The view Docker Hosts reads", because no host row is open. Stop the VM (test 6) and click **Refresh** of the view: the VM row says "Stopped", its row "Start the VM to see its containers, images, volumes and networks", and the VM does not start (`wsl --list --running`, or `limactl list`).
3. **The read.** Start the devspace. In the VM, make a service of your own: `wsl -d devspaces -u root -- docker run -d --name my-web --network my-net nginx` after `docker network create my-net` (on macOS `limactl shell devspaces sudo docker …`). Open the VM row: the groups **Containers**, **Images**, **Volumes** and **Networks** list first the dev container of the devspace, the Monitor, the worker of the window, the helper image `devspaces-worker:<hash>`, the build image `devspaces-buildx`, the workspace volume and the shared volumes, each with its purpose and size, then `my-web`, `nginx` and `my-net` with "not of Devspaces". `bridge`, `host` and `none` are listed, `my-net` with "1 container". The row **Build cache** shows a number of records and a size. `docker system df -v` in the VM (or `docker --context devspaces system df -v` with the setting `devspaces.createDockerContext`) shows the same sizes.
   - **Colors.** With the theme Dark Modern, then Light Modern: `my-web` (running) and `nginx` and `my-net` (used by it) are violet; the Monitor and the dev container of the devspace have the colors of the theme; a stopped worker and `devspaces-buildx` (no running container uses it) are gray, and `host` and `none` are a dimmed violet. The description of a row (for example "not of Devspaces · Running") has the color of its name. **Stop** `my-web` and click **Refresh**: `my-web`, `nginx` and `my-net` are a dimmed violet. With the theme Dark High Contrast, the dimmed violet is darker than the violet. In the repository view, the rows without a running devspace and the owners without one below them are gray; the row of the running devspace and its owner are not. Set `"workbench.colorCustomizations": { "devspaces.inactiveForeground": "#ff0000" }`: the gray rows of both views turn red. Set `"explorer.decorations": { "colors": false }`: the text of the rows has the colors of the theme, and only the icons are violet or gray. Remove both settings and **Start** `my-web` again.
   - **Stop, Start and Remove… of your own service.** Hover over `my-web` and over the dev container of the devspace: neither row shows a Stop button; **Stop** is in the context menu (right-click) of both. **Stop** on `my-web`: it says "Stopped", and **Start** is offered; **Start** runs it again. Stop it, select `my-web`, `my-net` and `nginx`, and click **Remove…**: the question says that some objects do not belong to Devspaces. After **Remove**, all three are gone. `bridge` has no **Remove…**. Make the network again with a container on it that never ran (`docker network create my-net`, then `docker create --name my-web --network my-net nginx`), click **Refresh**, and remove only `my-net`: the message says "Removed 0 of 1 objects … Left: my-net", the log says "A container uses this network.", and the network stays. Remove `my-web` and `my-net` again (in the VM) at the end.
   - **Remove Unused Build Cache….** On the row **Build cache**, run **Remove Unused Build Cache…**: the question says how much space it frees. After the answer, the row shows the new size, and the log names what Docker counts.
4. **Remove….** Stop the worker of a window that is closed (its row has **Stop**; after the stop, **Remove…**), select it together with the helper image, and click **Remove…**: one question names both. After **Remove**, the container is gone, and the message says that the image was left because a container uses it. The rows of the devspace have only **Stop** and **Delete…**.
5. **A remote host.** Open the remote host row: a password login asks for the password (when the host has no key), and the groups appear. Click the row: it only opens or closes, and the check mark and the first row of the repository view keep the Docker host of Devspaces. Choose the remote host in the first row of the repository view: the check mark moves to it.
6. **Stop the VM….** With the devspace running, run **Stop the VM…** in the menu of the VM row: the question names the devspace. After **Stop the VM**, the window of the devspace loses its connection, `wsl --list --running` does not name `devspaces` (macOS: `limactl list` says `Stopped`), and the VM row says "Stopped". Without a running devspace, **Stop the VM…** asks nothing.
7. **Start the VM.** Run **Start the VM** in the menu of the VM row: the progress of the test of the host shows, the VM runs afterwards, and the Docker host of Devspaces stays as it was. Two minutes after nothing runs there, the VM powers itself off again.
8. **Settings of the VM.** macOS: **Settings of the VM** opens the Settings editor with `devspaces.vmMemoryGiB` and `devspaces.vmCpus` only. Windows: the menu has no **Settings of the VM**, and the Command Palette has none either.
9. **Remove the VM….** Push the changes of the devspace first. **Remove the VM…** asks; after the answer, the VM is gone (`wsl --list`, or the folder `~/.nimblescape/devspaces/vm/devspaces` on macOS), the VM row says "Not set up", the scheduled task is gone, and the view of the repositories shows the setup of the VM. **Set Up** in the menu of the VM row sets it up again.
10. **Remove and Set Up the VM Again….** The VM row has no button for it. Run **Remove and Set Up the VM Again…** in the context menu of the VM row: after the question, the VM is removed and set up again, and Devspaces uses the new VM: the devspace of before is gone.
11. **The update every 30 seconds.** Open the VM row and the remote host row. In a terminal, run `docker run -d --name my-sleep alpine sleep 600` in the VM (test 3) and on the remote host: within 30 seconds, both hosts show `my-sleep` (running) without a click, and the log says "The view Docker Hosts reads … again: its objects changed". `docker stop my-sleep` and then `docker rm my-sleep`: each change shows within 30 seconds. With no change for two minutes, the log has no new line "reads … again". Collapse the remote host row, change something there, and wait one minute: nothing reads it; open it again: the change shows within 30 seconds.
12. **The pauses of the update.** Switch to another program for 3 minutes and make a change in the VM meanwhile: the view does not change; switch back: the change shows at once. Show the Explorer instead of Devspaces for one minute and make a change: it shows at once when the view shows again.
13. **The update and the VM.** Stop the devspace and keep the VM row open while the view is visible. The VM goes to sleep as usual (macOS within about 4 minutes, `limactl list` says `Stopped`; Windows: `wsl --list --running` does not name `devspaces` within about 5 minutes): the VM row says "Stopped" within 30 seconds, and the view does not start the VM again. Start the devspace: within 30 seconds after the VM runs, the VM row shows its objects again without a click.
14. **The update and a password.** On a remote host that needs a password, open its row (it asks once). Wait 3 minutes with the view hidden, so that the login closes, then show the view: the update asks nothing and logs once that it uses only an open login; the rows of before stay. **Refresh** asks for the password, and the updates go on.

## The utilization page

[`R-ENG-009`](requirements.md#r-eng-009), `src/vscode/usagePage.ts`, `src/vscode/usagePageModel.ts`, `resources/usagePage/` and `src/core/hosts/`. Run tests 1 to 8 on macOS (Lima), on Linux (Lima) and on Windows (the WSL distribution), and tests 9 and 10 once with a remote host that needs a password (no key, no SSH agent); CI runs the unit tests and the samples in BusyBox ash, dash and over a real SSH server only. Before the tests: the VM of Devspaces set up with this build, one devspace started there, and the log of Devspaces open.

1. **The values.** **Show Utilization** on the VM row (or the pulse button on the row) opens the page "Utilization: lima:devspaces" (Windows: `wsl:devspaces`) in the editor; a second **Show Utilization** shows the same page. After at most two readings, the status says "Live · every 2 s", and the cards show CPU, memory and the disk of the Docker data with "This computer: free for the disk of the VM". The table lists the dev container, the Monitor and the worker by name. In the VM, `docker stats --no-stream` shows about the same CPU and the same memory for each container (the page shows a mean over 2 seconds). Windows: the footer says that the totals include the other WSL distributions and Docker Desktop.
2. **Pressure.** The CPU card shows a line "Pressure: CPU … · memory … · I/O …", not "Pressure: not available in this kernel", so the kernel of the VM has pressure (PSI) on; `cat /proc/pressure/cpu` in the VM shows the same kind of values. Write the kernel version (the description of the page) into the pull request.
3. **One login.** While the page reads, the log has the line "The shell on lima:devspaces is open" (Windows: `wsl:devspaces`) at most once, not once for each reading. ## The report of a resource

[`R-ENG-010`](requirements.md#r-eng-010), `src/vscode/reportPage.ts`, `src/vscode/reportPageModel.ts`, `resources/reportPage/`, `src/core/hosts/reportRead.ts`, `src/core/hosts/monitorLog.ts`, `src/core/hosts/devspaceReport.ts`, `src/core/hosts/imageReport.ts` and `src/core/hosts/helperReport.ts`. Before the tests: the VM of Devspaces set up with this build, one devspace started there, its window closed again, the Monitor run at least once (**Update All Images Now**), and the log of Devspaces open.

1. **The click.** Open the VM row of the view **Docker Hosts**, then **Volumes**, and click `devspaces-vscode`: a tab "devspaces-vscode" with its title in italics (a preview tab) opens in the editor, the focus stays in the view, and the header says "Reading…", then "Read today …". The page shows the versions of the VS Code Server and the extensions, each with a tag such as "kept: used 5 minutes ago" or "removed at the next cleanup", and the facts of Docker with the containers that use the volume. The versions match `ls` of the folder `server` of the volume in the VM.
2. **Preview tabs and kept tabs.** Click the next row: its report replaces the preview tab, whose title stays in italics. Click a row of an image that is not of Devspaces (for example `node:…` of another project, or pull `hello-world` in the VM first): the page shows only the facts of Docker, with the name in violet, and the tab has the name after the last `/` (its tooltip shows the whole address). Click the row of the kept tab: the kept tab shows, and it reads nothing (the header keeps its time). The page has no button **Keep Open**.
3. **A tab after a reload of the window.** Keep a report tab of a resource of a remote host open, and run **Developer: Reload Window**: the tab opens again, says "The view Docker Hosts does not show this resource now.", and nothing asks for a password. Open the host row in the view, then click **Refresh** on the page: it reads.
4. **The Monitor.** Click the container `devspaces-monitor`: the report shows "What it did: the last runs" with the run of before the tests, the next background run, and the button **Show Log of the Monitor**. The button opens a document "devspaces-monitor.log" with the last lines of the log, each with two times as `2026-11-12 22:07:25.606` in the time zone of this computer; `docker logs --tail 20 --timestamps devspaces-monitor` in the VM shows the same last lines with the same times in UTC. The document cannot be edited.
5. **Refresh and the selection.** Click **Refresh**: the content is dimmed while it reads, and the place of the scroll stays. Select a text of the page and copy it: the selection stays while the page reads.
6. **The VM.** Let the VM go to sleep (stop the devspace and wait about 4 minutes, `limactl list` says `Stopped`; Windows: `wsl --list --running` does not name `devspaces`), keep a page of a resource of the VM open, and click **Refresh**: the page says "The VM of Devspaces does not run." with **Start the VM**, and the VM stays off. **Start the VM** starts it, and the page reads.

Click its workspace volume: "Git at the last record" shows 1 uncommitted file with the tag "not on GitHub", recorded at the close of the window, and the same numbers as the row of the devspace in the repository view. With a Docker Compose devspace (for example with a `db` service), click the container of the service and its data volume: the service shows its image with "pulled and not built", and the volume says "kept unless you tick it" at Delete….
9. **The images and the helpers.** Click the devspace image `devspaces-…:N`: "The build" says "the current image of the devspace", and "Built from" lists the image of the configuration with the digest of the build and "Registry now" with the time of the last run of the Monitor; the digest of the build is the one of `docker image inspect` of that base image (RepoDigests) when the image is up to date. Click the base image: "This version" has the same answer of the registry, and "Devspaces that use it" names the devspace. Click the helper image `devspaces-worker:…`: it says "this version of Devspaces" and the last check of the Monitor, the same time as "Check of the helper image" on the report of the volume `devspaces-monitor`. Click `devspaces-buildx:…`: it says "the pin of this version of Devspaces". With a window of a devspace open, click its worker `…-worker1`: it names that devspace.
10. **The layers of an image.** Click an image that is not of Devspaces (for example `hello-world`) and a devspace image: after the facts of Docker, **Layers** lists the steps of the build, the first one first (the `FROM` image steps at the top), each with its size and time. ## The settings of the view Docker Hosts and its console

[`R-ENG-008`](requirements.md#r-eng-008), [`R-ENG-010`](requirements.md#r-eng-010), `src/vscode/hostConsole.ts`, `src/core/hosts/hostConsole.ts`, `src/vscode/dockerHostsSettings.ts`, `src/core/relay/dockerPipeRules.ts`. Run these tests on macOS and on Windows, with the VM of Devspaces and a remote host with a password.

1. **Read only.** Without the settings (the defaults), open the view **Docker Hosts**: no row has a button except **Show Utilization** and **Refresh** of a host row, the context menu of an object has only **Show Report**, the title has no **+**, and the menu **…** of the view is empty. A click on an object opens its report. While the VM is stopped, its row says "The VM is stopped: …" and a click on it starts nothing; its report page and its utilization page have no **Start the VM**.

Set `devspaces.dockerHostsActions` to `disabled`: they disappear. Turn the setting off again with `contextMenu`: they disappear at once, and the Command Palette still has **Remove Devspaces from This Docker Engine…** and **Remove the VM…**.
5. **Logs.** On the report of the Monitor, **Show Log of the Monitor** is missing, and the menu of a container row has no **Show Log**. The menu of every container row now has **Show Log**, also with `devspaces.dockerHostsActions` set to `disabled`, and also for a stopped container and a container that is not of Devspaces (for example `docker run -d --name hello alpine echo hello` on the host: its log shows `hello`). Stop the VM: **Show Log** on a container row of the VM, if the row is still shown, says that the VM does not run and does not start it. Do the same for the worker of the remote host from a second computer or VS Code profile: the same log. A worker of an older version says that it has no log. Turn it off again: the button disappears from the open report at once. On a remote host with an open devspace of the window, `docker logs devspaces-monitor` with the Docker pipe of the extension (its address is in the log of Devspaces) is refused with "the logs of containers are off".
6. **The gear.** Turn on `devspaces.dockerHostsSettingsButton`: a gear appears in the title of the view. It opens a quick pick with four groups (actions of the view, actions that remove or delete, logs of containers, Open Console on the host rows), the current values marked; a choice changes the setting in your user settings, and the view follows at once. The gear itself is not in it. The Command Palette has no command for it.
7. **The console of the VM.** Turn on `devspaces.dockerHostsConsoleButton`: each host row with an engine has a terminal button next to **Show Utilization**. Click it on the VM row: a terminal "Console: VM of Devspaces" opens with a shell in the VM (macOS: the user of Lima, `whoami`; Windows: `root`). 9. **In a devspace window.** In the window of a devspace, open a console of the VM: it runs on your computer and reaches the VM, not the container.
