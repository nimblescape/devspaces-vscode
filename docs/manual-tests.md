# Manual tests

The runners of GitHub have no WSL 2 on Windows and no nested virtualization on macOS, so CI cannot test the VM of Devspaces there. Each step that changes the VM on Windows or macOS has a list of manual tests here ([`R-VM-009`](requirements.md#r-vm-009)). Run them with a build of the branch (`npm run install-local`), and write the results into the pull request.

## The WSL distribution from the image of the VM

[`R-ENG-005`](requirements.md#r-eng-005), [`R-VM-002`](requirements.md#r-vm-002), [`R-VM-007`](requirements.md#r-vm-007), `src/core/docker/wslSetup.ts` and `src/vscode/wslSetupCommands.ts`. Before the tests: Windows 10 or 11 (Home too), on x64 and, when one is at hand, on Arm, a Windows user without administrator rights, WSL of the Microsoft Store, and no distribution `devspaces` (`wsl --list`).

1. **Setup without a question.** **Set Up Docker for Devspaces** in the view: no question of Devspaces and no prompt of Windows. The progress shows "Downloading the VM of Devspaces" with the megabytes, then "Creating the WSL distribution.", then "Starting the WSL distribution and Docker." The log names the version of the image, `ghcr.io/nimblescape/devspaces-vm`, the size of the file, and `Docker Engine` with its version at the end. Write down how long the first start took.
2. **The system of the image.** `wsl -d devspaces -u root -- cat /etc/os-release` names Debian 13, `wsl -d devspaces -u root -- systemctl is-active docker devspaces-upgrade.timer` says `active` twice, and `wsl -d devspaces -u root -- ls /mnt/c` fails, because no drive of Windows is mounted. The Start menu has no entry `devspaces`, and Windows Terminal has no profile for it.
3. **Not the default.** `wsl --list` does not mark `devspaces` as the default, also on a computer with no other distribution (then WSL has no default).
4. **A devspace.** Start a devspace and open it: it opens as on macOS and Linux, and `wsl -d devspaces -u root -- docker ps` lists its container.
5. **The upgrade in the VM.** Keep the distribution running for 2 minutes after its first start: `wsl -d devspaces -u root -- journalctl -u devspaces-upgrade --no-pager` shows a run of the service. It says `skipped` when the image is less than 20 hours old (the version of the image in the log is its build time in UTC), and otherwise it upgrades the packages. The devspace of test 4 still runs afterwards.
6. **The command again.** Run **Devspaces: Set Up Docker for Devspaces in WSL…** again: no question, no download, and the log says that the distribution exists and Devspaces uses it.
7. **Without a connection.** Remove the distribution (**Devspaces: Remove the WSL Distribution of Devspaces…**), turn off the network, and set it up again: the message says that the image of the VM could not be downloaded, and **Show details** names `ghcr.io`. Turn on the network, and set it up again.

## The choice of the Docker host

[`R-ENG-001`](requirements.md#r-eng-001), `src/vscode/remoteDockerCommands.ts`. Run it on Windows, macOS and Linux. Before the tests: the VM of Devspaces is not set up (on Windows no distribution `devspaces` in `wsl --list`; on macOS and Linux no folder `~/.nimblescape/devspaces/vm/devspaces`), and Devspaces uses a remote host (**Devspaces: Use a Remote Docker Host…**).

1. **No entry for the Docker of this computer.** The command palette has no **Devspaces: Use the Local Docker**. **Devspaces: Choose the Docker Host…** (also the first row of the view) lists the remote host, and in the group **WSL** (Windows) or **Lima** (macOS and Linux) the entry **Set Up Docker for Devspaces in WSL…** or **Set Up Docker for Devspaces in Its VM…**. It has no entry for Docker Desktop or for the Docker Engine of this computer, also when one of them runs.
2. **The setup from the choice.** Choose that entry: the setup of the VM runs as from the button of the view, and afterwards Devspaces uses the VM. **Choose the Docker Host…** then lists `wsl:devspaces` (Windows) or the Lima VM (macOS and Linux) in that group, and no setup entry.
3. **Back to the VM.** Choose the remote host, and then the VM again in **Choose the Docker Host…**: no setup runs, and the first row of the view names the VM.
4. **Removal of the current host.** While Devspaces uses the remote host, remove it with **Devspaces: Remove a Host from the List…**: the message says that Devspaces has no Docker host now, and the view shows the Docker setup, not the Docker of this computer.

## Windows with Docker Desktop

[`R-ENG-001`](requirements.md#r-eng-001), [`R-VM-008`](requirements.md#r-vm-008). Before the tests: Windows 10 or 11 with Docker Desktop on WSL 2, running, a Windows user without administrator rights for Devspaces, and no distribution `devspaces` (`wsl --list`). Write down the versions of Windows, WSL (`wsl --version`) and Docker Desktop, and `docker context show` in a terminal of Windows.

1. **The setup shows although Docker Desktop runs.** The view of Devspaces shows the Docker setup with **Set Up Docker for Devspaces**, not the repositories. **Devspaces: Choose the Docker Host…** has no entry for Docker Desktop.
2. **The setup next to Docker Desktop.** Run **Set Up Docker for Devspaces**: it runs as test 1 of [The WSL distribution from the image of the VM](#the-wsl-distribution-from-the-image-of-the-vm). Afterwards `wsl --list --verbose` shows `devspaces` and `docker-desktop` as running, and `docker context show` names the same context as before.
3. **Two engines.** `wsl -d devspaces -u root -- docker info --format "{{.Name}}"` names the distribution of Devspaces, and `docker info --format "{{.Name}}"` in a terminal of Windows names `docker-desktop`. `docker ps -a` in a terminal of Windows does not list the containers of Devspaces.
4. **No integration of Docker Desktop.** Docker Desktop, **Settings**, **Resources**, **WSL integration**: `devspaces` is not turned on. Write down whether Docker Desktop lists it.
5. **A devspace next to a container of Docker Desktop.** Start a devspace and open it. In a terminal of Windows, run `docker run -d --rm --name port-test -p 8080:80 nginx` on Docker Desktop, and `wsl -d devspaces -u root -- docker run -d --rm --name port-test -p 127.0.0.1:8080:80 nginx` in the distribution of Devspaces. Write down whether both start, and what `curl http://localhost:8080` in a terminal of Windows and `wsl -d devspaces -u root -- curl -s http://127.0.0.1:8080` answer. Then stop both containers (`docker stop port-test`, `wsl -d devspaces -u root -- docker stop port-test`).
6. **Docker Desktop quits.** Quit Docker Desktop (its icon in the notification area, **Quit Docker Desktop**): the devspace of test 5 keeps running, and its window stays connected. Start Docker Desktop again: the same.
7. **Devspaces of an older version.** On a computer where an older version of Devspaces made devspaces in Docker Desktop: they stay in Docker Desktop (`docker ps -a`), and Devspaces does not move or remove them. Write down what the view of Devspaces shows for them.

## The idle script in WSL

[`R-VM-004`](requirements.md#r-vm-004), `src/core/docker/wslKeeper.ts` and `src/core/docker/wslLifetime.ts`. Before the tests: the WSL distribution of Devspaces set up with this build, and no devspace running there. `wsl --list --running` shows whether the distribution runs without starting it; each `wsl -d devspaces …` below starts it when it does not run, and WSL stops it again 15 seconds after that command ended when nothing else holds it.

1. **One keeper, no window.** Start a devspace in the distribution and open it, and open a second VS Code window with the view of Devspaces. No console window appears. `wsl -d devspaces -u root --exec pgrep -c -x idle` says `1`. The log of Devspaces has "Devspaces starts the keeper of the WSL distribution devspaces (wslg.exe)".
2. **Runs after VS Code closed.** Choose **Keep Running When Closed** for the devspace of test 1, and close VS Code. 10 minutes later, `wsl --list --running` still names `devspaces`.
3. **Stops when nothing runs, also with a window open.** Open VS Code, choose **Stop When Closed** and **Stop** for the devspace, and leave the window open without using Devspaces. The Monitor ends 5 minutes after the stop, and the workers of Devspaces close 10 minutes after their last use; about 2 minutes after the last container stopped, `wsl --list --running` no longer names `devspaces`. Then `wsl -d devspaces -u root -- cat /var/log/devspaces-idle.log` shows "The keeper runs the idle script.", "Busy: a container runs.", "Nothing runs in the VM of Devspaces (1 of 2 checks).", "(2 of 2 checks)" and "The VM of Devspaces stops.".
4. **The background leaves it stopped.** After test 3, click into the view of Devspaces: the view shows the devspace as stopped, with **Start**, `wsl --list --running` still does not name `devspaces`, and the log of Devspaces says that the distribution does not run and that Devspaces does not start it for its work in the background.
5. **A start starts it.** Start the devspace again: the distribution runs, and `pgrep -c -x idle` of test 1 says `1` again.

## The scheduled task on Windows

[`R-VM-005`](requirements.md#r-vm-005), `src/core/docker/wslTask.ts`. Before the tests: Windows 10 or 11 (Home too), a Windows user without administrator rights, WSL of the Microsoft Store, the WSL distribution of Devspaces set up with this build, and one devspace started there once, so that the Monitor exists. `whoami /user` shows the SID of your user; below, `<task>` is `nimblescape Devspaces WSL <SID>`.

1. **Created after the setup, without a prompt.** No prompt of Windows appeared at the setup. The log of Devspaces has "Devspaces wrote its scheduled task". `schtasks /Query /TN "<task>" /V /FO LIST` shows the task: "Run As User" is your user, "Logon Mode" is "Interactive only", "Scheduled Type" is daily at 06:12 (the default schedule 06:07 plus 5 minutes). `%LOCALAPPDATA%\nimblescape\devspaces\task\task.xml` exists.
2. **The triggers follow the setting.** Set `devspaces.cacheUpdateSchedule` to `30 */3 * * 1-5`: Task Scheduler (`taskschd.msc`, root folder **Task Scheduler Library**) shows 8 weekly triggers, Monday to Friday, at 00:35, 03:35, … 21:35. Set it to `90`: one daily trigger at 00:05 that repeats every 1 hour 30 minutes for 1 day. Set it back to the default: one daily trigger at 06:12. Each change writes one line in the log.
3. **A new window changes nothing.** Reload the window: no new line "Devspaces wrote its scheduled task", and the time of `task.xml` stays.
4. **A run while VS Code is closed.** Set the schedule to a time 2 minutes from now (for example `40 14 * * *` at 14:38), close VS Code, and stop the distribution (`wsl --terminate devspaces`). 5 minutes after that time, no console window appears, and `wsl --list --verbose` shows `devspaces` as running. It stops by itself about 2 minutes after the Monitor ended (5 minutes after its background run). Then `wsl -d devspaces -u root -- cat /var/log/devspaces-task.log` shows "The task starts the Monitor" and "The Monitor runs", and `wsl -d devspaces -u root -- docker logs devspaces-monitor` shows the background run. Task Scheduler shows "The operation completed successfully. (0x0)" as the last run result.
5. **A missed time.** Put the computer to sleep before a time of the schedule and wake it after that time: the task starts about 10 minutes after the wake (the history of the task in Task Scheduler, and the log of the task).
6. **On battery.** On a laptop on battery, test 4 runs as well.
7. **After the registration.** Write down whether Task Scheduler starts the task once about 10 minutes after test 1 or test 2 (a start boundary in the past with "Run task as soon as possible after a scheduled start is missed"). That is harmless: the Monitor runs its background run only when it is due.
8. **Removal.** **Devspaces: Remove the WSL Distribution of Devspaces…**: `schtasks /Query /TN "<task>"` says that the task does not exist, `task.xml` is gone, and the log has "Devspaces removed its scheduled task".
9. **A distribution of your own.** With a distribution `devspaces` that you made yourself (not with the setup of Devspaces), no task is created.

## The scheduled task on macOS

[`R-VM-005`](requirements.md#r-vm-005), `src/core/vm/vmTask.ts` and `src/vmTask/main.ts`. Before the tests: a Mac with the VM of Devspaces set up with this build, and one devspace started there once.

1. **Created after the setup.** `launchctl print gui/$(id -u)/com.nimblescape.devspaces.vm` shows the agent, and `~/.nimblescape/devspaces/task` has `vmTask.js`, `task.json` and `last-start.json`.
2. **A run while VS Code is closed.** Set the schedule to a time 2 minutes from now, quit VS Code, and wait until the VM powered itself off (`LIMA_HOME="$HOME/.nimblescape/devspaces/vm" "$HOME"/.nimblescape/devspaces/lima/*/bin/limactl list`). 5 minutes after that time, the VM runs, and `~/.nimblescape/devspaces/task/task.log` says that the Monitor runs with the schedule. Later the VM powers itself off again.
3. **A missed time.** Put the Mac to sleep before a time of the schedule and wake it after that time: the VM starts 5 minutes after the wake. Log out before a time of the schedule and log in after it: the VM starts 5 minutes after the login.
4. **No start without a missed time.** Log out and in when no time of the schedule passed since the last start: `task.log` gets no new line, and the VM stays off.
5. **Removal.** Delete the VM with the commands of [Uninstall](guide.md#uninstall) and open a window of VS Code: the agent and `~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist` are gone.

## The view Docker Hosts and the VM

[`R-ENG-008`](requirements.md#r-eng-008), [`R-VM-010`](requirements.md#r-vm-010), `src/vscode/dockerHostsView.ts`, `src/vscode/vmCommands.ts` and `src/core/vm/vmState.ts`. Run it on Windows (the WSL distribution) and on macOS (the Lima VM); CI runs the unit tests only. Before the tests: the VM of Devspaces set up with this build, one devspace started there once, a remote host in the list of Devspaces, and the log of Devspaces open.

1. **The rows.** The view **Docker Hosts** is below the repositories. Its first row is `wsl:devspaces` (Windows) or `lima:devspaces` (macOS) with "Local VM of Devspaces" and its state, then the remote host. The Docker host of Devspaces has a check mark. No other WSL distribution and no other Lima VM is listed. The tooltip of the VM row names the space of its disk (on macOS also its memory and CPUs).
2. **No read in the background.** Reload the window and wait one minute: the log has no line "The view Docker Hosts reads". Stop the VM (test 6) and click **Refresh** of the view: the VM row says "Stopped", its row "Start the VM to see its containers, images, volumes and networks", and the VM does not start (`wsl --list --running`, or `limactl list`).
3. **The read.** Start the devspace. In the VM, make a service of your own: `wsl -d devspaces -u root -- docker run -d --name my-web --network my-net nginx` after `docker network create my-net` (on macOS `limactl shell devspaces sudo docker …`). Open the VM row: the groups **Containers**, **Images**, **Volumes** and **Networks** list first the dev container of the devspace, the Monitor, the worker of the window, the helper image `devspaces-worker:<hash>`, the build image `devspaces-buildx`, the workspace volume and the shared volumes, each with its purpose and size, then `my-web`, `nginx` and `my-net` with "not of Devspaces". `bridge`, `host` and `none` are listed, `my-net` with "1 container". The row **Build cache** shows a number of records and a size. `docker system df -v` in the VM (or `docker --context devspaces system df -v` with the setting `devspaces.createDockerContext`) shows the same sizes.
   - **Stop, Start and Remove… of your own service.** **Stop** on `my-web`: it says "Stopped", and **Start** is offered; **Start** runs it again. Stop it, select `my-web`, `my-net` and `nginx`, and click **Remove…**: the question says that some objects do not belong to Devspaces. After **Remove**, all three are gone. `bridge` has no **Remove…**. Make the network again with a container on it that never ran (`docker network create my-net`, then `docker create --name my-web --network my-net nginx`), click **Refresh**, and remove only `my-net`: the message says "Removed 0 of 1 objects … Left: my-net", the log says "A container uses this network.", and the network stays. Remove `my-web` and `my-net` again (in the VM) at the end.
   - **Colors.** With the theme Dark Modern, then Light Modern: `my-web` (running) and `nginx` and `my-net` (used by it) are violet; the Monitor and the dev container of the devspace have the colors of the theme; a stopped worker and `devspaces-buildx` (no running container uses it) are gray, and `host` and `none` are a dimmed violet. **Stop** `my-web` and click **Refresh**: `my-web`, `nginx` and `my-net` are a dimmed violet. In the repository view, the rows without a running devspace and the owners without one below them are gray; the row of the running devspace and its owner are not. Set `"workbench.colorCustomizations": { "devspaces.inactiveForeground": "#ff0000" }`: the gray rows of both views turn red.
   - **Remove Unused Build Cache….** On the row **Build cache**, run **Remove Unused Build Cache…**: the question says how much space it frees. After the answer, the row shows the new size, and the log names what Docker counts.
4. **Remove….** Stop the worker of a window that is closed (its row has **Stop**; after the stop, **Remove…**), select it together with the helper image, and click **Remove…**: one question names both. After **Remove**, the container is gone, and the message says that the image was left because a container uses it. The rows of the devspace have only **Stop** and **Delete…**.
5. **A remote host.** Open the remote host row: a password login asks for the password (when the host has no key), and the groups appear. Click the row: Devspaces tests the host and uses it, and the check mark moves to it.
6. **Stop the VM….** With the devspace running, run **Stop the VM…** in the menu of the VM row: the question names the devspace. After **Stop the VM**, the window of the devspace loses its connection, `wsl --list --running` does not name `devspaces` (macOS: `limactl list` says `Stopped`), and the VM row says "Stopped". Without a running devspace, **Stop the VM…** asks nothing.
7. **Start the VM.** Run **Start the VM** in the menu of the VM row: the progress of the test of the host shows, the VM runs afterwards, and the Docker host of Devspaces stays as it was. Two minutes after nothing runs there, the VM powers itself off again.
8. **Settings of the VM.** macOS: **Settings of the VM** opens the Settings editor with `devspaces.vmMemoryGiB` and `devspaces.vmCpus` only. Windows: the menu has no **Settings of the VM**, and the Command Palette has none either.
9. **Remove the VM….** Push the changes of the devspace first. **Remove the VM…** asks; after the answer, the VM is gone (`wsl --list`, or the folder `~/.nimblescape/devspaces/vm/devspaces` on macOS), the VM row says "Not set up", the scheduled task is gone, and the view of the repositories shows the setup of the VM. A click on the VM row sets it up again.
10. **Remove and Set Up the VM Again….** After the question, the VM is removed and set up again, and Devspaces uses the new VM: the devspace of before is gone.
