## Requirements

- Visual Studio Code 1.125 or later, the build of Microsoft. The Dev Containers extension is licensed for this build only.
- Docker: Devspaces runs your devspaces in a VM of its own with Docker Engine: on Windows a WSL distribution of Devspaces (with WSL 2), on macOS and Linux a Lima VM (on Linux with QEMU and `/dev/kvm`), see [Installing Docker](#installing-docker). It never uses Docker Desktop or Docker Engine of your computer, on any platform; devspaces that an older version made there stay there and are not moved. Docker can also run on another computer that you reach over SSH, and then your computer needs no Docker (see [Remote Docker host](#remote-docker-host)). Podman is not supported.
- A GitHub account on github.com. Devspaces does not work with GitHub Enterprise Server or GHE.com: it uses the GitHub sign-in of VS Code for github.com and the GitHub API at `api.github.com`. When the settings `github-enterprise.uris` or `github-enterprise.uri` of VS Code name a GitHub Enterprise instance, the view shows a note under the button **Sign in with GitHub**.
- The Dev Containers extension (`ms-vscode-remote.remote-containers`). VS Code installs it together with Devspaces.

## Install

Install **Devspaces** from the Visual Studio Marketplace: search for "Devspaces" in the Extensions view of VS Code, or run:

```sh
code --install-extension nimblescape.nimblescape-devspaces-2
```

VS Code installs the Dev Containers extension with it. To install a `.vsix` file instead, run **Extensions: Install from VSIX…** or `code --install-extension nimblescape-devspaces-2-<version>.vsix`; to create the file yourself, see [Build from source](#build-from-source).

### Update from version 0.4.0 or older

This section and the next one are about the first extension of Devspaces, with the ID `nimblescape.nimblescape-devspaces`: 0.4.0 and 0.2.1 are versions of that extension. Devspaces 2 started at version 0.1.0 with the new names. When you used the first extension on a Docker engine, remove its old objects there as described here.

Version 0.4.0 and older named the image of the worker `devspaces-helper:<hash>` (with the second tag `devspaces-monitor:<hash>`), its cache volume `devspaces-helper-cache`, and its labels `nimblescape.devspaces.helper…`. Later versions name them `devspaces-worker:<hash>`, `devspaces-worker-cache`, and `nimblescape.devspaces.worker…`, build the new image at the first use, and do not use or remove the old objects. On each Docker engine, after the first start of a devspace with the new version (which replaces the Monitor), remove the old objects, because the host access checks of the new version do not protect the old volume:

```sh
for tag in $(docker image ls devspaces-helper --format '{{.Tag}}'); do docker image rm "devspaces-helper:$tag" "devspaces-monitor:$tag"; done
docker volume rm devspaces-helper-cache
```

A `devspaces-monitor:<hash>` tag that does not exist gives an error for that tag only. All computers that use one Docker engine should have the same version, so that the worker of only one version runs there.

### Update from version 0.2.1 or older

Version 0.2.1 and older named the Docker objects of Devspaces `devspace-…` and their labels `nimblescape.devspace.…`. Later versions name them `devspaces-…` and `nimblescape.devspaces.…`, and they do not use the objects of the older versions: the sidebar does not show a devspace of an older version, and a start of its repository creates a new devspace that clones the repository again.

1. Before the update, push the changes in each devspace.
2. After the update, remove the objects of the older version on each Docker engine before you start a devspace, because the host access checks of the new version do not protect them. These are the containers, volumes, images, and networks whose names start with `devspace-` (without `s`): the Monitor container and volume `devspace-monitor`, the volumes `devspace-vscode` and `devspace-helper-cache`, the images `devspace-helper` and `devspace-monitor`, and the containers, volumes, images, and Compose networks of each devspace. Volumes that a configuration names itself (for example `api-node_modules`) have other names; `docker volume ls --filter label=nimblescape.devspace.id` lists them with the other volumes of the devspaces.
3. Rename your settings and keybindings as described in [Settings](#settings).

All computers that use one Docker engine need the same version: an older version does not see the devspaces of a newer one, and the other way round.

## First steps

1. Select the **Devspaces** icon in the activity bar. If Docker is not installed, the view shows the steps to set it up (see [Installing Docker](#installing-docker)), or to use Docker on another computer instead (see [Remote Docker host](#remote-docker-host)).
2. Select **Sign in with GitHub**. The list shows your repositories that have a Dev Container configuration, grouped by owner (with a [default image](#default-image), also the repositories without one). The first load can take a moment with many repositories; the view shows the repositories as they arrive, and later updates read only the repositories that changed.
3. Select **Start** on a repository, double-click it, or select it and press `Enter`. A repository with several sources (several configurations, or a configuration and a [default image](#default-image)) has one child row per source; **Start** is on the child rows then, and a double-click or `Enter` on the repository starts its first child row. The first start creates the devspace: it clones the repository, builds the image, and creates the container, which can take several minutes. Your first devspace also builds the helper image of Devspaces, in a short container `devspaces-build-<id>` on the Docker engine, which first pulls the build image `docker/buildx-bin` once from Docker Hub. Later starts take seconds.
4. The window connects to the container. You work in the repository folder under `/workspaces/<name>`.

The first start of a repository that belongs neither to one of your accounts nor to one of their organizations asks for a confirmation, because it runs code from that repository.

To go to another devspace, use **Devspaces: Switch Devspace…** (on macOS `Cmd+Alt+E`; on Windows and Linux, [set a key](#status-bar-and-switcher)) or select the Devspaces item in the status bar.

## Several GitHub accounts

VS Code can be signed in to several GitHub accounts at the same time, for example a personal account and the account of a course. Devspaces uses every GitHub account of VS Code that you allowed for Devspaces, and shows one list for all of them.

- **Add an account.** Select **Add GitHub Account…** in the title bar of the view (or run **Devspaces: Add GitHub Account…**). VS Code shows its accounts; **Sign in to another account** at the end signs in with a new one in the browser. When VS Code already has a GitHub account that Devspaces does not use, for example an account that only another extension uses, Devspaces asks once: "The GitHub account `<login>` is signed in to VS Code. Use it in Devspaces?" **Use in Devspaces** adds it; after **Not Now**, **Add GitHub Account…** still offers it.
- **The list.** The view lists the repositories of all accounts, each repository once. The tooltip of a row names the account that **Start** uses, with its permission on the repository, for example `Account: octocat (admin)`. With more than one account, the row of a devspace starts with the login of its account, for example `@octocat main   Stopped`. A hint of an organization that refuses the access names the account, for example "The organization `acme` refuses the access of `octocat`."
- **Which account starts a repository.** A devspace belongs to the account that created it, and always opens with that account. A new devspace uses the account with the highest permission on the repository (admin, maintain, write, triage, read). With equal permission, the account whose login owns the repository wins, then a member of the organization of the repository, then the login that comes first in alphabetical order.
- **Start with Account….** When two or more of your accounts can access a repository, its context menu has **Start with Account…**. It lists the accounts in the order above and creates a new devspace of the account that you select, with its own clone, container and images, or opens the devspace of that account when it has one. The devspace of the other account stays as it is, with its own row; **Delete** removes it when you no longer need it. The next **Start** opens the devspace that was used last.
- **One devspace, one account.** Git and the GitHub CLI in a devspace work as the account of the devspace. A push to a repository that only another of your accounts may change fails there; start the repository with that account instead.
- **Stop using an account.** In the Accounts menu of VS Code (the person icon in the activity bar), select the account, then **Manage Trusted Extensions**, and remove Devspaces there. **Sign Out** there removes the account for every extension. The list and the devspaces of the account disappear from the view, and a window of one of its devspaces closes its connection. The devspaces stay on the Docker engine and come back when the account is used again.
- **A devspace of an account that is not signed in.** Devspaces does not show it. When you start its repository, Devspaces asks: **Sign In as `<login>`** opens it after the sign-in of that account, and **New Devspace as `<login>`** creates a separate devspace of one of your accounts.

## Open from a link

A link opens a repository in Devspaces, for example from a website or a course page:

```text
vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name
```

For VS Code Insiders, the link starts with `vscode-insiders://`. On a web page:

```html
<a href="vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name">Open in Devspaces</a>
```

When you select the link:

1. Your browser usually asks whether it may open VS Code.
2. When Devspaces is not installed, VS Code offers to install it from the Visual Studio Marketplace, with the Dev Containers extension, and then opens the link. When Devspaces is installed, VS Code asks whether Devspaces may open the link. With **Do not ask me again for this extension**, VS Code opens later links to Devspaces without this question; **Extensions: Manage Authorized Extension URIs...** takes that choice back.
3. When you are not signed in, Devspaces asks for the GitHub sign-in.
4. On Windows without a Docker host of Devspaces, Devspaces sets up its own Docker in WSL, also when Docker Desktop is installed: it checks WSL (without WSL, it installs WSL 2 first, see [Installing Docker](#installing-docker); after the restart of Windows, the first VS Code window goes on with the setup and with the link by itself), sets up the WSL distribution of Devspaces with Docker Engine without a question (the log names the downloads and the folder), downloads the Docker CLI of Devspaces when your computer has none, and then uses the distribution as its Docker host (see [The WSL distribution of Devspaces](#the-wsl-distribution-of-devspaces-windows)). When that distribution exists already, Devspaces uses it as it is. Then the link goes on. On macOS and Linux without a Docker host of Devspaces, Devspaces sets up its Lima VM in the same way, without a question, and uses it (see [The VM of Devspaces](#the-vm-of-devspaces-macos-and-linux)).
5. Devspaces opens the devspace of the repository that you used last on the current Docker engine. Without one, Devspaces asks before it creates a devspace, and before any Docker work: the devspace clones the repository and runs code from it (Dockerfile, Features, and commands) on your Docker engine. For a repository that belongs neither to one of your accounts nor to one of their organizations, this question is the confirmation of the first start, as in the list. After **Open**, Devspaces starts the repository as a double-click on its row does, from its first source, with the account that **Start** uses (see [Several GitHub accounts](#several-github-accounts)). The repository does not need to be in your list: Devspaces then asks GitHub with each of your accounts, and only the accounts that GitHub shows it to count. For a repository of one of your accounts or of one of their organizations, the question also has the button **Always Open**: it opens the repository in the same way and turns off the setting `devspaces.confirmOpenFromLink`, so later links create such devspaces without this question. Turn the setting on again to get the question back. The confirmation for a repository of another owner has no such button, and it always comes.

The devspace opens in the window that VS Code gives the link, usually the window that was active last, when that window is empty; otherwise it opens in a new window, and that window keeps what it has. A link opens nothing, and a message says why, when it does not name a repository as `owner/name`, when GitHub does not show the repository to any of your accounts, or when the repository has no Dev Container configuration and `devspaces.defaultImage` is empty. When GitHub cannot be asked, for example without a connection to the internet, the link opens your devspace of the repository on the current Docker engine, if you have one there.

### Course links

A course link opens your own repository of a course, for example the repository that GitHub Classroom creates for you when you accept an assignment. GitHub Classroom names it after the assignment, with your GitHub login at the end: for the login `octocat`, the assignment `my-school/module-ts-2` gives the repository `my-school/module-ts-2-octocat`. One course link works for every student of the course:

```text
vscode://nimblescape.nimblescape-devspaces-2/course?repository=owner/name-<username>
```

On a web page:

```html
<a href="vscode://nimblescape.nimblescape-devspaces-2/course?repository=my-school/module-ts-2-<username>">Open in Devspaces</a>
```

A course link needs the GitHub sign-in, because only the sign-in tells Devspaces your login. When you are not signed in, Devspaces asks for the sign-in first; without it, the link opens nothing. Devspaces then puts the login of each of your accounts in place of `<username>` and opens the repository that exists, as a link `/open?repository=owner/name` does (see [Open from a link](#open-from-a-link)). It opens it with the account of the login in its name, also when another of your accounts has more rights on it, for example the account of a teacher who owns the organization of the course: the repository is the personal one of that login. When the repositories of two of your accounts exist, Devspaces asks which one to open. This also works when Devspaces is not installed yet: VS Code first offers to install it, as for a link `/open`.

- `<username>` can stand anywhere in the name, also more than once. A course link without `<username>` gets `-<username>` at the end of the name, so `/course?repository=my-school/module-ts-2` opens the same repository.
- The owner is the organization of the course and cannot contain `<username>`.
- When GitHub does not show the repository to your account, for example before you accepted the assignment, or when you signed in with another account than the one of the course, the link opens nothing, and a message names each repository and login that Devspaces tried. **Add GitHub Account…** adds the account of the course.

## The sidebar

The sidebar of Devspaces has two views: **Devspaces** with the repositories above, and **Docker Hosts** below it (see [The view Docker Hosts](#the-view-docker-hosts)). In the view of the repositories, the first row names the Docker engine that the view shows: **Local Docker host: VM of Devspaces** for the VM of Devspaces on your computer (`wsl:devspaces` on Windows, `lima:devspaces` on macOS and Linux; its tooltip names it), or **Remote Docker host: `<host>`** for another computer (see [Remote Docker host](#remote-docker-host)). Select it to choose another engine. Below it, the repositories are grouped by owner. When Devspaces uses its VM and the VM does not exist, for example after you removed it with `limactl` or `wsl --unregister`, the view shows the setup of the VM instead of the repositories, as before the first setup (on Windows from the next start of VS Code).

The title bar has **Select Organizations…** (limits the list and the scan to the organizations and accounts that you select; with several GitHub accounts, each organization names the accounts that are members), **Show Only Devspaces** (lists only the repositories that have a devspace, in any state; **Show All Repositories** lists all again), **Search**, **Refresh**, **Expand All** (opens every owner, group and repository with several sources), and VS Code's **Collapse All**. Its **…** menu has **Add GitHub Account…**, **Edit Repository Groups…**, **Update All Images Now**, and **Remove Devspaces from This Docker Engine…**.

### What a row shows

A row shows the repository name, the branch that is checked out in the devspace, and the state of its devspace. Work that is not on GitHub yet shows as numbers, in every state: uncommitted files, unpushed commits (on any local branch, also one without an upstream) and stashes, for example `Running · 1 uncommitted · 3 unpushed`. Such a row also has the badge **↑** at its right edge, and so do the owner, the group and the repository with several sources above it, so that a closed level does not hide it; the tooltip names each number. While the devspace runs, Devspaces counts again when the view is shown, when the window gets the focus (at most every 15 seconds), and after an action, never in the background. While it is stopped, the row shows the numbers of its last stop, and the tooltip says when they were counted. A commit that you pushed from another clone counts as unpushed until the devspace fetches again. VS Code shows the badge while the setting `explorer.decorations.badges` is on (the default). With more than one GitHub account, the login of the account of the devspace comes first, for example `@octocat main   Stopped`. The tooltip shows more, for example the source of the devspace, its GitHub account, and the time of the last use.

A repository with one possible source is one row: its one Dev Container configuration, or the [default image](#default-image) when it has no configuration (the row then shows `(default image)` next to the branch). A repository with several possible sources is a node with one child row per source: a configuration in `.devcontainer/<name>/devcontainer.json` next to the one at the root, or a configuration and the default image. Each child row is its own devspace, so two devspaces of one repository can run at the same time, and the buttons, the state and the context menu are on the child rows. A double-click or `Enter` on the repository name starts its first child row (see [Default image](#default-image)). The label of a child row is the word of its source:

- `default` for the default image;
- `config` for the configuration at the root of the repository (`.devcontainer/devcontainer.json` or `.devcontainer.json`, which count as one configuration);
- the folder name for another configuration, for example `python` for `.devcontainer/python/devcontainer.json`.

A devspace keeps its source. When the branch that is checked out in the devspace does not have its configuration, the start uses the first configuration of that branch and says so once; the devspace stays on its row, and its configuration applies again on a branch that has it.

The same word is in the Docker names of the devspace, for example `devspaces-acme-api-default-brave-curie` and `devspaces-acme-api-config-calm-noether`, and in the texts that name it, for example `acme/api · default`.

| State | Meaning |
|---|---|
| `Connected` | This window is connected to the devspace. |
| `Connected · other window` | Another VS Code window is connected to it. **Start** brings that window to the front. |
| `Running` | The container runs, but no window is connected, for example during the waiting time after a close, or while an agent works in it. |
| `Stopped` | The container is stopped. **Start** starts it. |
| `Updating` | Devspaces creates, updates, rebuilds, or deletes the devspace. |
| `No container` | The container was removed outside of Devspaces. **Start** creates it again from the image of the devspace. |
| `Files missing` | The volume with the repository is missing. **Start** offers **Clone again** or **Delete devspace**. |
| `State unknown (…)` | Devspaces could not read the states on that Docker engine, for example while it prepares the engine (`Docker not ready`), when a remote host does not answer (`<host> cannot be reached`), or after you removed Devspaces from the engine (`Devspaces removed from Docker`). The local Docker is named `Docker`, a remote engine by its host. The actions stay available. |

A repository without a devspace shows no state; **Start** creates its devspace on the default branch.

A row whose devspace does not run (`Stopped`, `No container`, `Files missing`) and a repository without a devspace show their name, their description and their icon in gray, so that the devspaces that run stand out. An owner, a group and a repository with several sources are gray too while no row below them runs. A devspace counts as running while it is `Connected`, `Connected · other window`, `Running` or `Updating`, while another of its containers runs (`· containers running`), and while its state is unknown. The warning icon of `Files missing` stays orange, because it needs your action. To change the gray, set `devspaces.inactiveForeground` in `workbench.colorCustomizations`. The color of the text comes from the file decorations of VS Code: with `"explorer.decorations": { "colors": false }` the text keeps the colors of your theme, and only the icons are colored.

More markers in a row:

- `· kept`: the devspace keeps running when no window uses it (see [Stop on close](#stop-on-close)).
- `· containers running`: the dev container is not running, but another container of the devspace is, for example a database of Docker Compose. **Stop** stops it.
- `not on GitHub`: GitHub no longer lists the repository, for example after you lost access. The devspace stays until you delete it.
- `host access unrestricted`: the host access checks are off for this repository (see [Security](#security)).

### Actions of a row

| Action | Effect |
|---|---|
| **Start** (or a double-click, or `Enter`) | Starts the devspace and connects the current window. Creates the devspace on the first start, from the source of the row. If another window is connected to it, that window comes to the front: a devspace is never open in two windows. |
| **Start in New Window** | The same, but a new window connects, and the current window keeps its devspace. With the setting `devspaces.openInNewWindow` on, the menu offers **Start in Current Window** instead. |
| **Start with Account…** | Only when two or more of your GitHub accounts can access the repository, and the row offers **Start**: starts the devspace of the account that you select, and creates it when that account has none (see [Several GitHub accounts](#several-github-accounts)). |
| **Stop** | Stops the container at once. Your files stay. If a window is connected, the connection closes first. The Monitor on the Docker engine is told first, so the devspace stops even when you quit VS Code right after the click. A notification shows the progress until `owner/name stopped.` |
| **Delete** | Removes the containers, the images, and the volume with the repository, after you confirm it. The confirmation shows uncommitted changes, unpushed commits, and stashes as far as Devspaces recorded them, and offers **Open devspace**. Additional volumes of the configuration, for example of a database, are removed only when you tick them. |
| **Keep Running When Closed** | The devspace keeps running when no window uses it, for example for a server or an agent. Only **Stop** or **Delete** stops it. **Stop When Closed** switches back. The choice is stored with the devspace. |
| **Close and Keep Running** | Only in a window that is connected to the devspace: closes the window, and the container keeps running this time. The next window that connects to it ends this. |
| **Rebuild** | Builds the image again and creates the container again. The volume with the repository stays. |
| **Show on GitHub** | Opens the repository in the browser. |
| **Turn Off Host Access Checks…** / **Turn On Host Access Checks** | Switches the host access checks of this repository (see [Security](#security)). |

A row has the buttons **Start**, **Stop** (when the devspace runs) and **⋯**. The other actions, also **Delete**, are in the context menu of the row and in its **⋯** button. A repository with child rows has no buttons and no context menu of its own: every action is on its child rows, and a double-click or `Enter` on the repository starts its first child row.

### Default image

By default, a devspace is built from the Dev Container configuration of its repository (`devcontainer.json`). With the setting `devspaces.defaultImage` you name one image, for example `ghcr.io/majikmate/devcontainer-base:latest`, that every repository can start from next to its configuration. This is useful when the repositories of a course or a team have no configuration, or when one shared image should be used for all of them.

With a default image, each repository with a configuration shows a `default` row next to the row of each of its configurations (`config`, or the folder name of the configuration). Each row is its own devspace with its own clone: **Start** on `default` creates the devspace of the default image, **Start** on `config` the devspace of the configuration, and both can run at the same time, also each in its own window. The setting `devspaces.startWithDefaultImage` (on by default) puts the `default` row first; off, it is the last row. A double-click or `Enter` on the repository starts its first row and opens its rows to show it: the default image while the setting is on, else the first configuration. A single click on the name of the repository only selects it; the arrow next to it and the arrow keys open and close its rows. A repository that has no Dev Container configuration on its default branch is listed too, as one row (the tooltip says so), and starts from the default image. Without a default image, these repositories are not listed, and no `default` row exists. **Search** and the switcher list the repositories the same way; when a repository has several sources, they ask which one to start. The devspaces of one repository share the named volumes that its configurations mount (for example a volume named after the folder of the repository): two of them that run at the same time write the same volume.

A devspace started from the default image is created from that image alone, as if the configuration of the repository were `{ "image": "<default image>" }`: the `devcontainer.json` of the repository, its Dockerfile, Features, lifecycle commands, mounts, ports and extensions are not read. The metadata of the image (its user, its settings and extensions) applies, as for any image. The repository is cloned into the workspace volume as usual.

A devspace keeps the source it was created from. When you change the default image in the settings, the next start of a devspace built from the old image asks **Rebuild now** or **Later**, as after a change of `devcontainer.json`; **Later** opens the devspace with its current image, and the next start asks again. When you clear the setting, the `default` devspaces that exist keep their row and keep starting from the image they were built from; a repository that has no `default` devspace loses its `default` row until the setting is set again.

### Status bar and switcher

The status bar shows the devspace of the window (`owner/name · branch`), **Open devspace…** in a window without one, `Updating owner/name…` while an operation runs, or **Reconnect owner/name** when the connection was lost. Select it to open the switcher, the progress details, or to reconnect. The devspace of a child row is named with the word of its source, for example `owner/name · default`, in the status bar, the switcher and the messages.

**Switch Devspace…** lists your recent devspaces with their state and, under **Open repository…**, every repository of the list. The selected devspace opens in the current window. **Switch Devspace in New Window…** opens it in a new window. With `devspaces.openInNewWindow` on, the two commands swap their roles.

On macOS, the key of **Switch Devspace…** is `Cmd+Alt+E`. On Windows and Linux, the command has no key, because on many Windows keyboards `Ctrl+Alt+E` is `AltGr+E` and types a character such as `€`. To set a key, open **Keyboard Shortcuts** (`Ctrl+K Ctrl+S`, on macOS `Cmd+K Cmd+S`), search for `Devspaces: Switch Devspace`, select the row, press `Enter`, press your keys, and press `Enter` again. In `keybindings.json`, the ID of the command is `devspaces.switchDevspace`.

## The view Docker Hosts

The view **Docker Hosts** shows the Docker hosts of Devspaces: the VM of Devspaces first (`lima:devspaces` on macOS and Linux, `wsl:devspaces` on Windows), also before its setup, then each remote host of the list of Devspaces. It shows no other Lima VM and no other WSL distribution of yours, and never the Docker of your computer.

- **The Docker host of Devspaces** has a check mark. You choose the Docker host of Devspaces only in the first row of the repository view: a click on a host row of the view **Docker Hosts** only opens or closes the row, so you can look at the objects of another host, and the repository view and **Start** keep their host. While the VM is not set up, **Set Up** in the menu of its row sets it up, and Devspaces uses it then. The **+** in the title of the view adds a remote host (**Use a Remote Docker Host…**), and **Refresh** reads the open hosts again.
- **What a host shows**: open a host row to see all its **Containers**, **Images**, **Volumes** and **Networks**, each group with the number of its objects and the sum of their sizes, and the row **Build cache**. In each group, the objects of Devspaces come first: those with a label `nimblescape.devspaces.*`, the containers and volumes whose name starts with `devspaces-`, the build image `devspaces-buildx` that Devspaces pins, the base images that the configurations of your devspaces on this computer name, the base image of the helper image (`node`), and the networks of Docker Compose of your devspaces. Each of them says what it is for: a devspace (its repository and its part: the dev container, a service, its image, its workspace volume, an additional volume, its network), the Monitor, a worker of a window, a batch helper, a build of the helper image, the helper image, the build image, a base image, or a shared volume (the Monitor, the cache of the workers, the VS Code Server and its extensions). The helper image is named by its tag `devspaces-worker:<hash>`. After a new build of the helper image, the earlier build loses its tag and is named `devspaces-worker (earlier build, <ID>)`: Docker keeps it while a container that was created from it exists, for example the Monitor. A devspace that this computer does not know, for example of another computer or of another VS Code profile, says so. Every other object says **not of Devspaces**, for example a service that you run on the host; a container of Docker Compose also names its service and project (`service web of shop`). A network row shows its driver and the number of its containers; `bridge`, `host` and `none` (and `ingress` and `docker_gwbridge` on a node of Docker Swarm) are the networks of Docker itself. The size of an image row is its whole size; the size of the group **Images** counts only the bytes that the images do not share with other images. The row **Build cache** shows the number of the records of the build cache of Docker, their size, and how much space their removal frees (the records that no build uses and that share their data with no image), as `docker system df` counts them.
- **Colors**: the name, the description and the icon of an object that is not of Devspaces are violet, for example a database that you run on the host. An object that is not active is dimmed: a dimmed violet when it is not of Devspaces, gray when it is of Devspaces. Active is a container that runs (also paused or restarting), and an image, a volume or a network that a running container uses; the tooltip of a row says which it is. So a bright violet row is a service of the host that uses its CPU and memory now, and **Stop** frees them. The hosts, the groups and the row **Build cache** keep the colors of your theme. To change the colors, set `devspaces.hosts.notDevspacesForeground`, `devspaces.hosts.notDevspacesInactiveForeground` and `devspaces.inactiveForeground` in `workbench.colorCustomizations`. The color of the text comes from the file decorations of VS Code: with `"explorer.decorations": { "colors": false }` the text keeps the colors of your theme, and only the icons are colored.
- **When it reads**: Devspaces reads a host only when you open its row, and again when you click **Refresh** of the view or of the host row, never in the background. It reads with one `docker system df -v`, which can take some seconds on an engine with large volumes, one `docker network ls`, `docker image ls` of the images with the labels of Devspaces and of the tags of all images, and, while containers run, `docker container inspect` of the running containers (for the colors, at most 100 per call). It never starts the VM to read it: while the VM is stopped, its row says so and offers **Start the VM**. When you open a remote host, a password login may ask for your password, because you started it. The reads and the actions of the view on a host share one login of the host (one `ssh`, or one `wsl.exe` on Windows), also on the VM of Devspaces, not one connection per Docker command; that login closes 2 minutes after its last use, so a password host asks again only after such a pause.
- **Stop, Start and Remove**: the rows of a devspace of this computer have the commands of the devspace: **Stop**, and **Delete…**, which checks the Git changes first (see [Actions of a row](#actions-of-a-row)). Every other running container has **Stop**, for example to free the CPU and the memory of a service of the host for your devspaces; the Monitor and a worker start again when a window needs them. A stopped container that is not of Devspaces has **Start**. **Stop** is only in the context menu of a container row (right-click), not a button on the row. Every other row that does not run has **Remove…**: select one or more rows, and Devspaces asks once and names them. Devspaces never removes with force: Docker keeps an image or a volume that a container uses, and the message names what was left. Devspaces also keeps a network that a container uses, even a stopped one, because that container could not start again without it, and it never removes the networks of Docker itself. While the VM of Devspaces is stopped, Devspaces changes none of its objects, because a Docker call would start the VM; it shows the row that starts the VM instead. A removed volume of a devspace that this computer does not know deletes the changes of that devspace that were not pushed, and an object that is not of Devspaces may be needed by another program or hold its data; the question says so.
- **Remove Unused Build Cache…** on the row **Build cache** removes the records of the build cache that no build uses (`docker builder prune --all`), after one question that says how much space it frees. The next builds on that host take longer, because they build those steps again; Devspaces builds its images again when it needs them.
- **The report of an object**: a click on a container, an image, a volume or a network opens its report in the editor (see [Report of a resource](#report-of-a-resource)); **Show Report** in its menu does the same.
- **The menu of a host row** has **Show Utilization** (also the button with the pulse icon on the row; see [Utilization of a host](#utilization-of-a-host)), **Update All Images Now** and **Remove Devspaces from This Docker Engine…** for that host, whatever host Devspaces uses, and, for a remote host, **Remove from the List**.
- **The menu of the VM row** manages the VM, the same on every platform: **Set Up** while there is none; **Start the VM** (Devspaces tests its Docker, which starts it; the VM powers itself off again two minutes after nothing runs there and nothing is connected to its Docker); **Stop the VM…** (`limactl stop`, or `wsl --terminate devspaces`), which asks first while devspaces run there and names them, because their windows lose the connection; **Remove the VM…** and **Remove and Set Up the VM Again…**, each after a question, because they delete every devspace in the VM with the changes that you did not push; and **Settings of the VM**, its memory and CPUs (macOS and Linux; on Windows, the file `.wslconfig` of your Windows user sets them). The tooltip of the VM row shows its state, its memory and CPUs (Lima), and the space that its disk takes on your computer. Devspaces reads them without a start of the VM.

### Utilization of a host

**Show Utilization** on a host row of the view **Docker Hosts** (the VM of Devspaces once it is set up, and each remote host) opens a page in the editor that shows how busy that host is now, so that you see what uses its CPU, memory and disk before you stop or remove something. Each host has one page; the command shows it again when it is open. The page only shows values and changes nothing on the host.

- **What it shows**: the CPU of the whole host (busy, each CPU, the time that waits for the disk or that the hypervisor takes, the load, and the pressure of the kernel: the time that tasks waited for CPU, memory or I/O), with a line of the last minutes; the memory (used, available, file cache, swap, and processes that the kernel ended because the memory ran out); the disk of the Docker data, and for the VM the free space on your computer for the disk of the VM; and the running containers, the busiest first, with their CPU (100 % is one CPU, as `docker stats` counts it), memory, network, disk reads and writes, and processes. The colors and purposes are those of the view **Docker Hosts**.
- **The sizes** of the objects of Docker come from `docker system df -v`, as in the view. The page reads them by itself after its first values (a few seconds after the start) when you open it, after **Resume**, and when you show it again after it was hidden for more than 15 seconds (each only when the sizes are older than a minute), then every 10 minutes while it reads. After a read that failed (for example when your account on the host cannot use Docker), it shows the error and tries again 10 minutes later. After a read that took longer than its time limit of 3 minutes, which ends the login of the values too, it reads by itself again only after a **Refresh Sizes** that works, after a new start of the host, or when you open it again. It reads every volume and can take a minute; meanwhile the header says "reading the sizes", and the values can wait, because both use the same login. This read uses only the login that the page already has: it never asks for a password and never logs in itself, and it does not run on a VM that does not run. **Refresh Sizes** (before the first read: **Read Sizes**) reads them at once. The page shows the disk use of Docker with what can be freed (images and volumes that no container uses, stopped containers, and the build cache that no build uses; an unused volume can still hold data), the stopped containers, the largest volumes and images, and the networks, and the purpose of each running container.
- **When it reads**: every 2 seconds on the VM and every 5 seconds on a remote host, less often when the host needs long to answer. It reads nothing while the page is hidden; when you show it again within 15 seconds, it goes on, else it starts again. It pauses after 2 minutes without the focus of the VS Code window, and after 30 minutes without a click or a key on the page; **Pause** pauses it too, and **Resume** goes on. While you select text on the page, it keeps its content, so that you can copy the text; it shows the newest values when the selection ends.
- **How it reads**: each reading is one command on the one login of Devspaces to the host, the same login as the view **Docker Hosts**: a fixed script that reads only system files (`/proc` and the cgroups of the containers) and the free space of the disks, and `docker ps` and `docker info` for the names of the containers and the data folder of Docker. It writes no file and starts no container there. A reading waits while the read of the sizes or an action of the view **Docker Hosts** runs on that login, so the time after "updated" in the header can stand still for that time. While a devspace of the window is open on a remote host, its connection cannot read these files, so the page logs in once more. A remote host with a password asks for it only when you open the page, or click **Resume**, **Retry** or **Refresh Sizes**; a new start after a hide asks nothing.
- **The VM**: the page never starts the VM and does not keep it running. When the VM is stopped, or goes to sleep because nothing runs there, the page says so and offers **Start the VM**. When the VM starts in another way, for example for a devspace, the page reads again within 30 seconds while you look at it. **Stop the VM…**, **Remove the VM…** and **Remove and Set Up the VM Again…** pause the page until you click **Resume**, and **Refresh Sizes** is off meanwhile. On Windows, all WSL distributions share one Linux kernel, so the totals of CPU and memory include your other distributions and Docker Desktop.
- **When something is missing on a remote host**: an account that may not use Docker there sees the values with short container IDs instead of names; a kernel without pressure values says so; a host that is not Linux or has no `sh` is not read. When a reading fails, the page stops reading, says why, and offers **Retry** where a new try can help and **Show Log**.

### Report of a resource

A click on an object row of the view **Docker Hosts** (a container, an image, a volume or a network) opens its report in the editor, a page that only shows values and changes nothing. A report opens like a file of the Explorer: a click opens a preview tab with its title in italics, the focus stays in the view, and the next click replaces the tab. A double click on the row, or on the tab, keeps the tab open with a regular title. A click on a resource whose report is open shows its tab. The tab has the name of the resource; for an image the part after the last `/`, for example `devcontainer-base:2.0.35`, and its tooltip shows the whole address.

- **What it shows**: every object shows the facts of Docker: its ID, when it was created, and its size; for a container its image, its state, its restart policy, its ports, its networks and its mounts; for an image its tags, its platform and the version that its publisher gives; for a volume its driver and the containers that use it, with the place and the mode of the mount; for a network its driver and its subnets; and the project of Docker Compose of the object. An object that is not of Devspaces shows only these; Devspaces never reads its content. Before them, an object of Devspaces shows what it holds, with a colored tag that says what the rule of Devspaces does with each item (for example "kept: newest" or "removed at the next cleanup"): the volume of the store of VS Code (`devspaces-vscode`) each version of the VS Code Server and each extension, and which of them the next cleanup of the Monitor keeps or removes and why; the container and the volume of the Monitor what the Monitor did in its last 7 runs (what it pulled, built, downloaded, prepared and removed, and what failed), its next background run, and its other records; the volume of the cache of the workers its content. The objects of a devspace show their devspace and its owner: the dev container its image and build, whether the next Start creates it again and why (an older container setup, a configuration that could not be read, the host access checks off when it was created), **Keep Running When Closed**, and the windows that use it now with what the Monitor does when the last one closes; a container of another service of Docker Compose whether its image was pulled or built for the devspace (**Delete…** removes only a built one); the workspace volume where its configuration comes from, when it was created and last opened, and the Git state that this computer recorded last (uncommitted files, unpushed commits and stashes, with a tag when something is not on GitHub): a window records it when it leaves the devspace, and **Delete…** reads it again in the running container before it asks; the report itself does not read Git. The other volumes of a devspace say what **Delete…** does with them (the data of a service is kept unless you tick it), and the network of its Docker Compose project that **Delete…** removes it. An object of a devspace of another computer or another VS Code profile shows what its labels say, and its workspace volume warns that its Git state is not known here. A devspace image shows its build and a table **Built from**: each image and Feature of its configuration with the digest of the build and what the registry answered the Monitor at its last run ("up to date", "newer in the registry"); a prepared image shows what changed against the build and when the next Start takes it over; a base image shows its version against the registry, the devspaces of this computer that are built on it, and its older versions that pulls replaced; the helper image shows whether this version of Devspaces uses it and the last check of the Monitor; the build image whether it is the pin of this version. A worker shows the window that it serves, and each helper container when Devspaces removes it. Each section says where its values come from. The tags at the top sum up what needs your attention, for example how many items the next cleanup removes, or the failures of the last run of the Monitor.
- **How it reads**: Devspaces reads the shared volumes with one short-lived container of a helper image that is already on the host. The container never downloads an image, has no network, mounts only the volumes that exist and only read-only, and is removed at its end. It needs a helper image on the host; when there is none, the report says so, and the next start of a devspace on that host builds it.
- **When it reads**: when the page opens and when you click **Refresh**, never in the background and never while the page is hidden. When VS Code opens a report tab again at its start, the page reads nothing until you click **Refresh**, so nothing asks for a password at the start; until the view has read the host, the page says that the view does not show the resource. The header says when the content was read ("Read today 07:52"). The page reads on the one login of Devspaces to the host, the same login as the view, or through the connection of a devspace of the window that is open on that host, so a remote host with a password may ask for it only when neither is open. When a read fails, the page says why and keeps the content of the read before.
- **The VM**: the page never starts the VM. While the VM is stopped, it says so and offers **Start the VM**, and it reads when the VM runs.
- **Show Log of the Monitor**: the reports of the container and of the volume of the Monitor have this button. It opens the last 2000 lines of the log of the Monitor as a read-only document. Each line starts with two times in the time zone of your computer, for example `2026-11-12 22:07:25.606`: when Docker received the line, and when the Monitor wrote it.

### Repository groups

Each entry of `devspaces.repositoryGroups` is a regular expression (JavaScript syntax) for the repository name without the owner, or an object with `pattern`, an optional `name`, and optional `flags` (`i`, `u`, `s`). In an owner where at least one repository matches, the view shows only the matching repositories and those with a devspace. Each capturing group becomes a level of the tree, and the last one is the label of the row; the first matching entry wins, and an entry with a `name` gets its own node. For example, `^(\d{4}-[^-]+-[^-]+)-([^-]+-[^-]+)-(.+)$` shows `2026-web-1a-module-html-css` as `2026-web-1a` › `module-html` › `css`. The view runs these regular expressions in a separate thread with a time limit of one second for each entry, so a slow expression cannot stop VS Code. When an entry takes longer than one second for the names of your repositories, for example because of a nested repetition such as `(a+)+`, the view lists the repositories without groups, and a warning names the entry, until you change the setting.

**Devspaces: Edit Repository Groups…** opens an editor for this setting, because the Settings editor of VS Code can only open `settings.json` for it. It shows a preview of the tree for the repositories that the view has loaded, tests a repository name, and marks an expression that takes longer than one second as too slow; such an expression cannot be saved. **Save** replaces only this one value in your user `settings.json`. If the value changed in `settings.json` while the editor was open, the editor asks first: **Load settings.json**, **Save Mine**, or **Cancel**.

## Updates

Devspaces keeps your devspaces current in two places: in the background on each Docker engine, and at each start.

### The background run

A small container on each Docker engine, the **Monitor** (`devspaces-monitor`), does the background work at the times of `devspaces.cacheUpdateSchedule` (by default daily at 06:07 in your time zone). A time that was missed, for example while the engine was off, runs once when the monitor runs again. A run that reaches no server at all, for example right after the computer wakes up and before its Wi-Fi or VPN is back, does not count as a run: the monitor tries it again after 2, 5, 10, 20 and 30 minutes, then every hour, until a run reaches the network, and a shorter schedule still runs at its own times meanwhile. A run that reached at least one server counts, also when single images or downloads failed, so one registry that is down never makes the monitor run again and again. Each run:

1. **Pulls the newer versions of the images that the devspaces on that engine use**, for example `node:20` or `mcr.microsoft.com/devcontainers/base:ubuntu`, and removes the older versions of those images that nothing uses any more. It pulls without a sign-in, so private images are not updated in the background; an image pinned by a digest never changes.
2. **Builds the helper image of Devspaces again** (`devspaces-worker`) when its base image `node` has a newer version, so that a start does not need to build it. It checks the base image without a sign-in, and builds the image on the engine, with the Docker CLI in its own container. The windows of Devspaces learn about this check, and a window checks the base image itself only when the monitor has not done it for a week. After such a build, each open window starts a new worker on that engine from the new build, in the background, and closes its earlier worker once no operation runs on it, so that the earlier build can be removed (on a remote host whose login asks for a password, the earlier worker stays until the window closes). The monitor itself moves to the new build too, by itself, once nothing runs in it: it starts its successor from the new build and then ends, and the successor removes the earlier monitor.
3. **Removes what no container uses**: the earlier builds of the helper image, the helper images that no running container used for 7 days, the older versions of the build image `devspaces-buildx` and of the base image of the helper image, the stopped helper containers that are older than 10 minutes, and on the VM of Devspaces the build cache that no build used for 7 days. It never removes a devspace container, a volume or a network, and never an image that a container uses.
4. **Downloads the newest VS Code server** into a store that all dev containers of the engine share, and links it into the running dev containers, so that a window that VS Code restores after its own update finds its server.
5. **Downloads the VS Code extensions** that the devspaces on that engine used in the last 14 days, also those of other users of the engine: of each extension, the newest release that works with the current VS Code server, or the exact version when the extension is listed as `publisher.name@x.y.z`. A start then installs them without a download.
6. **Cleans up** the store of the VS Code servers and extensions at most once a day.
7. **Prepares the next image of each devspace** whose base image or Features changed: it builds the new image in the background, so that the update at the next start takes seconds. It prepares one devspace at a time, the most recently used first, and stops a prepare after 30 minutes. It uses no token and no credentials, so devspaces with private images or Features, and repositories whose host access checks are off, are not prepared.

The monitor sends `User-Agent: nimblescape-devspaces/<version>` with each request to the update service of VS Code and to the Visual Studio Marketplace.

At the end of each run, the monitor keeps a short report of the run on its engine, for the last 7 runs: when the run started and ended, whether it reached the network, and what it did, for example "2 images pulled", "a new VS Code Server downloaded and linked into 1 container" or "3 extensions downloaded", with the names of the first ones, and what failed and why. The full details of each step stay in the log of the monitor.

How long the monitor runs depends on the Docker engine. Devspaces asks no question about the monitor.

- **On a remote host** (see [Remote Docker host](#remote-docker-host)), the monitor keeps running, also while no devspace runs there and VS Code is closed, and Docker starts it again when Docker or the host restarts. Its background work runs at the scheduled time even when no devspace runs. With the setting `devspaces.stopMonitorWhenIdle` on, it ends when idle, as on your computer.
- **On the WSL distribution of Devspaces and on the VM of Devspaces**, the monitor ends 5 minutes after the last devspace there stopped, so that the distribution or the VM can stop too. It does not end during a background run, and not while it waits for the retry of a run that reached no server, up to the retry after 30 minutes. On the WSL distribution and on the VM of Devspaces, a scheduled task of your user starts the distribution or the VM and the monitor at the times of the schedule, also while VS Code is closed (see [The WSL distribution of Devspaces](#the-wsl-distribution-of-devspaces-windows) and [The VM of Devspaces](#the-vm-of-devspaces-macos-and-linux)).

You can change the setting `devspaces.stopMonitorWhenIdle` at any time. A change applies on each engine at the next start of a devspace or **Update All Images Now** there. Until then, a monitor that keeps running goes on; **Remove Devspaces from This Docker Engine…** removes it at once. On an engine that several computers use, a monitor that keeps running and that another computer created stays; the computer that created it replaces it when it turns the setting on (see [Shared Docker engines](#shared-docker-engines)).

A monitor that keeps running ends itself after 30 days in which no devspace was used on its engine: no window was connected to a devspace there, no devspace was started, stopped or deleted there, and **Update All Images Now** did not run there. Once it found the 30 days, it starts no scheduled background run until a devspace is used there again. When it ended, Docker does not start it again, and the next start of a devspace there creates it again.

**Devspaces: Update All Images Now** (Command Palette, or the **…** menu of the view) runs the same work at once on the current Docker engine, for example after a new image was pushed. The run starts within a minute, and the command does not wait for it: the message says "The Monitor on `<engine>` updates the images now."

### The update at a start

At each start, Devspaces checks whether the images and Features of the devspace have newer versions. It uses the registry answers of the last background run when they are recent, and asks the registries itself otherwise. Without internet access, it skips the check and starts the devspace with its current image.

When a newer image is available and the devspace has a container, running or stopped, Devspaces says so before it changes anything. The update creates the container again from the new image: your files in the workspace stay, but programs and files that you added outside the workspace, for example in the home folder, are gone. With the default `devspaces.updateContainer` = `notify`, the dialog says, for example:

> A newer image is available for owner/name. To use it, the running container is stopped and created again from the new image. Your files in the workspace are kept; programs and files that you added outside the workspace are not. Choose Continue to update now, or Cancel to leave the devspace closed.

- **Continue** updates the container. **Cancel** ends the start: nothing changes, and the window does not connect.
- With `ask`, the buttons are **Update Now** and **Later**. **Later** opens the current container without the update; the next start asks again.

A first start, a missing image, and **Rebuild** never ask.

After **Continue** or **Update Now**, Devspaces uses the image that the background run prepared when it fits. While the background run still prepares it, the progress shows "Preparing the newer image (3 min)…" and the start waits for it; cancel the progress to stop waiting. Otherwise Devspaces pulls and builds the new image. In every case the new image passes all checks again before the container is created.

If the build of a newer image fails, or the new image needs access to your computer that the checks refuse, the devspace starts with its current container, and a message says so.

### One image for identical devspaces

Devspaces whose builds have the same inputs, for example the repositories of a course that all use the same configuration, use one image: the first start builds it, and the others only add their own name to it ([R-DS-010](requirements.md#r-ds-010)). With a Dockerfile, the build context (the folder that the build reads, with all its files) must also be identical; a Dockerfile that uses a secret, copies from another image, or adds a file from the network builds an image for its devspace alone. An image that was built for one devspace earlier and that is identical to such a shared image is merged by the Monitor when it is idle: when that devspace is stopped, the Monitor removes its stopped container and the duplicate image. The next start creates the container from the shared image without a build and without a question, as after an update: your files in the workspace stay, programs and files that you added outside the workspace are gone, and the lifecycle commands of the configuration (for example `postCreateCommand`) run again. A running devspace is never touched.

## Stop on close

When you close the last window of a devspace, switch to another devspace, or quit VS Code, the Monitor on its Docker engine stops the container 5 minutes later. A window that connects again within that time keeps it running. If the window cannot say goodbye (the computer sleeps or goes offline, or VS Code crashes), the monitor stops the container after `devspaces.stopAfterMinutes` (default 10 minutes) without a sign from any window.

A devspace keeps running when no window uses it in these cases, and its row shows `· kept`:

- **Keep Running When Closed** is on for it. Only **Stop** or **Delete** stops it.
- You closed its window with **Close and Keep Running**. The next window that connects to it ends this.
- `devspaces.stopOnClose` is off.
- `devspaces.respectShutdownActionNone` is on, and its configuration says `"shutdownAction": "none"`.

Work that runs in a container after its window closed, for example a long build in a terminal, ends when the container stops.

## Remote Docker host

Your devspaces can run on Docker on another computer, for example a build server or a stronger machine, reached over SSH. VS Code, Devspaces, and your GitHub sign-in stay on your computer; the containers, volumes, and images are on the other computer. Devspaces keeps its own list of such hosts, and uses one of them, or its own VM, in all its windows on this computer. It does not create or change a [Docker context](https://docs.docker.com/engine/manage-resources/contexts/) or any setting of Docker, so the `docker` command in your terminals keeps its target; only the setting `devspaces.createDockerContext` creates one, for the VM of Devspaces (see [Other Docker tools](#other-docker-tools)). The window of a devspace on the other computer reaches its engine through a Docker pipe of Devspaces on your computer, which the folder URI of the window names: the Dev Containers extension uses it for that window, and Devspaces carries its Docker connections over its own SSH connection. Devspaces sets no `DOCKER_HOST` of your environment and writes no setting of the Dev Containers extension. That window runs the Dev Containers extension with the Docker CLI of Devspaces (see [What to know](#what-to-know)). How the connection works inside, with diagrams, is in [remote-connection.md](remote-connection.md).

### Set up

1. On the other computer, install Docker Engine and let your SSH user use it: add the user to the group `docker`, or use rootless Docker. Your computer needs no Docker: when it has no Docker CLI, Devspaces downloads its own after you choose the host in step 3 (see [What to know](#what-to-know)).
2. You need the SSH address of the host (`user@host` or `user@host:port`, or a host of your SSH config) and a way to log in: a password, or a key. Nothing needs to be set up on your computer: when the login asks a question, Devspaces asks it in VS Code (see [SSH questions](#ssh-questions)).
3. Run **Devspaces: Use a Remote Docker Host…**, or select the first row of the view. Before the setup of the VM of Devspaces, the Docker setup in the view offers **Use a Remote Docker Host…** too. The list shows the hosts that Devspaces used before (**Hosts of Devspaces**), the other hosts of your SSH config (`~/.ssh/config`, on Windows `%USERPROFILE%\.ssh\config`, with its `Include` files), and the SSH hosts of your Docker contexts. **Enter an SSH address…** takes `user@host` or `user@host:port` (an IPv6 address in brackets).
4. Devspaces tests the connection with one SSH login, which may ask for the host key and your password (see [SSH questions](#ssh-questions)), adds the host to its list, and uses it: "Devspaces now uses Docker on `<host>`." After a login with your password, Devspaces offers to log in with a key next time (see [A key for the next logins](#a-key-for-the-next-logins)).
5. To go back to the VM of Devspaces, choose it in the same list: `wsl:devspaces` in the group **WSL** on Windows, `lima:devspaces` in the group **Lima** on macOS and Linux. While the VM does not exist, that group has its setup instead (**Set Up Docker for Devspaces in WSL…**, or **… in Its VM…**). The remote host stays in the list. Devspaces never uses the Docker of your computer, so the list has no local Docker.
6. **Remove a Host from the List…** at the end of the list of step 3 removes a host from the list. Its devspaces stay on that computer: add the host again to show them in the sidebar. An open window of such a devspace keeps working. When Devspaces uses that host, it has no Docker host afterwards, and the view shows the Docker setup.

### SSH questions

When the login to the host asks a question, Devspaces asks it in VS Code, only in a flow that you started: the test of **Use a Remote Docker Host…**, and a command with its progress notification, for example **Start** or **Open**.

- **The host key**, the first time that your computer connects to the host: a dialog shows its fingerprint. Choose **Accept and Connect** only when it is the fingerprint of that host (ask the person who runs the host). `ssh` then keeps the key in your `known_hosts`, as in a terminal. When the host shows another key later, `ssh` refuses the login.
- **Your password**, the passphrase of your key, or a code: an input box at the top of the window, which hides what you type. When the answer was not accepted, the box asks again. Cancel ends the login. **Cancel** of the progress notification closes the box too.
- Devspaces keeps no answer. The work of Devspaces in the background (the states in the view, the builds of its helper image) asks nothing: without a key, it waits for your next command and shows the state as unknown until then. Each window logs in once for each host. After a **Start**, the window of the devspace logs in once more before it connects, because VS Code starts it again; without a key, it asks for your password again, with the notification "Connecting to `<host>` for `<repository>`…".
- This needs the OpenSSH client of your computer (Windows 10 and 11, macOS, and Linux bring it). It asks through the program in `SSH_ASKPASS`, which Devspaces sets only for these logins.

### A key for the next logins

After a login with your password, Devspaces asks once: "Log in to `<host>` without a password next time?"

- **Use a Key**: Devspaces creates its own SSH key `~/.ssh/devspaces_ed25519` on your computer (on Windows in `%USERPROFILE%\.ssh`), when it is not there yet, and adds its public key to `~/.ssh/authorized_keys` of your account on the host, on the same login. Then it tests a login with the key. From then on, every login of Devspaces to that host uses this key and needs no password, also the work in the background. Devspaces never writes over another file in `~/.ssh` and never changes your SSH config.
- **Not for This Host**: Devspaces keeps asking for the password on that host and does not offer the key again, until you remove the host from the list and add it again.
- When you close the dialog, Devspaces asks again after the next login with your password.
- The key has no passphrase, so every program of your user on this computer can use it (see [Security](security.md#remote-and-shared-engines)). One key serves all hosts. To remove it from a host, delete the line that ends with `devspaces@<name of your computer>` from `~/.ssh/authorized_keys` there.
- When the key cannot be set up, a warning says why, for example when the SSH server of the host allows no keys. When the test login with the key failed, Devspaces removes the line of the key from `authorized_keys` again. Devspaces then asks again after the next login with your password, unless you choose **Not for This Host** in the warning.

### The WSL distribution of Devspaces (Windows)

On Windows, Devspaces uses Docker Engine in a WSL distribution of its own, named `devspaces`, as a host of its list: without Docker Desktop and without SSH. This is the VM of Devspaces on Windows, also when Docker Desktop is installed: both run side by side, and Devspaces never uses Docker Desktop.

- **Set it up**: click **Set Up Docker for Devspaces** in the Docker setup of the view, or run **Devspaces: Set Up Docker for Devspaces in WSL…**. A link to Devspaces while Devspaces has no Docker host sets it up too (see [Open from a link](#open-from-a-link)). The setup of a new distribution asks no question: the click or the link is the decision, and the log names what Devspaces downloads and the folder. It needs WSL 2.4.4 or later; without WSL, it installs WSL 2 first with `wsl --install --no-distribution` in a terminal of VS Code, and a message says so. Windows asks for administrator permission (without it, an administrator of the computer runs this command). Then restart Windows and open VS Code again: the first window after the restart goes on with the setup by itself, and opens the link that needed it. Until Windows restarts, the setup says that the restart is missing, before any download. Then Devspaces:
  1. downloads the `.wsl` file of the image of the VM of Devspaces (Debian 13 with Docker Engine, about 200 MB) from `ghcr.io`, and checks it against the SHA-256 in the code of Devspaces;
  2. creates the distribution `devspaces` of WSL 2 for your Windows user with `wsl --install --from-file`, with its virtual disk in `%LOCALAPPDATA%\nimblescape\devspaces\wsl\disk`; this needs no administrator permission;
  3. starts the distribution (the first start can take some minutes), in which systemd starts Docker, waits for Docker, and then uses it as the Docker host of Devspaces. When WSL runs out of time to start the distribution (`Wsl/Service/CreateInstance/ERROR_TIMEOUT`, for example in a slow virtual machine), Devspaces starts it again, up to 3 times. On a computer without a Docker CLI, it first downloads the Docker CLI of Devspaces.

  The `.wsl` file is the one for the architecture of Windows (x64 or Arm64), also when VS Code runs as an x64 program on Windows on Arm. The log shows its size. Before the download, Devspaces checks that WSL 2 can start its virtual machine. When it cannot (the error `HCS_E_SERVICE_NOT_AVAILABLE`), the message says to restart Windows after the installation of WSL, or to turn on virtualization: in the firmware settings (UEFI or BIOS) of the computer, or, when Windows runs in a virtual machine, nested virtualization in the settings of that virtual machine. When WSL finds this only at the creation of the distribution, the downloaded file stays in the folder of the distribution, and the next setup uses it again without a new download. One setup or removal runs at a time, also across your VS Code windows; when another window set up or removed the distribution after the check of this setup, the command changes nothing and says so. A progress notification shows each step; **Cancel** stops the step that runs (during the creation of the distribution, after that step). When a step fails, the message names it, and **Show details** opens the log. When the distribution exists already, the command uses it as it is, without a question.
- **What it changes**: your other WSL distributions and Docker Desktop stay as they are. In the distribution, `/etc/wsl.conf` of the image turns on systemd, makes root the user of `wsl -d devspaces`, does not mount the drives of Windows at the start, and turns off the start of Windows programs. So Docker and your devspaces do not see your Windows files by default. These settings are no wall: root in the distribution can mount the drives of Windows again (see [Security](security.md#remote-and-shared-engines)). The distribution grows with your devspaces, their images and their volumes.
- **Not your default distribution**: `wsl` without `-d` in a terminal does not open the distribution of Devspaces, and Docker Desktop does not integrate it by default. WSL makes a new distribution its default when it has none, and the first one that is left when you remove the default. So after its setup, and at the start of each window, Devspaces makes your first other installed distribution the default again (not one of Docker Desktop, Rancher Desktop or Podman), or, when WSL refuses all of them, leaves WSL without a default (your next new distribution becomes the default). `wsl -d devspaces` opens it. When you turned on the WSL integration of Docker Desktop for `devspaces` (Docker Desktop: **Settings** > **Resources** > **WSL integration**), or when the distribution stays the default (the log says why) while Docker Desktop integrates the default distribution, Devspaces warns once in a window, because Docker warns that Docker Desktop and a Docker Engine in the same distribution can conflict. Turn it off there.
- **A distribution of your own**: a distribution with the name `devspaces` that you made yourself is never changed or removed. Devspaces knows its own distribution by the folder of its virtual disk, which the registry of your Windows user names. When the registry cannot be read, Devspaces neither uses the distribution as its own nor removes it, and says so. The setup only offers to use a distribution of your own as it is (**Use It**), when Docker Engine runs there so that `docker info` works as root.
- **Use it**: when the distribution `devspaces` exists on your computer, **Devspaces: Use a Remote Docker Host…** and the choice of the Docker host in the first row of the view list it as `wsl:devspaces` in the group **WSL**. While it does not exist, that group has **Set Up Docker for Devspaces in WSL…** instead, so that you can go back from a remote host to the distribution. Devspaces tests it with `docker info` in the distribution and then uses it as any other host of its list: the same view, the same windows, and the same Docker CLI of Devspaces.
- **Builds there**: Devspaces builds its helper image there as on every Docker engine: in a short container of its build image `devspaces-buildx`, with buildx (BuildKit), which is much faster in a slow virtual machine than the classic builder of Docker. The first build pulls the build image once from Docker Hub. The log shows the output of the build.
- **No login**: Devspaces starts `wsl.exe` as your Windows user and runs its commands as root of the distribution. There is no password, no key, and no question. When the distribution does not run, the first `wsl.exe` starts it. Devspaces waits up to 2 minutes for that start, because the first start after a restart of Windows can take more than 30 seconds when Windows runs in a virtual machine, and it starts the distribution again, up to 3 times, when WSL itself runs out of time (`Wsl/Service/CreateInstance/ERROR_TIMEOUT`). Then it waits up to 3 minutes for Docker there, which systemd starts with the distribution (about 45 seconds in such a virtual machine).
- **When it runs**: WSL starts the distribution for a Start, an Open, or another command of Devspaces there, and for the window of a devspace there. While a container runs there, Devspaces keeps the distribution running, also after VS Code closed, as Docker Desktop does: for example a devspace that keeps running when closed, or the Monitor. For this, a window that uses the distribution starts a small program of WSL without a window, `wslg.exe`, which runs the idle script of the VM: it looks every minute whether a container runs there, a program uses Docker there, or the VM upgrades its packages. When nothing ran there at two checks in a row, about 2 minutes, WSL stops the distribution, with Docker, also while a window of VS Code is open; the next Start or Open starts it again. The idle script writes its checks to `/var/log/devspaces-idle.log` in the distribution (`wsl -d devspaces -u root -- cat /var/log/devspaces-idle.log`). After you close the window of a devspace, the Monitor stops that devspace 5 minutes later (unless it keeps running when closed), and the helper containers of Devspaces stop 10 minutes after their last use. The work of Devspaces in the background, for example the refresh of the view, does not start the distribution: the view then shows the devspaces there as stopped, with **Start**. When the list of your devspaces was lost, **Refresh** restores it. The Monitor there ends when idle (see [The background run](#the-background-run)), so the distribution does not run for it alone.
- **At the times of the background run**: a scheduled task of your Windows user starts the distribution and its Monitor at the times of `devspaces.cacheUpdateSchedule`, also while VS Code is closed, so that the images of your devspaces are up to date at your next start (see [The background run](#the-background-run)). It is the task `nimblescape Devspaces WSL <SID>` in the root folder of Task Scheduler, where `<SID>` is the security identifier of your Windows user. It runs only while you are logged in to Windows, and it needs no administrator permission. It starts 5 minutes after a time of the schedule, also on battery. It never wakes the computer: Task Scheduler runs a time that the computer missed while it slept or was off once, 10 minutes after the wake or the login. It runs `wslg.exe`, which shows no window (without `wslg.exe`, `wsl.exe` shows a console window while it runs), and holds the distribution as the window does: while the Monitor does its work, and about 2 minutes more. When a window uses the distribution at that time, the distribution and the Monitor run already. The task writes what it does to `/var/log/devspaces-task.log` in the distribution. Devspaces creates the task after the setup of the distribution, writes it again when the setting changes, and removes it with the distribution. A distribution `devspaces` that you made yourself gets no task.
- **Updates**: the VM upgrades its packages itself, also the VM of Lima: a service in the distribution runs `apt-get upgrade`, from Debian and from the package repository of Docker, so also Docker Engine, a minute after a start when the last upgrade that ended well is 20 hours old, and then every hour while the distribution runs; a failed upgrade is tried again after 6 hours. Docker and your running devspaces go on, and the distribution does not stop during an upgrade.
- **A damaged disk**: when Windows cannot read the virtual disk of the distribution (`Wsl/Service/CreateInstance/MountDisk/HCS/ERROR_FILE_CORRUPT`, for example after Windows or its virtual machine stopped during a write), WSL cannot start it. The message says so and offers **Remove and Set Up Again**: it deletes the distribution with everything in it, as below, without another question, and sets up a new one, which Devspaces then uses; when an operation of a devspace failed, it runs again afterwards. Changes that you did not push are lost with the old disk.
- **Stop it**: **Stop the VM…** in the menu of its row in the view **Docker Hosts** stops the distribution with `wsl --terminate devspaces`; it asks first while devspaces run there. Nothing is deleted, and the next Start of a devspace starts it again.
- **Remove it**: **Devspaces: Remove the WSL Distribution of Devspaces…**, or **Remove the VM…** in the menu of its row in the view **Docker Hosts**, asks first, then deletes the distribution with `wsl --unregister devspaces`, with everything in it: all devspaces there with the changes that you did not push, their images and their volumes. Push your changes first. It also removes the folder of the distribution and the host `wsl:devspaces` from the list; when Devspaces used it, Devspaces has no Docker host afterwards, and the view shows the Docker setup. The rows of the devspaces that were there are not shown while the host is gone; when you set the distribution up again, they show **Files missing**, and **Delete** removes them. It removes only a distribution that Devspaces set up.
- When the distribution is not installed, the message says so. A devspace in the distribution opens only on this computer: on another computer, its window does not open, and the message says that WSL is missing.
- **Remove by hand**: the Docker commands of [Remove by hand](#remove-by-hand) work with `wsl -d devspaces -u root -- docker` in place of `docker`.

### The VM of Devspaces (macOS and Linux)

On macOS and Linux, Devspaces uses Docker Engine in a VM of its own, made with [Lima](https://lima-vm.io): Apple Virtualization on macOS, and QEMU with KVM on Linux. Every VM of Devspaces runs the same Debian image with Docker Engine.

- **Set it up**: click **Set Up Docker for Devspaces** in the Docker setup of the view, or run **Devspaces: Set Up Docker for Devspaces in Its VM…**. A link to Devspaces while Devspaces has no Docker host sets it up too. The setup asks no question: the click or the link is the decision, and the log names what Devspaces downloads and the folder, `~/.nimblescape/devspaces`. Devspaces downloads Lima from `github.com` and the disk of the VM from `ghcr.io`, each checked against the SHA-256 in its code, creates the VM, starts it, waits for Docker there, and then uses it as the Docker host of Devspaces. On a computer without a Docker CLI, it first downloads the Docker CLI of Devspaces. A progress notification shows each step, with the percent of the download; **Cancel** stops the step that runs. A VM that exists is not created again. After the setup, the view lists your repositories without devspaces, because the new VM has none yet: **Start** creates the first one. Devspaces builds its helper image in the VM in the background right after the setup, and the log says when it is ready, so that the first Start does not wait for it.
- **Linux**: the VM needs QEMU and access to `/dev/kvm`. When QEMU is missing, the setup first installs it from the package source of your distribution (Debian, Ubuntu, Fedora, Arch Linux, and distributions based on them) in the terminal **Install QEMU**, without a question of Devspaces: `sudo` asks for your password there. Then the setup goes on by itself. When your user may not use `/dev/kvm`, the same terminal adds your user to the group `kvm`; log out of the computer and in again, and set up Docker for Devspaces again. On other distributions, the message says what to install. When `/dev/kvm` is missing, the processor has no virtualization, or it is turned off in the firmware settings: then this computer cannot run devspaces, and the message offers **Use a Remote Docker Host…**. Devspaces never runs the VM with an emulated processor, and never uses the Docker of the computer instead.
- **The VM**: 4 GiB of memory and 4 CPUs, each at most half of the computer, and a disk of at most 100 GiB, whose file grows with your devspaces. The settings `devspaces.vmMemoryGiB` and `devspaces.vmCpus` change the memory and the CPUs from the next start of the VM: when the VM is stopped, Devspaces gives it the new values before it starts it. A value above half of the computer counts as that half, and a warning says so. When the VM runs out of memory and its kernel ends a process, for example a build step or the TypeScript server of your devspace, a warning says so and names `devspaces.vmMemoryGiB`, once per start of the VM. No folder of your computer is in the VM.
- **Use it**: when the VM exists, **Devspaces: Use a Remote Docker Host…** and the choice of the Docker host in the first row of the view list it as `lima:devspaces` in the group **Lima**. While it does not exist, that group has **Set Up Docker for Devspaces in Its VM…** instead, so that you can go back from a remote host to the VM. Devspaces reaches it over the SSH of Lima as root, with the key that Lima made: there is no password and no question.
- **When it runs**: Devspaces starts the VM when it needs it, for example for a Start, an Open, or the window of a devspace there. The VM powers itself off when no container ran there for some minutes. **Start the VM** and **Stop the VM…** in the menu of its row in the view **Docker Hosts** start and stop it by hand; the stop asks first while devspaces run there.
- **Remove it**: **Remove the VM…** in the menu of its row in the view **Docker Hosts** (or **Devspaces: Remove the VM…**) asks first, then deletes the VM with `limactl delete`, with everything in it: all devspaces there with the changes that you did not push, their images and their volumes. Push your changes first. The host `lima:devspaces` leaves the list; when Devspaces used it, Devspaces has no Docker host afterwards, and the view shows the Docker setup. Lima and the downloaded files stay in `~/.nimblescape/devspaces` for the next setup, until the uninstall (see [Uninstall](#uninstall)). **Remove and Set Up the VM Again…** removes the VM after the same question and sets up a new one, which Devspaces then uses.
- **At the times of the background run**: a scheduled task of your user starts the VM and its Monitor at the times of `devspaces.cacheUpdateSchedule`, also while VS Code is closed, so that the images of your devspaces are up to date at your next start (see [The background run](#the-background-run)). On macOS it is the launch agent `~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist`, on Linux the systemd user timer `devspaces-vm.timer` with `devspaces-vm.service` in `~/.config/systemd/user`; neither needs administrator permission. The task starts the VM 5 minutes after a time of the schedule, so that the network is back after a wake or a login. It never wakes the computer: a time that the computer missed while it slept or was off runs once after the wake or the login, after the same 5 minutes. When the Monitor has done its work, it ends, and the VM powers itself off. When a window uses the VM at that time, the VM and the Monitor run already. On Linux, the systemd of your user runs the timer only while you are logged in, unless lingering is on for your user. The task writes what it does to `~/.nimblescape/devspaces/task/task.log`. Devspaces creates the task with the VM, writes it again when the setting changes, and removes it when the VM no longer exists.

### Other Docker tools

By default, Devspaces creates no Docker context, so the `docker` command in your terminals, the Dev Containers extension and the Container Tools extension do not see the containers, images and volumes of the VM of Devspaces. To see them, turn on the setting `devspaces.createDockerContext`:

- Devspaces creates the Docker context `devspaces`, with the description "The VM of nimblescape Devspaces". Use it with `docker --context devspaces ps`, or choose it in the other tool. It never becomes the current Docker context, so `docker` without `--context` keeps its target.
- macOS and Linux: the context points to the Docker socket of the VM, which Lima puts into `~/.nimblescape/devspaces/vm/devspaces/sock/docker.sock` while the VM runs. It reaches the VM only while the VM runs: nothing but Devspaces starts it. Start a devspace, or the window of one, first.
- Windows: the context exists while the WSL distribution of Devspaces exists. It points to a named pipe of Devspaces (`npipe:////./pipe/devspaces-context-<id>`), which a window of Devspaces serves: the context works only while a VS Code window with Devspaces is open, and then it starts the distribution when it does not run.
- Turning the setting off removes the context. Devspaces changes and removes only its own context: when a context `devspaces` that Devspaces did not create exists, for example one of version 0.2.0, a warning says so and Devspaces leaves it as it is. Devspaces does not remove the context while it is the current Docker context (`docker context use default` first).
- A Docker context gives full access to the engine. Manage your devspaces only with Devspaces: a deleted volume deletes the work that you did not push, and a container that another tool created has no labels and records of Devspaces. To see the containers, images, volumes and networks in the VM, and to stop, start or remove them, use the view **Docker Hosts** (see [The view Docker Hosts](#the-view-docker-hosts)): it needs no Docker context.

### What to know

- The view and the switcher show only the devspaces of the current Docker engine, and the commands of the Command Palette act only on them. Each devspace belongs to the engine where it was created, and a repository gets its own devspace on each engine. Two names of the same computer (an SSH alias and `user@address`) count as two hosts. A window of a devspace that opens again, for example from **Open Recent**, always runs on the engine of its devspace, without a question. So do **Close and Keep Running** and **Reconnect** in the status bar of that window, also while another engine is current.
- Devspaces does not follow your Docker context, and never reads the current one. **Devspaces: Use a Remote Docker Host…** lists the SSH hosts of your Docker contexts, so that you can add one to its list.
- When the host cannot be reached, the message names the reason: the computer does not answer, the login failed, the host key is unknown, or Docker does not run there. Devspaces never starts or installs Docker on a remote host.
- To stop using a host, run **Remove Devspaces from This Docker Engine…** and then **Remove from the List** in the menu of its row in the view **Docker Hosts**, or **Devspaces: Remove Devspaces from This Docker Engine…** while it is the current engine, then **Remove a Host from the List…**.
- Published ports are bound to `127.0.0.1` of the other computer. Reach them through the port forwarding of VS Code (the Ports view, `forwardPorts`). `host.docker.internal` exists only with Docker Desktop.
- Rootless Docker on the other computer works. Its limits: no published ports below 1024, Docker-in-Docker needs set-up there, and resource limits need cgroup v2.
- The window of a devspace on another computer connects only while Devspaces runs in that VS Code: its folder URI names the Docker pipe of Devspaces on your computer. Such a URI does not work on another computer, or after you copied it; open the devspace there from the Devspaces view. When the window cannot serve its pipe, it closes its connection and says so.
- **Only the Docker requests that are needed.** In the window of a devspace on another computer, the Dev Containers extension can read, start the container, and run programs in it, but it cannot create, build or remove containers or images there. Its **Rebuild Container** fails with a message of Devspaces: use **Rebuild** of Devspaces in the view. The Docker calls of Devspaces itself are limited in the same way to what it needs. See [The request filter](remote-connection.md#the-request-filter).
- **The Docker CLI of Devspaces.** The window of a devspace on another computer runs the Dev Containers extension with a Docker CLI that Devspaces downloads from `download.docker.com` and checks against the size and SHA-256 in its code, so every computer connects with the same tested version, also when the Docker CLI of your computer is older or newer. The first such window downloads it once for each version (between 20 and 90 MB, depending on the system) while it starts, and a notification shows the progress. When the download fails or you cancel it, the window uses the Docker CLI of your computer and says so. Once it is there, Devspaces runs its own Docker calls on the other computer with it too, in every window. On a computer without a Docker CLI, **Use a Remote Docker Host…** downloads it after you choose the host; when that download fails or you cancel it, Devspaces does not change its host. The Docker tools in your terminals keep their Docker CLI. The log of the window names the CLI that it uses. The Docker CLI of Devspaces works with Docker Engine 19.03 and later. When the Docker engine of the other computer is too old for it, or needs a newer Docker CLI, Start, Open and the view say so with both Docker API versions and what to do, before a window of a devspace there opens. When a window uses the Docker CLI of your computer for the other computer, and the engine there needs a newer Docker CLI, the message says so too: update the Docker CLI of your computer.
- **One SSH login per window.** Devspaces keeps one SSH connection per window and engine for its worker, for the Docker connections of the window of a devspace, and for its own Docker calls while that connection is open. Its checks before that connection opens (the first time in a window, and again after 10 minutes without use) run on the same SSH login, so the open of a window logs in to the host once. The work of Devspaces in the background on the helper image (a rebuild from a newer base image, the removal of old helper images) waits for that connection and runs through it, without a login of its own. You set up nothing for this: no connection sharing in your SSH config, and no change of the SSH server. A build of the helper image when it is missing on the engine, for example after an update of Devspaces, still logs in a few more times before the connection, once for each Docker connection of the build. When an SSH server drops a new connection before the login, the message says so: wait a minute, then try again.

## Shared Docker engines

Several people, each with their own computer, can use the same remote Docker engine. Each devspace belongs to the GitHub account that created it, and the Monitor on the engine decides by the newest sign of any computer: closing a window on one computer never stops a devspace that a window on another computer still uses.

The engine has one Monitor for all computers, and it keeps running unless the computer that created it turns `devspaces.stopMonitorWhenIdle` on (see [The background run](#the-background-run)). **Remove Devspaces from This Docker Engine…** says when other computers use Devspaces on the engine. It deletes only the devspaces of your GitHub accounts in Devspaces; the devspaces of other accounts and of other computers stay. It removes the Monitor and the helper containers of all computers, so an operation of another computer that runs at that time can fail. The next work of that computer on the engine creates them again.

One devspace can be used from several computers, for example with the same GitHub account at school and at home. When another computer updated the devspace to a newer image, the next start on your computer continues from that newer image: it does not ask about a changed configuration or build again for a change that the newer image has already.

**A shared engine is for a group that trusts each other.** Everyone who can use Docker on that engine (root and the members of the group `docker` there) can reach every container and every volume on it, including the GitHub token in the memory of another person's running devspace. Devspaces separates accounts against mistakes, not against the other users of the engine. For people who must not see each other's work, give each person an engine of their own, for example a virtual machine.

## Installing Docker

Until the VM of Devspaces is set up or a remote host is chosen, the view shows the steps to set it up instead of the repositories, each with its button:

1. On Windows: **Install WSL 2** (`wsl --install --no-distribution` in a terminal of VS Code, without a question of Devspaces: WSL 2 without a Linux distribution, because the WSL distribution of Devspaces brings its own). Windows asks for administrator permission; without it, ask an administrator of the computer to run this command. Once WSL 2 is ready, the view shows "✓ WSL 2 is installed.", and a message asks you to restart Windows. After the restart, the first VS Code window goes on with step 2 by itself.
2. On Windows: **Set Up Docker for Devspaces** creates the WSL distribution of Devspaces with Docker Engine, downloads the Docker CLI of Devspaces, and connects to the distribution, without Docker Desktop and without administrator permission (see [The WSL distribution of Devspaces](#the-wsl-distribution-of-devspaces-windows)). When WSL 2 is missing, it installs WSL 2 first (step 1). This is the setup of Docker on Windows: Devspaces does not install Docker Desktop, and does not use it when it is installed.
3. On macOS and Linux: **Set Up Docker for Devspaces** creates the VM of Devspaces with Docker Engine, downloads the Docker CLI of Devspaces, and connects to the VM, without Docker Desktop and without administrator permission (see [The VM of Devspaces](#the-vm-of-devspaces-macos-and-linux)). On Linux without QEMU, it first installs QEMU in a terminal, where `sudo` asks for your password.
4. The VM starts by itself when a devspace needs it.

Instead of an installation, the last step of the view, **Use a Remote Docker Host…**, uses Docker on another computer that you reach over SSH; your computer then needs no Docker (see [Remote Docker host](#remote-docker-host)).

The setup needs as few clicks as possible: **Install WSL 2**, and the installation of QEMU on Linux, run their commands in a terminal without a question of Devspaces (Windows or `sudo` asks for administrator permission itself), and the setup of the VM of Devspaces asks nothing; the log names its downloads and the folder, and its steps run without a terminal, with a progress notification and the log. The setup works only in a local window.

## Security

**A repository that you open is code that you run.** Its Dockerfile, its Features, its lifecycle commands, and the extensions in its container run with the rights of the container: they can use the network, attack the kernel that all containers share, use the channels that VS Code keeps open to your computer (for example the SSH agent and the clipboard), and use the GitHub token of the devspace. Open only repositories that you trust.

What Devspaces does to limit the harm:

- Each devspace runs in containers of its own, with the repository in a Docker volume. Devspaces mounts no file or folder of your computer into the container.
- **Host access checks**, on for every repository, refuse configurations that ask for access to your computer: bind mounts (also of the Docker socket), privileged mode, extra capabilities, devices and GPUs, the namespaces of the computer, ports on all network addresses, and the volumes of other programs. Published ports are bound to `127.0.0.1`. For a repository that you fully trust, **Turn Off Host Access Checks…** lifts these refusals after a warning; the row then shows `host access unrestricted`.
- Some things are refused whatever the switch says, for example the volumes and containers of other devspaces and the folder of the token.
- The GitHub token is never in an environment variable, on a command line, or in a log. It is kept only in the memory of the running dev container, at `/run/devspace`, and is gone when the container stops.
- Git and the GitHub CLI in the container use only the configuration of the devspace and the token of the account that owns it. Devspaces switches off the copy of your Git configuration, the forwarding of your Git and Docker credentials, and the sign-in of the GitHub CLI by the Dev Containers extension for its containers.

The checks are a guard rail against mistakes and copied templates, not a sandbox. The full security model, the complete lists, the known limits, and the steps to harden your computer are in [security.md](security.md).

**Privacy.** Devspaces uses the GitHub sign-in of VS Code and stores no token in its settings or files. Its stored lists hold metadata only, for example repository names, branch names, image names, and the GitHub account of each devspace. It collects no telemetry.

## Known limits

- The first start of a repository needs internet access, to download the repository and the images.
- The repository is in a Docker volume, not in a folder of your computer. Other programs on your computer cannot open its files directly, and configurations that mount files of the repository from your computer (`${localWorkspaceFolder}`) do not work.
- Only the volume with the repository, and additional named volumes of the configuration (`mounts`), survive an update or a rebuild. Files in other folders of the container, for example the home folder, are lost. When Devspaces itself needs to create a container again, the progress says so. When a container is damaged so that it cannot start (for example its `/etc/passwd` lacks the user), **Start** asks whether to create it again and names what is lost.
- Values of `${localEnv:…}` variables of your computer are not passed to the devspace.
- Each GitHub account has its own devspace of a repository, with its own clone. A configuration with a fixed volume name works for one account only; use `${devcontainerId}` in the name to give each devspace its own volume.
- In one devspace, Git works as one GitHub account, the account of the devspace. A push to a repository that only another of your accounts may change fails there.
- With several GitHub accounts, an organization repository that two accounts can see is read for each account at the first load of its list. Later updates read only the repositories that changed.
- Docker Compose configurations start the dev container together with the other services, for example a database. The same checks apply to every service. A service that mounts files of the repository (for example `./init.sql`) gets them from the volume of the devspace (Docker Engine 26 or newer). Remote `include` and `extends` of compose files do not work.
- With **Select Organizations…**, GitHub is asked only about the selected owners. Your devspaces of other owners stay in the list, but Devspaces does not check whether their repositories are still on GitHub.
- Git in the container older than version 2.32 reads the configuration of the devspace only through `~/.gitconfig`. When the image brings a `~/.gitconfig` with content, Git older than 2.31 gets no credential for github.com. Git older than 2.9 may use the credentials of your computer; Devspaces warns about it.

## Troubleshooting

- **The log.** **Devspaces: Show Log** opens the complete log of Devspaces, including the output of the clone, the build, and the lifecycle commands. Every progress notification of Devspaces has **Show details** for the same log. **Show details** also hides the notification: the operation goes on, the status bar shows its progress, and the notification stays in the notification center (the bell in the status bar) with its **Cancel** button.
- **The Monitor.** Its log shows each stop, each background run, and each prepare: `docker logs devspaces-monitor` on the engine, or from your computer `docker -H ssh://<host> logs devspaces-monitor`. Docker keeps at most 2 × 1 MB of it.
- **A devspace stops too early or keeps running.** Check its row for `· kept`, and the settings `stopOnClose`, `stopAfterMinutes`, and `respectShutdownActionNone`. If the window warns that its heartbeats failed, the Monitor may stop the devspace after `stopAfterMinutes`.
- **GitHub limits the requests.** When GitHub refuses the requests of your account for a while (its rate limit), the view keeps the repositories that it shows, and a message says at what time Devspaces loads the list again. It tries once at that time; after that, use **Refresh**.
- **`State unknown`.** Devspaces could not read the engine. On a remote host that you log in to without a key, the work in the background asks no password, so the state stays unknown until your next command logs in (see [SSH questions](#ssh-questions)); **Use a Key** after that login ends this (see [A key for the next logins](#a-key-for-the-next-logins)). Otherwise check that `ssh <host>` works and that Docker runs there. After the images of an engine were removed, Devspaces prepares the engine again in the background; the status bar shows "Devspaces: preparing `<host>`…".
- **Report a problem.** Open an issue on GitHub. [SUPPORT.md](../SUPPORT.md) says what to include.

## Uninstall

Devspaces keeps a few things on each Docker engine that you used: the Monitor (`devspaces-monitor`), its helper containers and images, and three volumes that all devspaces of the engine share. Remove them before you uninstall the extension. On each Docker engine:

1. Push the changes that you want to keep from each devspace there.
2. Close the windows of your devspaces there. The command does not run while a window on this computer is connected to a devspace on the engine or is opening one, or while an operation runs, also **Update All Images Now** in the same window. When that changes while it asks, it removes nothing after your answer.
3. Make the engine current with **Devspaces: Use a Remote Docker Host…**. The first row of the view names it. For an engine of the Docker of your computer that an older version used, use the Docker commands of [Remove by hand](#remove-by-hand) instead.
4. Run **Devspaces: Remove Devspaces from This Docker Engine…** (Command Palette, or the **…** menu of the view). It removes: the container `devspaces-monitor`, the helper containers, the helper images `devspaces-worker:<hash>` with their second tag `devspaces-monitor:<hash>`, the build image `devspaces-buildx:<version>`, and the volumes `devspaces-monitor`, `devspaces-worker-cache` and `devspaces-vscode`. In the question "Remove Devspaces from `<engine>`?", choose **Remove**.
5. When you have devspaces there, a second question asks "Also delete your devspace on `<engine>`?" (with several devspaces, for example "Also delete your 2 devspaces on `<engine>`?") and shows their recorded changes. **Delete Devspaces Too** deletes each one as **Delete** does, with its containers, its images and its volumes, also the clone of the repository, before the rest is removed. A volume that another devspace also uses stays, and so does a devspace that a window connects to in the meantime. **Keep Devspaces** keeps them, and the volume `devspaces-vscode` then stays while they use it. If you close the question, nothing is removed.

Then remove the VM of Devspaces, when you set it up. Push your changes first. On macOS and Linux, run **Devspaces: Remove the VM…** (or **Remove the VM…** in the menu of its row in the view **Docker Hosts**): it deletes the VM with all devspaces in it, and its scheduled task. On Windows, run **Devspaces: Remove the WSL Distribution of Devspaces…**: it deletes the distribution with its Docker engine, its folder and its scheduled task (see [The WSL distribution of Devspaces](#the-wsl-distribution-of-devspaces-windows)).

Then uninstall Devspaces in the Extensions view of VS Code, or run `code --uninstall-extension nimblescape.nimblescape-devspaces-2`.

What to know:

- The command never starts Docker; only the WSL distribution of Devspaces starts, because WSL starts it for every use. When the engine does not answer, it removes nothing and says so.
- While it removes Devspaces, a Start, a Rebuild, a Stop, a Delete or **Update All Images Now** on that engine in another window is refused with the message "Devspaces is being removed from `<engine>` in another window. Try again after that." An **Update All Images Now** that waits for Docker to start when the removal begins sends no request either. **Refresh** still updates the view, but it does not restore lost records of Devspaces from the volumes there, in any window, and says so. When that window was closed or crashed during the removal, the next Start runs.
- It deletes only the devspaces of your GitHub accounts in Devspaces, and with several accounts the second question names them. The devspaces of other accounts and of other computers stay, and the first question says so. Without a sign-in, your devspaces stay too.
- After the removal, this computer does no Docker work on the engine by itself, also not when VS Code starts, until you start or rebuild a devspace there or run **Update All Images Now**. That sets up the engine again. Until then, the devspaces that you kept there show `State unknown (Devspaces removed from Docker)`, or on a remote host `State unknown (Devspaces removed from <host>)`, and the reopen at startup does not open them. A window of one of them, for example from **Open Recent** or attached by hand with Dev Containers, stays connected while its GitHub account is signed in to Devspaces, and works without Devspaces, so you can still save your changes: nothing is updated in the background, and the container does not stop when you close the window. A message says so. A Start of that devspace in another window shows this window, and a Start in this window sets Devspaces up again and connects this window. A container that runs is never replaced under the window: one of an older version stays as it is, and the window closes its connection, so that a Start from the empty window makes a new one.
- **Stop** and **Delete** of a devspace that you kept there still work, and so does **Refresh** when the records of Devspaces on your computer were lost (it restores them from the volumes there): they build the helper image and create the volumes `devspaces-monitor` and `devspaces-vscode` there again, but they do not start the Monitor, nothing runs there by itself afterwards, and running the command again removes them again.
- A build of the helper image that another VS Code window began in the background before the removal, for example right after an update of Devspaces, goes on and can make the image `devspaces-worker:<hash>` there again. When `docker image ls` still lists it after the removal, run the command again.
- An **Update All Images Now** in another VS Code window that is already sending its request when the removal begins goes on, and can create the container `devspaces-monitor`, the helper image and the volumes there again. When `docker ps -a` still lists `devspaces-monitor` after the removal, run the command again.
- When something cannot be removed, for example a volume that a container still uses, the message says so. The log of Devspaces (**Devspaces: Show Log**) names each item and the command that removes it.
- The command removes nothing on your computer (see [What stays after the uninstall](#what-stays-after-the-uninstall)).

### At the next start of VS Code

VS Code runs the uninstall step of Devspaces once, at its next start after Devspaces was uninstalled from every profile, without a window and for at most 5 seconds. Then VS Code deletes the files of Devspaces in its storage (see **Files** in [Docker contexts and your computer](#docker-contexts-and-your-computer)). The uninstall step removes:

- the scheduled task that starts the VM of Devspaces, or the WSL distribution of Devspaces, at the times of `devspaces.cacheUpdateSchedule`;
- the Docker context `devspaces` of the setting `devspaces.createDockerContext`, when Devspaces created it and it is not the current Docker context;
- the folder `~/.nimblescape/devspaces` with Lima on macOS and Linux, or `%LOCALAPPDATA%\nimblescape\devspaces` on Windows, only when the VM of Devspaces is not in it.

It never deletes the VM of Devspaces, the WSL distribution or a devspace, because they can hold work that you did not push, and it cannot ask you. It never connects to a Docker engine or to a remote host. Until that start of VS Code, the scheduled task can still start the VM. VS Code writes the lines of the step into the log of its shared process, `sharedprocess.log` (**Developer: Open Logs Folder**).

### What stays after the uninstall

- **The VM of Devspaces**, when you did not remove it, with your devspaces, and the folder with Lima. Without the extension, delete the VM and the folder on macOS and Linux with:

  ```sh
  LIMA_HOME="$HOME/.nimblescape/devspaces/vm" "$HOME"/.nimblescape/devspaces/lima/*/bin/limactl delete --force devspaces
  rm -rf "$HOME/.nimblescape/devspaces"
  ```

  On Windows, `wsl --unregister devspaces` in a terminal deletes the distribution; then remove the folder `%LOCALAPPDATA%\nimblescape\devspaces`.
- **The scheduled task**, only when VS Code does not start again after the uninstall, for example when you remove VS Code too. Remove it by hand. On macOS:

  ```sh
  launchctl bootout gui/$(id -u)/com.nimblescape.devspaces.vm
  rm ~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist
  ```

  On Linux:

  ```sh
  systemctl --user disable --now devspaces-vm.timer
  rm ~/.config/systemd/user/devspaces-vm.service ~/.config/systemd/user/devspaces-vm.timer
  systemctl --user daemon-reload
  ```

  On Windows, in PowerShell:

  ```powershell
  $sid = [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value
  Unregister-ScheduledTask -TaskName "nimblescape Devspaces WSL $sid" -Confirm:$false
  ```

- **The objects of Devspaces on each Docker engine** where you did not run **Devspaces: Remove Devspaces from This Docker Engine…**. On a remote host, the Monitor can keep running; it ends itself after 30 days without a devspace there. [Remove by hand](#remove-by-hand) has the Docker commands.
- **The SSH key of Devspaces**, after **Use a Key**: the files `~/.ssh/devspaces_ed25519` and `devspaces_ed25519.pub` on your computer, and the line of the public key in `~/.ssh/authorized_keys` on each remote host; that line ends with `devspaces@` and the name of your computer. Delete the line on each host, then the two files.
- **What you installed for Devspaces**: QEMU and your membership in the group `kvm` on Linux, WSL 2 on Windows, and the Dev Containers extension, which other tools can use too.
- **Your settings** `devspaces.…` in `settings.json`, until you remove them.

### Remove by hand

These Docker commands remove the same without the extension, in a shell such as bash, zsh or PowerShell. For a remote engine, write `docker -H ssh://<host>` for each `docker`, or set `DOCKER_HOST=ssh://<host>` in the shell first (in PowerShell `$env:DOCKER_HOST = 'ssh://<host>'`). A command with an empty list stops with "requires at least 1 argument": there is nothing of that kind. A volume that does not exist gives an error for that volume only.

1. First the Monitor, the helper containers and a build of the helper image that runs, so that nothing of Devspaces works on the engine while you remove the rest, and no helper container uses a volume of a devspace:

   ```sh
   docker rm -f $(docker ps -aq --filter label=nimblescape.devspaces.monitor)
   docker rm -f $(docker ps -aq --filter label=nimblescape.devspaces.worker-run)
   docker rm -f $(docker ps -aq --filter label=nimblescape.devspaces.build-run)
   ```

2. Only if you want to delete the devspaces too: their containers, volumes, images and Docker Compose networks. These commands delete every devspace on the engine, also those of other accounts and other computers, with the clones of the repositories. Push your changes first.

   ```sh
   docker rm -f $(docker ps -aq --filter label=nimblescape.devspaces.id)
   docker volume rm $(docker volume ls -q --filter label=nimblescape.devspaces.id)
   docker image prune -a -f --filter label=nimblescape.devspaces.id
   docker network prune -f --filter label=nimblescape.devspaces.id
   ```

   Images that the devspaces were built from, for example `node:20`, stay; `docker image ls` lists them.

3. The rest that Devspaces keeps on the engine: the helper images, the build image and the shared volumes. The volume `devspaces-vscode` cannot be removed while a container of a devspace uses it.

   ```sh
   docker image prune -a -f --filter label=nimblescape.devspaces.worker
   docker image rm $(docker image ls --format '{{.Repository}}:{{.Tag}}' --filter reference=devspaces-buildx)
   docker volume rm devspaces-monitor devspaces-worker-cache devspaces-vscode
   ```

The objects of version 0.4.0 and older of the first extension have other names: see [Update from version 0.4.0 or older](#update-from-version-040-or-older).

### Docker contexts and your computer

- **Docker contexts.** Devspaces creates no Docker context, except the context `devspaces` of the setting `devspaces.createDockerContext` (see [Other Docker tools](#other-docker-tools)), which turning the setting off removes, and so does the uninstall (see [At the next start of VS Code](#at-the-next-start-of-vs-code)). Versions 0.1.0 and 0.2.0 did: their **Use a Remote Docker Host…** created a Docker context for each host, named after the host (for example `build-box`), with the description `Devspaces: remote Docker host <host>`, and made it the current context. Later versions do not use or remove these contexts. `docker context ls` lists them. To remove one, first set Docker to the local engine (`docker context use default`, or with Docker Desktop `docker context use desktop-linux`), then run `docker context rm <name>`.
- **Files.** Devspaces keeps its records, also the list of remote hosts (`remote-docker.json`), in a folder of VS Code: `~/.config/Code/User/globalStorage/nimblescape.nimblescape-devspaces-2` on Linux, `~/Library/Application Support/Code/User/globalStorage/nimblescape.nimblescape-devspaces-2` on macOS, and `%APPDATA%\Code\User\globalStorage\nimblescape.nimblescape-devspaces-2` on Windows. For VS Code Insiders, the folder `Code - Insiders` takes the place of `Code`. VS Code deletes this folder at its next start after the uninstall.
