# Security model

This document describes what Devspaces protects, how, and where its protection ends. The user guide is [guide.md](guide.md); how the parts work together is in [architecture.md](architecture.md).

## What Devspaces does on your computer

The README and the Marketplace page list these behaviors at the top. Each item links to its details.

- **GitHub sign-in.** Devspaces uses the GitHub sign-in of VS Code with the scopes `repo` and `read:org`, and with `read:packages` only when a private image on `ghcr.io` needs it. The scope `repo` reads and changes all repositories that the account can access. Devspaces uses every GitHub account of VS Code that you allowed for Devspaces, each with its own sign-in. VS Code keeps the sign-ins, and Devspaces saves no token on your computer. At each open from a VS Code window, Devspaces writes the token of the account that owns the devspace into the memory of the devspace, where Git, the GitHub CLI and every other program of that container can use it; a container that Docker restarts by itself has no token until the next open. See [The GitHub token](#the-github-token) and [Accounts](#accounts).
- **When.** Devspaces starts with every VS Code window: when VS Code starts, and right after the installation.
  - Before your first devspace, Devspaces only reads its Docker host when VS Code starts. It never reads the Docker context of this computer, because it never uses the Docker of this computer. It does not contact the Docker engine, read registry logins, build its helper image, or start a helper container; the first **Start** or **Refresh** builds the helper image.
  - After your first devspace, each window also works with Docker by itself, on the engine of the Docker host of Devspaces: a host of its list (also its VM). This work never starts Docker, and the WSL distribution of Devspaces only in the window of a devspace there, which starts it anyway, because WSL starts it for every use. When the window starts, it builds the helper image on that engine when its records show no build of the current helper image there, for example after an update that changed the image. While `devspaces.updateImagesOnConnect` is on (the default), it also checks once a week whether the base image of the helper image has a newer version, and then builds it again; it leaves out this check while the Monitor of that engine has done it within the week. Before such a build, it checks that Docker runs there. For the WSL distribution of Devspaces, it first starts its shell with `wsl.exe`. For an engine on another computer over SSH, it waits until the window has its SSH connection to that computer (for example the window of a devspace there), and works only through that connection, without an `ssh` login of its own; a missing helper image there is built by the next open. When its list of devspaces was lost, it restores the list from the volumes there.
  - While the view is visible, the window reads the state of your devspaces with a helper container, when this computer has devspaces on that engine. When this read finds the helper image missing, the window builds the image in the background, after the same checks, and the status bar shows "Devspaces: preparing" with the name of the engine. On another computer over SSH, it builds it only while the window has its SSH connection to that computer, through that connection; otherwise the next Start, Stop or Delete there builds it. On another computer, the helper container of the state reads and the restore starts with one `ssh` login of Devspaces, without a question (`BatchMode=yes`); the other Docker commands reach that computer through the `ssh` that the Docker CLI starts.
  - When VS Code starts with an empty window and `devspaces.reopenLastOnStartup` is on (the default), Devspaces opens the devspace of the window that you closed last, if that window was connected to a devspace and you did not stop the devspace with **Stop** (see [Reopen at startup](architecture.md#reopen-at-startup)). When VS Code restores the window of a devspace, Devspaces opens that devspace first. Both can start Docker Desktop and the container, and both write the GitHub token into the container.
  - Only while you look at the utilization page of a host (**Show Utilization** in the view "Docker Hosts"), the window reads the use of CPU, memory and disk of that host every 2 seconds (the VM of Devspaces) or 5 seconds (another computer), on the shell of the view, and the sizes of the objects of Docker (`docker system df -v`, as the view) after its first values and then every 10 minutes, only on that login while it is open. It reads nothing while the page is hidden or paused, it pauses after 2 minutes without the focus of the window and after 30 minutes without a click or a key on the page, and it never starts or keeps the VM of Devspaces running (see **The shell before the relay** in [Trust boundaries](#trust-boundaries)).
  - Only when you click an object row of the view "Docker Hosts" (or **Refresh** on its report page), the window reads the report of that object on the shell of the view: the facts of Docker, and for the shared volumes of Devspaces what they hold, read by one short-lived container of a helper image without a network (see **The shell before the relay** in [Trust boundaries](#trust-boundaries)). It never reads in the background and never starts the VM of Devspaces.
  - None of this Docker work runs on an engine from which you removed Devspaces with **Devspaces: Remove Devspaces from This Docker Engine…**, until you start or rebuild a devspace there, or run **Update All Images Now** there.
  - With the VM of Devspaces on macOS and Linux, a scheduled task of your user starts the VM and the Monitor at the times of `devspaces.cacheUpdateSchedule`, also while VS Code is closed: the launch agent `~/Library/LaunchAgents/com.nimblescape.devspaces.vm.plist` on macOS, the systemd user timer `devspaces-vm.timer` in `~/.config/systemd/user` on Linux, both without administrator permission. Its program, `~/.nimblescape/devspaces/task/vmTask.js` (a copy from the extension), runs with the rights of your user with the Electron of VS Code as Node.js. It starts only the VM and the existing container `devspaces-monitor` there, over the SSH of Lima, and gives the Monitor the schedule and the time zone; it reads no token and no registry login, and starts no devspace. It never wakes the computer. Devspaces creates it with the VM and removes it when the VM no longer exists (see [The VM of Devspaces](guide.md#the-vm-of-devspaces-macos-and-linux)).
  - With the WSL distribution of Devspaces on Windows, a scheduled task of your Windows user starts the distribution and the Monitor at the times of `devspaces.cacheUpdateSchedule`, also while VS Code is closed: the task `nimblescape Devspaces WSL <SID>` in the root folder of Task Scheduler (`<SID>`: the security identifier of your Windows user, from `whoami /user`), which Devspaces registers with `schtasks.exe` without administrator permission. It runs only while you are logged in, with the rights of your user, and never wakes the computer. Its action runs `wslg.exe` of WSL (no window), which runs a fixed script as root in the distribution: it starts the existing container `devspaces-monitor` there, gives it the schedule and the time zone, and then runs the idle script of the VM, which holds the distribution while something runs there, as the keeper of a window does; it reads no token and no registry login, and starts no devspace. Devspaces creates it after the setup of the distribution and removes it with the distribution; a distribution that you made yourself gets none (see [The WSL distribution of Devspaces](guide.md#the-wsl-distribution-of-devspaces-windows)).
  - Each window where you are signed in reads the repository list of each of your GitHub accounts in Devspaces from GitHub when it opens, and then every `devspaces.refreshIntervalMinutes` minutes (60 by default). Each account reads its own list with its own token.
  - When VS Code has a GitHub account that Devspaces does not use yet, Devspaces shows one notification the first time it sees that account. Only **Use in Devspaces** there asks VS Code for the account (see [Accounts](#accounts)).
  - A link `vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name`, for example on a website, opens your devspace of that repository. Without one, it asks before it creates a devspace (for a repository of your account or of one of your organizations, unless you chose "Always Open" in that question), and then starts the repository as a double-click on its row does, also when it is not in your list (see [Open from a link](guide.md#open-from-a-link)). VS Code first asks whether Devspaces may open the link, unless you chose "Do not ask me again for this extension" there. Like the reopen, a link can start Docker Desktop and the container, and it writes the GitHub token into the container. See [The trust model](#the-trust-model).
  - A course link `vscode://nimblescape.nimblescape-devspaces-2/course?repository=owner/name-<username>` does the same for your own repository of a course: Devspaces asks for the GitHub sign-in first if you are not signed in, puts the login of each of your accounts in place of `<username>`, and opens the repository that exists with the account of that login (see [Course links](guide.md#course-links)).
- **Docker CLI.** Devspaces runs the Docker CLI on your computer, for another computer with `DOCKER_HOST=ssh://<host>`, and for its VM through `wsl.exe` or the SSH of Lima: it checks that Docker answers, builds its helper image `devspaces-worker` on the Docker engine (in a container of its build image there, see **The build image of Devspaces** in [Trust boundaries](#trust-boundaries)), and starts its helper containers there. After the helper image of an engine was built again, each window starts a new helper container there from the new build, in the background with a login that asks nothing, and ends its earlier helper container once no operation runs in it ([R-DS-008](requirements.md#r-ds-008)). The engine is the VM of Devspaces, or Docker on another computer that you reach over SSH; Devspaces never uses Docker Desktop or Docker Engine of your computer, on any platform. For another computer, Devspaces runs `ssh` to check that the computer and its Docker answer, and then keeps it in its own list of hosts. It never creates or changes a Docker context or a setting of Docker, so the Docker tools in your terminals keep their target; only while you turn on the setting `devspaces.createDockerContext`, it creates the Docker context `devspaces` for its VM, which never becomes the current context, and removes it when you turn the setting off. On macOS and Linux the context points to the Docker socket of the VM; on Windows to a named pipe of Devspaces for your Windows user, which a window of Devspaces serves without a request filter, because a Docker context gives full access, and which only your user can write to (see [Other Docker tools](guide.md#other-docker-tools)). The window of a devspace on another computer reaches that Docker through a Docker pipe of Devspaces on your computer: a socket in a folder that only your user can open, or a named pipe on Windows. Devspaces carries each Docker connection of that window over its own SSH login to that computer, and so its own Docker calls there while that login is open, through such a pipe of its own (see [Trust boundaries](#trust-boundaries)). On Windows, when PATH of VS Code does not contain the folder of the Docker CLI that Devspaces uses (for example of a Docker Desktop that was installed for your user after VS Code started), Devspaces adds that folder at the end of PATH of the extension host of VS Code, so that the Dev Containers extension uses the same CLI; this lasts until the extension host ends and changes no setting. The window of a devspace on another computer runs the Dev Containers extension with the Docker CLI of Devspaces instead: one version that Devspaces downloads once from `download.docker.com` and checks against the size and SHA-256 in its code, whose folder it puts first in PATH of the extension host of that window only (see [the Docker CLI of Devspaces](architecture.md#the-docker-cli-of-devspaces)). Once it is there, Devspaces runs its own Docker calls on another computer with it too, in every window; on a computer without a Docker CLI, **Use a Remote Docker Host…** downloads it after you choose the host. See [Trust boundaries](#trust-boundaries), [the worker](architecture.md#the-worker-and-the-helper-channel) and [Remote Docker host](guide.md#remote-docker-host).
- **Dev Containers CLI.** The helper containers clone the repository into a Docker volume, and build, create, start, stop and remove the containers of a devspace with the Docker Engine API and the Dev Containers CLI. The lifecycle commands of the Dev Container configuration run in the dev container; `initializeCommand` is refused. See [Host access checks](#host-access-checks) and [the batch helper](architecture.md#the-batch-helper).
- **Registry logins.** The worker checks and pulls an image or Feature first without a login. When the registry refuses this or does not find the image, or when Docker Hub limits pulls without a login, the worker asks the extension for the login of its registry and names the image or Feature. The extension reads the login that Docker stored on your computer, from `~/.docker/config.json` (or `$DOCKER_CONFIG/config.json`) and by running the `docker-credential-*` helpers that it names. For `ghcr.io` without such a login, it uses the GitHub session with `read:packages`. The extension gives the logins of at most 8 registries in one open and writes each request to the log of Devspaces. The worker holds the login only for that one check or pull, and nothing stores it. For the build of the helper image, Devspaces runs `docker pull` of its build image `docker/buildx-bin` with the Docker CLI of your computer: the Docker CLI, not the extension, then sends the Docker Hub login that Docker stored, if there is one, as for any pull. Devspaces pulls the public base image `node:26-trixie-slim` the same way with `docker pull` before the build, as `docker build --pull` does. See [Registry access](#registry-access).
- **Docker installation.** When Docker is missing, Devspaces sets up Docker Engine in a VM of its own, without administrator permission and without a dialog (the log names the downloads and the folder). Devspaces never installs Docker on another computer. On Windows, Devspaces installs only WSL 2 without a Linux distribution (`wsl --install --no-distribution`, without a dialog of Devspaces: Windows asks for administrator permission itself) in a terminal of VS Code that you see. Then **Set Up Docker for Devspaces**, or a link to Devspaces while Devspaces has no Docker host, creates the WSL distribution `devspaces` of Devspaces for your Windows user: the `.wsl` file of the image of the VM of Devspaces from `ghcr.io`, with Docker Engine inside, checked against the size and SHA-256 in the code of Devspaces (see [Remote and shared engines](#remote-and-shared-engines)). On macOS and Linux, **Set Up Docker for Devspaces**, or a link to Devspaces while Devspaces has no Docker host, creates the Lima VM of Devspaces in `~/.nimblescape/devspaces`: Lima from `github.com` and the disk of the VM from `ghcr.io`, each checked against the size or SHA-256 in the code of Devspaces. Devspaces reaches the VM only over the SSH of Lima, with the key that Lima made for it. While the VM runs, Lima also carries its Docker socket into the folder of the VM (`~/.nimblescape/devspaces/vm/devspaces/sock/docker.sock`, in the folder of your user), over the same SSH as the user of Lima, who gets that socket at each start; that user may use `sudo` in the VM already, so this gives no new access. Only the Docker context of the setting `devspaces.createDockerContext` points to it. On Linux without QEMU, the setup first installs QEMU from the package source of your distribution with `sudo` in a terminal of VS Code that you see, and adds your user to the group `kvm` when your user may not use `/dev/kvm` (which lets your user run virtual machines). See [Installing Docker](guide.md#installing-docker).
- **SSH key.** After a login with your password to a remote host, Devspaces asks once whether to log in with a key next time. Only after **Use a Key** it creates its own key `~/.ssh/devspaces_ed25519` without a passphrase on your computer, when it is not there yet, and adds its public key to `~/.ssh/authorized_keys` of your account on that host. Its later SSH logins to that host use this key. It never writes over another file in `~/.ssh` and never changes your SSH config. See [The SSH key of Devspaces](#remote-and-shared-engines).
- **Background container.** On each Docker engine, the Monitor, the container `devspaces-monitor`, runs while a devspace runs there. On a remote host, it keeps running, also while no devspace runs and VS Code is closed, unless the setting `devspaces.stopMonitorWhenIdle` is on. On the WSL distribution of Devspaces and on the VM of Devspaces, it ends 5 minutes after the last devspace stopped; on the VM, the scheduled task of **When.** starts it at the times of the schedule. Devspaces asks no question about it. A Monitor that keeps running ends itself after 30 days in which no devspace was used on its engine. At the times of the setting `devspaces.cacheUpdateSchedule`, it pulls newer images of your devspaces, builds their next images in advance, removes older images of the same image repositories that no container uses, and downloads the newest VS Code Server and the extensions of the recent opens on that engine into a volume that the dev containers share. It also checks whether the base image of the helper image of Devspaces has a newer version, and then builds the helper image again on that engine, with the Docker CLI in its own container and the Dockerfile of Devspaces that the helper image holds. After such a build, the Monitor creates its successor `devspaces-monitor` from the new build, with the same settings, mounts and permissions, and ends; the successor removes the container of the earlier Monitor ([R-DS-009](requirements.md#r-ds-009)). In the same way, it moves to the script of a newer version of Devspaces that a window stored in its volume; the Monitor takes that script only when it matches the hash in its file name, the loader checks that hash again, and like every file of the volume it is no defence against someone who already has the Docker socket of the engine ([R-DS-011](requirements.md#r-ds-011)). It removes the objects of Devspaces that no container uses: the earlier builds of the helper image, the helper images that no running container used for 7 days, the older versions of the build image and of the base image of the helper image, the stopped helper containers that are older than 10 minutes, and on the VM of Devspaces the build cache that no build used for 7 days; never a devspace container, a volume or a network ([R-DS-007](requirements.md#r-ds-007)). To prepare an image, the engine runs the Dockerfile and the Features of the repository, also while no VS Code window is open. To link a newer VS Code Server into a running dev container that uses that volume, the Monitor runs a command in it as the remote user of the container, in the same way as `docker exec`. It stops a devspace a few minutes after its last window closes, unless you keep it running. It uses no token and no credentials. **Devspaces: Remove Devspaces from This Docker Engine…** removes it, with the helper containers, the helper images and the shared volumes of Devspaces (see [Uninstall](guide.md#uninstall)). See [the Monitor](architecture.md#the-monitor) and [Registry access](#registry-access).
- **Network.** Devspaces and its helper containers connect to GitHub, to a remote Docker host over SSH, to the image registries of your Dev Container configurations and of the setting `devspaces.defaultImage`, to the update service of VS Code, and to the Visual Studio Marketplace. The build of the helper image pulls the build image `docker/buildx-bin` and the image `node` from Docker Hub and installs packages from Debian, the Docker CLI from `download.docker.com` and the Dev Containers CLI from npm. The window of a devspace on another computer, or **Use a Remote Docker Host…** on a computer without a Docker CLI, downloads the Docker CLI of Devspaces from `download.docker.com` once for each version of it. The setup of the VM of Devspaces downloads the image of the VM from `ghcr.io` and, on macOS and Linux, Lima from GitHub; on Linux, the installation of QEMU reaches the package sources of your system. The VM itself reaches Debian and Docker for the upgrades of its packages. Each HTTPS request of the code of Devspaces, in VS Code and in its helper containers, sends the header `User-Agent: nimblescape-devspaces/<version>`. Other programs, such as Docker, Git and the Dev Containers CLI, send their own User-Agent. Only the Monitor asks the Visual Studio Marketplace: in its background run, for the extensions that the devspaces on its Docker engine used in the last 14 days, also the devspaces of other users of that engine. For each extension, it takes the newest release that works with the current VS Code Server, or the exact version when the extension is listed as `publisher.name@x.y.z`. It downloads only the files that its store does not have. Devspaces collects no telemetry. The code in a devspace can connect to any address (see [The trust model](#the-trust-model)). See [the helper image](architecture.md#the-helper-image) and [Registry access](#registry-access).

## The trust model

**A repository that you open is code that you run.** A malicious dev container can do harm. Its Dockerfile and build, its Features, its lifecycle commands, and the extensions in its container run with the rights of the container. They can:

- use the network: the internet, your local network, a VPN of your computer, and the services of your computer through `host.docker.internal`;
- attack the kernel, which every container shares with the Docker host (with Docker Desktop: with its virtual machine);
- use the channels that VS Code keeps open to your computer: the SSH and GPG agents, a socket that answers requests for your Git and Docker credentials, the opening of URLs, the clipboard, and your X11 display when one is set (see [Hardening your computer](#hardening-your-computer));
- read and change the repository, and use the GitHub token of the devspace. The token is the one of the account that owns the devspace: it can read and change the repositories that this account can access and read its organization memberships (scopes `repo` and `read:org`). The other accounts of Devspaces give their tokens only to their own devspaces.

The user in the container is the one that the repository chooses (`remoteUser`, `containerUser`, or the image), often a user without root rights that can use `sudo`. Devspaces does not change it.

The aim of Devspaces is that no setting of a configuration grants a container access to the Docker host beyond three things that it allows on purpose: the network (including VPN connections), ports on `localhost` of the host, and URLs that open in your browser. The checks are a guard rail against mistakes and copied templates, not a sandbox: a crafted repository can get around them. Open only repositories that you trust. For others, use a virtual machine, or a separate user account with its own Docker.

The first open of a repository that belongs neither to one of your accounts in Devspaces nor to one of their organizations asks for a confirmation.

**Links.** Any website can show a link to Devspaces (see [Open from a link](guide.md#open-from-a-link)). Your browser usually asks before it opens VS Code, and VS Code asks whether Devspaces may open the link. When you chose "Do not ask me again for this extension" in that question, VS Code no longer asks, and a click on such a link opens one of your devspaces without a further question; **Extensions: Manage Authorized Extension URIs...** in VS Code takes that choice back. When the link installed Devspaces, VS Code asked before the installation and does not ask again for that link. Before a link creates a devspace, Devspaces asks, and the question comes before any Docker work: for a repository of another owner, it always asks for the confirmation above; for a repository of one of your accounts or of one of their organizations, it asks whether it may create the devspace, unless you chose **Always Open** in that question. That button turns off the setting `devspaces.confirmOpenFromLink`, which counts only in your user settings, so a repository cannot turn the question off; turn the setting on again to get the question back. Devspaces takes only a link whose `owner/name` has the characters of GitHub names, and asks GitHub with each of your accounts in Devspaces for a repository that is not in your list. A course link opens only a repository whose name has the login of one of your accounts in place of `<username>`, with that account and with the same questions as a link `/open`, never with an account that has more rights on it.

**Workspace Trust.** In a VS Code window whose folder you have not trusted (Restricted Mode), Devspaces runs, and only your user settings count for its settings: VS Code ignores the values of the workspace or folder. The default extensions of `dev.containers.defaultExtensions`, which Devspaces records for the shared extension cache, also come only from your user settings, in every window.

## Trust boundaries

| Part | Where it runs | Trust |
|---|---|---|
| The extension | The local extension host of each VS Code window (`extensionKind: ui`) | Trusted. It holds the GitHub session, the local records, and the decisions. |
| The worker, its batch helpers, and the Monitor | Containers on the Docker engine | Not trusted by the extension. The engine may be on another computer and shared with other people. |
| The Docker engine | Your computer, or a remote host | Not trusted by the extension. Everyone who can use it controls every container on it. |
| The dev container | The Docker engine | Not trusted by the worker. It runs the code of the repository. |
| The Docker pipes of Devspaces: of a window, and of the extension for each SSH host | Your computer: a socket in a folder of your user, or a named pipe on Windows | Only for your user. Each pipe lets only the requests of the Docker API through that its program needs (the Dev Containers extension, or Devspaces). A program that can use the pipe of a window can still run programs in the containers of that engine; a program that can use the pipe of the extension can also create and start containers there, which the build of the helper image needs. The log of a container goes through the pipe of the extension only while the setting `devspaces.allowContainerLogs` is on (default off): then the log of any container, which **Show Log of the Monitor** needs (the Docker CLI asks for a log by the ID of the container). While it is off, both pipes refuse the log of every container. |
| The pipe of the questions of SSH logins | Your computer: a socket in a folder of your user, or a named pipe with a random name on Windows | Only for your user. It shows a question only for a login with its random token, and gives the answer only to that login. |
| The SSH key of Devspaces, after **Use a Key** | Your computer: `~/.ssh/devspaces_ed25519`, without a passphrase | Only for your user. Every program of your user can log in with it to each host that has its public key. |
| The WSL distribution of Devspaces (`wsl:devspaces`), on Windows | Your computer: a WSL distribution of your Windows user, with its Docker engine | Like the Docker engine. Every program of your Windows user can run commands as root in it with `wsl.exe`, as in every WSL distribution of that user. |

**Extension and worker.** The extension commands the worker only through typed operations (see [architecture.md](architecture.md#the-worker-and-the-helper-channel)). No Docker command and no script crosses the channel. Both sides check every message strictly, and the extension limits each request in size. Towards the worker, the extension:

- answers a request that changes its records only for the devspace of the operation, under its own registry lock, with its own clock and its own view of the windows; there is no generic write;
- allows each operation only its own kinds of requests; only `open` may ask for a secret;
- gives a secret only when the operation asks for it: the GitHub token to an open, and to an open the login of the registry that the request names together with an image or Feature, one request at a time and for at most 8 registries in one open (see [Registry access](#registry-access));
- shows every text of the worker, of a configuration, and of an error as plain text in its messages: it breaks the syntax of a link (`[label](target)`) in them, so that no such text becomes a link that runs a command of VS Code when you click it;
- keeps the remembered result of the host access check of a configuration in its own storage, stamped with the hash of the worker code that computed it; the worker and the engine never store it;
- uses the Monitor's registry answers only to decide whether an update is due, never as an input of a security check;
- uses the record of the Monitor's last check of the helper image only to decide whether the window checks the base image of the helper image itself, and takes it only for the helper image of its own version, never as an input of a security check.

The code that runs in the worker, the relay, the batch helpers, the Monitor, and the analysis threads is one readable file in the extension's own `.vsix` package: `dist/helperChannel.js`. The container that loads it checks it against the SHA-256 hash on its command line, stores it, and runs it from that file (see [architecture.md](architecture.md#pipe-loading)). Before the worker starts an analysis thread from that file, it checks the hash of the file again. Nothing in the file runs with `eval`. It holds fixed scripts as text, which run with `node -e` or `sh -c`: the one-line pipe loader, and the scripts that the worker and the steps of the batch helpers run in containers. To check a container, compare the output of `sha256sum dist/helperChannel.js` in the folder of the installed extension with the hash in the command of the container (`docker inspect`).

**The relay.** The same file holds the relay (see [architecture.md](architecture.md#the-relay)). On another computer, it is the first program of the worker container, so that one SSH login carries the worker channel and the Docker connections of the window. Devspaces starts it with `ssh … sh -s` and writes a fixed start script of one line on the input of `sh`: it prints a random marker and runs `docker run` with every word in single quotes, so no word is read as a command of the shell (a word with a line break is refused). What the login prints on the standard output before the marker is never read as a command or as data; only its size goes to the log (see [architecture.md](architecture.md#the-connection-of-the-relay)). The error output of `ssh` is kept as before: its last lines are the reason of a failure in the log and in the message, so they can contain a text of the host (for example its SSH banner). The relay keeps the rule above: the worker channel stays the typed operations, and the Docker streams never reach the worker. The relay connects a stream only to the worker, which it starts from the stored file with the hash that the pipe loader checked, or to the Docker socket of the container; it opens no other socket, host, or port. Both sides check every frame strictly and end the connection at a frame that breaks the rules. The credit of each stream limits what each side holds in memory for it, and a connection has at most 256 streams.

**The Docker pipe.** The window of a devspace on another computer reaches its Docker engine through a Docker pipe of Devspaces on your computer, whose address the URI of the window names (see [architecture.md](architecture.md#the-docker-pipe)). Every program that can connect to it controls that Docker engine, as `docker -H ssh://<host>` with your SSH keys does. On macOS and Linux, it is a socket with mode 0600 in a folder with mode 0700 in your runtime folder or your temporary folder; Devspaces refuses a folder of another user and a link. On Windows, it is a named pipe with the default security of Node.js: other users of the computer can open it for reading, but they cannot send a request. Its name contains 16 hexadecimal digits of a hash of the ID of this computer, the Docker host, and the container; the ID is no secret (see [Stored data](#stored-data)). A window serves only the address that this computer makes for its devspace. When it cannot serve it, for example while another program serves a named pipe with that name for more than 15 seconds, the window closes its connection before the Dev Containers extension uses the address. The pipe lets only the requests of the Docker API through that the Dev Containers extension needs to attach the window: reads, the start of the container, and programs in it (exec). It refuses every other request, for example the creation, the build or the removal of a container or an image, with an error, before any byte of it reaches the engine. It checks the method and the path of each request, not its query or its body, so a program that can use the pipe can still run any program in a container of that engine, also with more rights (see [remote-connection.md](remote-connection.md#the-request-filter)). The pipe does not change the bytes of a request that it lets through; for the log, it reads the method and the path of the first request (without the query). The window of a devspace on an engine from which you removed Devspaces runs `ssh … docker system dial-stdio` for each connection, as the Docker CLI does, so it starts no helper container there. So does a window while the connection of the relay cannot be had, with one SSH login for each connection.

For its own Docker calls, Devspaces serves one more such pipe for each SSH host, from the first time that its SSH connection to the host passed its checks until the window closes (see [architecture.md](architecture.md#the-docker-pipe)): a socket in the same kind of private folder, or a named pipe, with a random name that no URI contains. Only the Docker CLI of Devspaces gets it, as `DOCKER_HOST` of its calls on that host while the SSH connection is open; no environment variable and no setting of your user changes. Each connection goes over that SSH connection, or, when it ended meanwhile, over its own `ssh … docker system dial-stdio`. This pipe lets only the requests through that the Docker calls of Devspaces need: reads, the build of its helper image, and the removals of **Remove Devspaces from This Docker Engine…**. While its calls go through this pipe, Devspaces skips its SSH check before an operation on the host, because the Docker CLI then starts no `ssh` that could ask a question. The check of the Docker engine of each new SSH connection never goes through another SSH connection.

**The Docker CLI of Devspaces.** The window of a devspace on another computer runs the Dev Containers extension with a Docker CLI that Devspaces downloads, not with the Docker CLI of your computer (see [architecture.md](architecture.md#the-docker-cli-of-devspaces)). It is the static build of Docker Inc. from `https://download.docker.com`, in the one version that Devspaces names in its code with the size and SHA-256 of the file of each platform. Docker publishes no checksums and no signatures for these files, and the Windows and macOS programs carry no code signature; the hashes in the code were computed from a download of each file, and every later download must have exactly that size and hash, or Devspaces removes it before it reads anything out of it. So a changed file on the server, or a change on the way, cannot bring another program; the trust in the program is the trust in that version of Docker Inc. at the time of the pin. Devspaces downloads only from that host over HTTPS, without a redirect, and keeps only the program `docker` (`docker.exe`) of the archive, in `docker-cli/<version>/` of its global storage, which belongs to your user. A program that is already there is not checked again: a program of your user can change it, as it can change the extension itself. Devspaces puts that folder first in PATH of the extension host of such a window only, until the extension host ends; it changes no PATH of your user, no setting and no other window, and the Docker tools in your terminals keep their Docker CLI. That CLI reads your Docker configuration (`~/.docker/config.json`), as any Docker CLI does. The Dev Containers extension gives it the Docker pipe of the window; another extension of that window that starts `docker` gets this CLI too, with your current Docker context, as it would get the Docker CLI of your computer. When the download fails or you cancel it, the window uses the Docker CLI of your computer, if there is one. Devspaces itself runs its Docker calls on another computer with this CLI too, in every window, once it is there, and the Docker CLI of your computer only without it; its calls for the Docker of your computer keep the Docker CLI of your computer. On a computer without a Docker CLI, **Use a Remote Docker Host…** downloads this CLI after you choose the host, with the same checks; when that download fails or you cancel it, no host is set.

**The build image of Devspaces.** Devspaces builds its helper image on every engine in a short container `devspaces-build-<16 hex>` (see [architecture.md](architecture.md#the-helper-image)). It runs `docker/buildx-bin` of Docker Inc. from Docker Hub, the program buildx alone, in the one version and image digest that Devspaces names in its code (`src/core/docker/buildxPin.json`); Docker checks the content of the image against that digest at the pull, so another image under the same name cannot come in its place. On the engine it gets the tag `devspaces-buildx:<version>`, and Devspaces runs it by that tag, as it runs its helper image by its tag. The container gets the Docker socket of the engine, which gives it control of that engine, as the worker has; it has no network, no log of the engine (`--log-driver none`), no capabilities, `no-new-privileges`, and `--rm`, and gets the build context (the Dockerfile of the helper image) on its standard input. So the trust in the build is the trust in that version of buildx of Docker Inc. at the time of the pin, as for the Docker CLI of Devspaces. A daily workflow proposes a newer version as a pull request. Devspaces pulls the base image of the helper image with `docker pull` before the build, so the container needs no network.

**The shell before the relay.** Before an SSH connection of the relay starts, Devspaces runs its checks on the same login (see [architecture.md](architecture.md#the-shell-before-the-relay)): `ssh … sh -s` with the options of the SSH check, which asks no question outside of a flow that you started (see **SSH questions in VS Code** below). It writes only fixed command lines on the input of `sh`: `docker` and the words of a Docker call that only reads (each word in single quotes, a word with a line break is not sent), and `printf %s "$XDG_RUNTIME_DIR"`. Each line ends with a random marker that is new for each command; the output before the marker is the output of that command, and what the login prints before the shell answers is never read as a command or as data. So these calls run with the Docker CLI of the other computer and your account there, as `docker system dial-stdio` of your Docker context does. No call that changes something, and no call with an option that names a file or endpoint of your computer, runs there, except the actions of the view "Docker Hosts" that you start (`docker container stop`, `start` and `rm`, `docker image rm`, `docker volume rm`, `docker network rm`, each object by its ID or name, and `docker builder prune` only on the VM of Devspaces), so that the view uses one login of the host for its reads and its actions. The utilization page of a host ([`R-ENG-009`](requirements.md#r-eng-009)) writes one more kind of line there: `{ printf '%b' '<script>' | sh -s; }`, where the script is fixed in the code of Devspaces. The script of a sample only reads `/proc`, the cgroup files of the containers and the free space of the disks, and between two samples the page runs only `docker ps` (the names of the containers) or `docker info` (the data folder of Docker). The extension fills in only a random marker, the number and the kind of the sample, and the data folder of Docker, which it checks first (an absolute path without a quote and a line break), so no other text reaches the shell. Nothing of it writes a file or starts a container. The page shows the names and the other texts from the host only as text, in a webview whose content security policy allows only its own script and style sheet. The report of a resource of the view ([`R-ENG-010`](requirements.md#r-eng-010)) runs two more calls there (or through the Docker pipe of the extension while a connection of the relay is open), each exactly as the code of Devspaces makes it: the reader of the shared volumes of Devspaces, `docker run --rm --pull never --network none --read-only --cap-drop ALL --cap-add DAC_READ_SEARCH --security-opt no-new-privileges` of a helper image that is already on the host, with only the shared volumes that exist, each mounted read-only, and `node -e` with one fixed script that only reads them and prints what they contain; and `docker logs --tail 2000 --timestamps devspaces-monitor` for **Show Log of the Monitor**, only while the setting `devspaces.allowContainerLogs` is on (default off). The reader never reads a volume or another object that is not of Devspaces, and the report page also shows the texts from the host only as text, in a webview with the same content security policy. The connection of the relay then takes this login over. A shell that is not used for 2 minutes is closed.

**The view Docker Hosts and its console.** By default the view "Docker Hosts" only reads ([`R-ENG-008`](requirements.md#r-eng-008)): the setting `devspaces.dockerHostsActions` is `disabled`, so no row offers an action that changes a host, and a changing command that gets a row of the view runs nothing. `contextMenu` or `icons` turn the actions on. These are settings of the scope `application`: a workspace or folder setting, which a repository could bring along, cannot turn them on. **Open Console** (setting `devspaces.dockerHostsConsoleButton`, default off) opens a full shell on a host with the rights of your account there: your login over SSH, root in the WSL distribution of Devspaces, and the user of Lima in its VM, who may use `sudo` without a password. Its program runs on your computer (`ssh -tt`, `wsl.exe … script`, or the SSH of Lima), with the same key and the same questions in VS Code as the other logins of Devspaces; the extension writes only your keys into it. The start script of the console is fixed in the code of Devspaces; the extension fills in only the size of the terminal as whole numbers. The script reports the name of its terminal on the host; Devspaces uses that name for a change of the size only when it is `/dev/pts/<number>`, so no text from the host reaches a command line. The second connection that sets the size asks nothing (`BatchMode` over SSH).

**Worker and dev container.** The worker writes into a dev container only through the scripts of its registry, with the arguments as positional parameters and secrets only on standard input. These scripts follow no symbolic link that they did not create, and overwrite nothing that they did not write: a process in the dev container can plant links at any time. The batch helper that works on the volume of a devspace runs as root, but:

- the Docker socket lies in a folder that only root can enter;
- the clone runs as the user `devspace-git` (UID 52741), without groups, capabilities, or new privileges, and cannot reach the socket;
- the steps that read the repository (its configuration and its Docker Compose files) run as the user that owns the repository folder;
- root follows no link that the dev container planted in the volume.

## Host access checks

Before a container is created, Devspaces checks the final configuration: `devcontainer.json` with what its Features and its base image add to it (the label `devcontainer.metadata`), and every service of Docker Compose. It checks again before `up`, on the `runArgs` as Docker gets them and on the metadata of the image that was built. A configuration that breaks a rule is refused, before anything is pulled, built, or started, with a message that names each offending setting. The volume of the devspace is kept.

The checks are on for every repository by default. The user setting `devspaces.hostAccessChecksOff` lists the repositories whose checks are off; only your user settings count, never a workspace or folder setting.

### Refused while the checks are on

- Bind mounts of files and folders of the host, also of the Docker socket (for example by a Feature), and of `${localWorkspaceFolder}`.
- Privileged mode; capabilities beyond Docker's default set and `SYS_PTRACE`; security options other than `seccomp=unconfined` and `no-new-privileges`.
- Devices and GPUs, also `hostRequirements.gpu` and limits that name devices.
- The namespaces and control groups of the host (`--pid=host`, `--ipc=host`, `--uts=host`, `--userns=host`, `--cgroupns=host`, `--cgroup-parent`).
- Other container runtimes (`--runtime`), volume drivers and volume options other than `volume-nocopy` and `volume-subpath`, and `--use-api-socket`.
- `--oom-kill-disable` and a negative `--oom-score-adj`; log drivers that write to the host or use credentials of Docker.
- The network of another container (`--network container:…`, `network_mode: container:`), `--volumes-from`, and `--link`.
- Published ports on another address than `127.0.0.1`, and `-P`.
- The setting `remote.localPortHost` in the configuration, which would make VS Code forward ports on all addresses.
- The volumes of other programs and containers: volumes that Docker Compose or the Dev Containers extension created (by their labels), and anonymous volumes of other containers.
- Build options that reach files, keys, and agents of the helper during the build (`--secret`, `--ssh`, `--output`, `--allow`, `--build-context` with a folder).

### Refused whatever the switch says

- Everything of another devspace: its workspace volume, a volume that a devspace of another GitHub account uses or that its Delete kept, its named networks, and the images of the devspaces of other accounts (by image ID, not by name).
- The processes of other containers, and their volumes through `--volumes-from` or `volumes_from`, also of the dev container for the other services of Docker Compose.
- The folders of Devspaces as paths of the configuration (a mount, a build context, or a Dockerfile): the token folder `/run/devspace` (also as `/var/run/devspace`), the configuration folder `/workspaces/.devspace+`, and the folders of the helper with the Docker socket and the token. A mount propagation that shares `/`, `/run`, or `/var/run` with the host is refused too.
- The cache volume of the helper and the volumes of Devspaces (`devspaces-monitor`, `devspaces-vscode`).
- The variables that set the Git configuration (`GIT_CONFIG`, `GIT_CONFIG_*`) or that Devspaces sets (`GIT_SSH_COMMAND`, `DOCKER_CONFIG`, `GH_CONFIG_DIR`), and the token and host variables of the GitHub CLI (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`), in `runArgs`, `containerEnv`, and `remoteEnv`, also when a Feature or the base image sets them.
- `initializeCommand`: it would run in the helper, which has the Docker socket.
- Labels with the prefixes `nimblescape.devspaces.` and `devcontainer.` (except `devcontainer.metadata`), and the labels of Docker Compose. Such a label could hide a container from Devspaces or make it look like another devspace.
- A Dockerfile longer than 1 MiB, or one that links out of the repository.
- Options of `runArgs` and `build.options` that Devspaces does not know.

### What Devspaces changes instead of refusing

- Published ports without an address (`-p 3000:3000`, `appPort`) are bound to `127.0.0.1` while the checks are on.
- `--rm`, `-it`, and `-d` are removed, because Devspaces runs the container itself; `--name` is replaced by the name of the devspace. The log names each removed option.
- `shutdownAction` is `none`, so that only Devspaces stops the container.
- For Docker Compose, only the dev service gets the workspace volume; a bind mount of files of the repository becomes a mount of that folder of the workspace volume (Docker Engine 26 or newer); every container gets the labels of the devspace.
- Values of `${localEnv:…}` of your computer are not passed: the Dev Container CLI resolves them in the helper, where they are empty or have the helper's value.

### Turning the checks off

**Turn Off Host Access Checks…** in the context menu of a repository adds it to `devspaces.hostAccessChecksOff` after a warning; **Turn On Host Access Checks** removes it. With the checks off, the refusals of the first list are lifted, so the configuration, its Features, and its base image may use the files of the host, the Docker socket (which gives full control of Docker and of every other devspace, also their tokens), privileged mode, devices, and ports on all addresses. Everything in the second list stays refused. The row shows `host access unrestricted`, and the log says so at every start. A change applies when the container is created next; a container that was created without the checks is created again at the next start after they are turned on, if the configuration passes them.

A repository with the checks off is never prepared in the background, and an open with the checks off never uses a prepared image.

## The GitHub token

Devspaces signs in with the GitHub authentication of VS Code, with the scopes `repo` (list and clone private repositories) and `read:org` (organization memberships). It asks for `read:packages` only when a private image on `ghcr.io` needs it. VS Code stores the sessions, one per account and set of scopes; Devspaces keeps no token in its settings or files.

**One account per devspace.** Every call of Devspaces to the GitHub sign-in of VS Code names the account. The extension binds each operation to the account that owns its devspace, in its own memory: the worker never names an account, and the extension answers its requests for the token, the account and the registry logins only for that account. An operation of no account gets no token.

**Never in a variable, on a command line, or in a log.** The token travels only as the secret of an operation, and every process gets it on its standard input. The worker masks every secret that an operation held in all its progress, log lines, tool output, and errors; the extension's log masks it too.

**The clone.** The batch helper clones with the token, which lies in a tmpfs of the helper (`/run/devspace-secrets`) only during the clone step and belongs to the Git user only during that step. The remote URL of the clone contains no token, and `.git/config` holds none.

**In the dev container.** Devspaces keeps the token only in the memory of the running dev container:

- `/run/devspace` is a tmpfs that Devspaces adds to every dev container it creates (`nosuid`, `nodev`, `noexec`, 1 MiB, mode 0700, owned by the remote user). It holds `github-token` (mode 0600) and `gh/hosts.yml`, which signs the GitHub CLI in with the same account. The settings of the GitHub CLI (`config.yml`) stay in the volume.
- Devspaces writes the token at each open from a window, after the container runs and before the lifecycle commands, so that they can use Git and the GitHub CLI as the owner account. The write runs as root through `docker exec` with the token on standard input. It first checks that `/run/devspace` is exactly the tmpfs that Devspaces created, with no other mount at or below it and no propagation to the host; otherwise it writes nothing, and the open says that Git could not be prepared.
- The token is never in the workspace volume, a kept volume, or an export. It is gone when the container stops. Like other memory, the kernel may swap it to the swap space of the host or of the Docker VM.
- When a window leaves a devspace because its owner account left Devspaces (a sign-out, or you removed the access of Devspaces to that account), Devspaces removes the token from every running dev container of that devspace at once, before the window closes its remote connection (the window waits at most 30 seconds for that). The windows of the devspaces of your other accounts stay connected, and a new account never closes a window. Otherwise it stays in the running container until the container stops or the next open replaces it. A sign-out in VS Code may not make the token invalid on GitHub; to do that, revoke the access of VS Code in the GitHub settings (Applications).
- A container that starts without an open from a window (a restart by Docker, `docker start`) has no token until the next open. The Monitor never writes the token.

**Who can read it.** While the container runs, every process in it that runs as its user or as root can read the token, and so can everyone who can use the Docker engine (`docker exec`), on your computer or on a remote host.

## Git inside the container

Git and the GitHub CLI in a devspace use only its own configuration and the token of the account that owns it. Nothing of your computer is used: no copied `~/.gitconfig`, no forwarded credential helper, no forwarded Docker credentials, and no SSH agent for Git.

- The folder `/workspaces/.devspace+` in the volume holds `gitconfig` (the identity of the owner account from its GitHub profile, and a credential helper that answers only for `https://github.com` from the token file), `credentials.gitconfig` (your credential helpers for other Git servers), `docker/`, and `gh/config.yml`. It holds no secret.
- Devspaces sets only documented variables of Git, Docker, and the GitHub CLI in `containerEnv` and `remoteEnv`: `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` (they remove every other credential helper and add the helper of the container), `DOCKER_CONFIG`, `GIT_SSH_COMMAND=ssh -o IdentityAgent=none`, and `GH_CONFIG_DIR=/run/devspace/gh`.
- For each container, the settings of the Dev Containers extension switch off the copy of your Git configuration (`dev.containers.copyGitConfig` and `remote.containers.copyGitConfig`), its Git credential helper (`dev.containers.gitCredentialHelperConfigLocation: none`), its Docker credential helper (`dev.containers.dockerCredentialHelper`), and the sign-in of the GitHub CLI with your token (`dev.containers.githubCLILoginWithToken`). Your global settings stay unchanged, so your other dev containers keep working.
- A container gets a `~/.gitconfig` of Devspaces when it has none or an empty one, so that Git older than 2.32 reads the configuration of the volume too.

### Variables that Devspaces never sets

The Dev Containers extension and the VS Code server expect their own values in these variables, so Devspaces never sets or changes them, in the dev container or in the helper:

- `REMOTE_CONTAINERS_IPC` and every other `REMOTE_CONTAINERS*` variable;
- `SSH_AUTH_SOCK` and `BROWSER`;
- every `VSCODE_*` variable.

`DOCKER_HOST` is never set: the helper reaches Docker through `/var/run/docker.sock`, a link to the socket of its engine, the engine on which the extension started it. The steps of the batch helper also never pass `PATH`, `HOSTNAME`, `NODE_OPTIONS`, `TMPDIR`, or any `DOCKER_*`, `BUILDX_*`, `BUILDKIT_*`, or `LD_*` variable from a configuration to the tools.

## Registry access

- **At an open**, the image check and the pulls run in the worker, on the Docker engine. The image check asks each registry first without a login. The worker asks the extension for the login of the registry only when the registry refuses this request (HTTP 401 or 403, also when its token service refuses a token without a login), or when it answers 404, because some registries answer 404 for a private repository. After a 404, the worker asks the registry again only when your computer has a login for it. A pull also goes first without a login. The worker asks for the login only when the registry refuses the pull (HTTP 401 or 403, or Docker's answer that the repository does not exist or needs a login, also `no basic auth credentials`), when the registry does not find the image (`manifest unknown`, `name unknown`, or the `<reference>: not found` of the containerd image store), for the same reason as the 404 above, or when Docker Hub limits pulls without a login (`toomanyrequests`). It then pulls again with the login, when your computer has one. Each request names the image or Feature, as its registry and repository. The extension checks that they form a valid image name with a valid host name, and gives only the login of that registry: the credentials that Docker stored on your computer (the `docker-credential-*` helpers run on your computer), or for `ghcr.io` without such a login, the GitHub session with `read:packages` of the account that owns the devspace. It answers one request at a time and refuses a second request that comes meanwhile, gives the logins of at most 8 registries in one open, and writes each request with its answer or the reason of its refusal to the log of Devspaces (Devspaces: Show Log), never the login itself. A registry counts against this limit only when the worker asked for its login and your computer has one. The worker holds the login only for that check or pull, then forgets it, and asks again for the next one. It sends the login only in the header of its request to that registry, never into a file.
- **Where this protection ends:** the extension cannot read the configuration of a devspace, because it lies on the Docker engine, so it relies on the worker for which images and Features an open uses. Whoever controls the Docker engine controls the worker, and can get the logins of up to 8 registries at each open, as well as the GitHub token (see [Trust boundaries](#trust-boundaries)).
- **In the background**, the Monitor and its prepares use no token and no credentials at all. They pull and ask registries anonymously. A private image or Feature is therefore not updated or prepared in the background; its next open checks and builds it with your credentials.
- The worker and the Monitor reach the internet through the proxy of the Docker daemon (`HTTPProxy`, `HTTPSProxy`, `NoProxy` of `docker info`), never through the proxy settings of your computer or of VS Code.
- The image check asks for the digest of a tag with an HTTP `HEAD` request, which does not count against the pull limit of Docker Hub. An image is pulled only when its digest changed.

## Accounts

Devspaces can use several GitHub accounts at the same time. An account of Devspaces is a GitHub account of VS Code that has a session with the scopes `repo` and `read:org` and that you allowed for Devspaces. Devspaces reads these accounts at each change of the GitHub sessions of VS Code and asks VS Code for each one by name, without a dialog. It never opens a sign-in dialog of VS Code without a click of yours.

- **Adding an account.** **Devspaces: Add GitHub Account…** (in the title bar of the view) opens the account picker of VS Code, which ends with **Sign in to another account**. When VS Code has a GitHub account that Devspaces does not use yet, for example one that only another extension uses, Devspaces shows one notification the first time it sees that account, while it uses another account already. **Use in Devspaces** asks VS Code for that account. **Not Now**, or a closed notification, is remembered for that account on this computer.
- **Removing an account.** In the Accounts menu of VS Code, select the account, then **Manage Trusted Extensions**, and remove Devspaces there; or select **Sign Out**, which removes the account for every extension. VS Code has no function with which an extension can remove its own access.
- **One devspace, one account.** A devspace belongs to the account that created it, its owner. Docker cannot change the owner of its volumes and images. The devspace gets only the token and the registry logins of its owner, and Git and the GitHub CLI in it work as that account. A push to a repository that only another of your accounts may change fails in that devspace.
- **Which account a Start uses.** An existing devspace of the source opens with its owner; when two accounts have one, the one used last opens. For a new devspace, only the accounts that can access the repository count: their list has it, or GitHub shows it to them. Among them, the highest permission wins (admin, maintain, write, triage, read, then unknown), then the account whose login owns the repository, then a member of the organization that owns it, then the login that comes first in alphabetical order. The tooltip of a row names the account. **Start with Account…** in the context menu creates a separate devspace of another account that can access the repository; the existing devspace stays as it is.
- **The list.** Each account loads and stores its own list with its own token (one file per account). The view shows one list of all accounts, merged in memory, and names the account in the hint of an organization that refuses one account. The trust of an owner (the questions of the first open and of a link) counts the logins and the organizations of all accounts of Devspaces.
- **An account that leaves.** When an account leaves Devspaces, its list and its devspaces are hidden at once, and every window of one of its devspaces closes its connection after its token left the running containers of that devspace.
- **Devspaces of an account that Devspaces does not use** are not shown and not counted, and no command acts on them. Only a Start of their repository and source names the login of their owner, in a question: **Sign In as `<login>`** asks VS Code for that account, and **New Devspace as `<login>`** creates a separate devspace of an account of Devspaces. The devspace of the other account stays.

All devspaces of a Docker engine are Docker objects of the same engine. The separation protects against using the wrong account, not against another person who can use your user account or the engine.

## Remote and shared engines

- On a remote host, the token goes into the memory of the container on that host, never onto its disk: the extension sends it over SSH to its worker there, which writes it into the container through the Docker Engine API.
- **SSH questions in VS Code.** Only an SSH login of a flow that you started (a command with its progress notification, or the test of a host of **Use a Remote Docker Host…**) asks you, in VS Code: for an unknown host key, a password, the passphrase of a key, or a code (see [architecture.md](architecture.md#login-without-setup)). Every other login of Devspaces runs with `BatchMode=yes`, for example the reads of the view and the builds in the background, so an unknown host key or a key that is not loaded fails at once, with a message. The `ssh` that the Docker CLI starts for the Docker commands has no terminal to ask on; on Windows, it can wait until the time limit of the command instead.
  - `ssh` of your computer asks the questions through the program in `SSH_ASKPASS`: a small helper of Devspaces in its storage, which runs with the Node.js of VS Code (on Linux and macOS through a short shell script next to it; on Windows started directly, without `cmd.exe`, so the text of a question can never become a command). The helper sends the question over a pipe that only your user can open, with a random token of that one login, and gives the answer back to `ssh`. Devspaces never stores, logs, or sends an answer anywhere else; the log names only the kind of a question and the fingerprint of a host key.
  - A host key is accepted only when you choose **Accept and Connect** in the dialog that shows its fingerprint; then `ssh` writes it to your `known_hosts`, as `ssh` in a terminal does. Compare the fingerprint with the one that the person who runs the host gives you. A host key that changed is refused by `ssh` without a question.
  - The text of a question comes from `ssh`, and for a keyboard-interactive login from the host; it is shown as plain text.
- **The SSH key of Devspaces.** Only when you choose **Use a Key** after a login with your password, Devspaces creates the key `~/.ssh/devspaces_ed25519` on your computer with `ssh-keygen` (when it is not there yet) and adds its public key to `~/.ssh/authorized_keys` of your account on that host (see [architecture.md](architecture.md#the-key-of-devspaces)). **Not for This Host** is remembered for the host.
  - The private key has no passphrase, so that the logins in the background need no question. Every program that runs as your user on this computer can read it, and log in to each host where its public key is in `authorized_keys`, as with any key without a passphrase. `ssh-keygen` writes it only for your user (mode 0600; on Windows only for your account). Devspaces never sends it anywhere and never copies it into a container; only the public key goes to the host.
  - On the host, Devspaces adds one line to `~/.ssh/authorized_keys`, with the comment `devspaces@<name of your computer>`, and changes nothing else there. When the test login with the key fails, it removes that line again. It never writes over a file in `~/.ssh` of your computer, and never changes your SSH config or your agent.
  - For the Docker CLI, which takes no options of `ssh`, the calls to such a host find a small `ssh` script of Devspaces first in PATH (in the storage of the extension, only for your user), which adds the key to the `ssh` of your computer.
  - To remove the key: delete its line from `~/.ssh/authorized_keys` on each host, and the files `~/.ssh/devspaces_ed25519` and `devspaces_ed25519.pub` on your computer.
- **The WSL distribution of Devspaces.** On Windows, Devspaces can use the WSL distribution `devspaces` as a host of its list (see [architecture.md](architecture.md#the-wsl-distribution-of-devspaces)). It starts `wsl.exe -d devspaces -u root --cd / --exec …` as your Windows user: the shell before the relay and the connection of the relay (`sh -s`), and `docker system dial-stdio` for the Docker pipes. To know whether the distribution runs, it runs `wsl.exe --list --running --quiet`. These commands run as root of the distribution, without a login and without a question, because WSL lets every program of a Windows user do that in the distributions of that user. Devspaces offers only the distribution with the name `devspaces`, never another one. Its Docker engine is an engine like any other for Devspaces: the token goes into the memory of a container there, and the Docker pipes of Devspaces for it are only for your user, as for an SSH host. WSL runs all distributions of a computer in one virtual machine, with one Linux kernel and one network.
  - **The keeper**: so that the distribution runs while something runs there, also after VS Code closed, a window that uses it starts `wslg.exe` of WSL (only for the distribution `devspaces`, never in another distribution) (`%ProgramFiles%\WSL\wslg.exe`, which opens no console window) with a short script as root of the distribution: it runs the idle script of the image of the VM (`/usr/lib/devspaces/idle`), which looks every minute whether a container runs, a program is connected to Docker Engine, or the package upgrade runs, and ends after two checks in a row at which nothing ran; its output goes to `/var/log/devspaces-idle.log` in the distribution. It is not a child of VS Code, so it runs on after VS Code closed, and it reads and sends nothing else. No other process of Devspaces keeps the distribution running when nothing runs there. Devspaces adds no start entry at the logon to Windows.
  - **Not your default distribution**: `wsl` without `-d` opens the default distribution of WSL, and this one would open as root. WSL makes a new distribution the default when it has none, and the first one that is left when you remove the default. So after the setup, and at the start of each window, Devspaces reads the WSL distributions of your Windows user from the registry (as below), and while its distribution is the default, it makes your first other installed distribution the default (`wsl --set-default`; not one of Docker Desktop, Rancher Desktop or Podman), or, when WSL refuses all of them, deletes the value `DefaultDistribution` of `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`, so that WSL has no default until your next new distribution. It changes nothing else of WSL. It reads the settings files of Docker Desktop (`%APPDATA%\Docker\settings-store.json` and `settings.json`) only to warn when the WSL integration of Docker Desktop is on for `devspaces`; it never changes them.
  - **Its setup** (**Set Up Docker for Devspaces**, see [architecture.md](architecture.md#the-wsl-distribution-of-devspaces)): Devspaces downloads the `.wsl` file of the image of its VM from `ghcr.io/nimblescape/devspaces-vm` over HTTPS, without a login (the anonymous token of the registry; `ghcr.io` redirects the download to the storage of GitHub). The file is kept only when it has the SHA-256 and the size that the code of Devspaces pins; the pin is the trust anchor, so a redirect of the download may lead to another HTTPS host. The image is built from the recipe in the repository of Devspaces (`vm/recipe.sh`) with the packages of Debian and of Docker, which apt checks with their keys at the build. `wsl --install --from-file` registers the file for your Windows user, with its virtual disk in `%LOCALAPPDATA%\nimblescape\devspaces\wsl`. The image brings systemd and Docker Engine, so no script installs packages at the setup. Nothing runs before the download, apart from the checks of WSL (`wsl.exe --version`, `--status`, `--list`), and, when a distribution `devspaces` exists or `wsl.exe --list` fails, the read of the WSL distributions of your Windows user from the registry (`reg.exe export` of `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss` into a temporary file, removed after the read). Files in the folder of the virtual disk that no distribution of the registry uses, the disk of a setup that did not end, are removed before a new registration; when a distribution uses them, or when neither the registry nor the list of WSL tells, or when the registry does not tell the folder of a distribution, nothing is removed, and the new distribution gets another empty folder there.
  - **Settings of the distribution, not a wall**: its `/etc/wsl.conf` mounts no drive of Windows at the start (`[automount] enabled=false`) and turns off the start of Windows programs (`[interop] enabled=false`), so that Docker and your devspaces do not see your Windows files by default. These settings are no security boundary: root in the distribution can mount the drives of Windows again (`mount -t drvfs`) and then read and change the files of your Windows user. A program that can use the Docker engine there, for example a container with the Docker socket, can become root in the distribution, and so can a container that breaks out. So use the distribution only for images and devspaces that you would also run as your Windows user. It also shares the kernel, the memory and the network of the WSL virtual machine with your other distributions.
  - **Upgrade of its packages**: the VM upgrades its packages itself, as the VM of Lima does (see [The image of the VM](architecture.md#the-image-of-the-vm)): a service of systemd in the distribution runs `apt-get upgrade` about once a day while it runs. The packages come from the package sources of the image: Debian, and the package repository of Docker (`download.docker.com`); apt checks them with the keys of these sources. Devspaces itself runs no upgrade from Windows.
  - **Its removal** (**Remove the WSL Distribution of Devspaces…**) runs `wsl --unregister devspaces` after a warning, and only for the distribution that Devspaces set up: the registry of your Windows user must name the folder of Devspaces as the folder of its virtual disk (when the registry cannot be read, Devspaces removes nothing and says so). A distribution with the name `devspaces` that you made, with its disk in another folder, is never changed or removed.
- Devspaces reaches another computer only through its own list of hosts (`remote-docker.json`, see [Remote Docker host](guide.md#remote-docker-host)). A Docker context or `DOCKER_HOST` of your computer is not used, also when it points to another computer; **Use a Remote Docker Host…** lists the SSH hosts of your Docker contexts, so that you can add one to the list.
- The name of a worker container carries the name of its window (see [architecture.md](architecture.md#the-worker-and-the-helper-channel)), on every engine that the window uses: in the window of a devspace, on the engine of the devspace, the name of the devspace with the owner and the name of its repository; otherwise, the name of its workspace file or of its first folder, also of a folder on your computer. Everyone who can use the engine sees it, for example with `docker ps`.
- **A shared engine is for a group that trusts each other.** Root and every member of the group `docker` on the engine can reach every container and every volume on it, including the token in the memory of another person's running devspace. The account separation of Devspaces does not protect against them. For people who must not see each other's work, each person needs an engine of their own, for example in a virtual machine.

## Known limits

- The Dockerfile and the Features are not checked: they run as trusted code, like the rest of the repository. A Dockerfile can build from or copy out of the local images of other devspaces (`FROM`, `COPY --from`, `RUN --mount`), and choose a BuildKit frontend (`# syntax`). An `ONBUILD` instruction of a base image runs unchecked in the build.
- All devspaces of an engine share its images and build cache, also across GitHub accounts. Do not open repositories that you do not trust on an engine where the devspaces of other accounts hold data that you need to protect.
- Devspaces whose builds have the same inputs use one image, also across GitHub accounts ([R-DS-010](requirements.md#r-ds-010)). Such an image holds only what its inputs build: the image of the configuration (or the images of the `FROM` lines of its Dockerfile), the Features, the label of the configuration, and for a Dockerfile the files of its build context that the Dockerfile copies. The configuration has only Features of a registry, each named without a digest, whose digest the registry gave to the account of the open in this open (so a devspace gets no Feature of its configuration that its account cannot read). An image built from a Dockerfile is shared only between devspaces whose build contexts are identical (the same hash of all names, types, modes, file contents and link targets), so a devspace gets no file of another repository that its own repository does not hold. The hash is read as the owner of the repository; the build reads a copy of the build context that the worker makes and checks against the hash of the key, so a change in the working copy after the key was computed does not go into the shared image. A Dockerfile that mounts a secret or an SSH agent, copies from an image, adds a file from the network, or names another frontend gives no shared image, because each account has its own secrets and the key cannot name what such a build reads. A cache mount (`RUN --mount=type=cache`) is not part of the key: it can carry files of an earlier build on the same engine into the image, as for any build on a shared engine. Devspaces takes an image of the same inputs by its label `nimblescape.devspaces.image-key` only when the image has the tag of a devspace image (or of a prepared devspace image), none of the labels of a devspace, and a dev container that Devspaces created from it carries a build record with the same key, or the background prepare that built the image recorded it for the key. That record is a file in the lock folder of the Monitor's volume (0700, which no dev container mounts); the prepare writes it only for an image that it built itself from inputs whose key it computed, or for an image for which such a dev container vouches already. A shared image is built only from the inputs of its key: the copy of the configuration that Devspaces read, and the lockfile text that it read, which the build must find unchanged in the repository. So a change in the working copy after the key was computed, for example by a program in a running dev container, does not go into an image that other devspaces take by that key. The label alone is not enough, because the Dockerfile of any repository can write it into the image that it builds. A person who can use the engine can make such an image and container (see the item about a shared engine above). The Features that a Feature depends on (`dependsOn`) are not part of the inputs, and the registry is not asked for them: two devspaces can share an image that has an older version of such a Feature than a new build would install, or such a Feature from a registry that the account of the second devspace cannot read. The Monitor merges a devspace image that was built for one devspace with a shared image only when both are really identical (the same layers and the same settings, apart from the labels of Devspaces), so the devspace gets no other content than it had; it removes only a stopped dev container of that devspace, without force, under the lock of the devspace, and never a container of another devspace or one without the label of its devspace ID. Its merge record (in the same lock folder) holds the build record that the devspace image carried, for the new tag on the shared image; the open takes it only when it names that tag, that image, its key, and the owner of the devspace.
- Every container reaches the ports on `localhost` of the host through `host.docker.internal` (Docker Desktop), also the ports that VS Code forwards for other devspaces. Ports on `127.0.0.1` are protected against the network, not against other containers.
- The kernel is shared. A container is not a strong security boundary.
- The channels of VS Code and the Dev Containers extension stay open in every container. Git in the devspace does not use them, but a program that looks for them can.
- The checks allow `--network host`, `SYS_PTRACE`, and `seccomp=unconfined`. With `--network host`, a server in the container that listens on all addresses can be reached from your network, and on Linux with Docker Engine the container can also reach local programs through their abstract Unix sockets (for example the X11 display and D-Bus).
- When the default runtime of Docker is `nvidia`, the variable `NVIDIA_VISIBLE_DEVICES` gives a container the GPUs. It is not refused.
- An `ENV` of an image, or an environment file of the repository, can set variables that the checks refuse in the configuration, for example `GH_TOKEN`.
- An image or a program in the container can change the settings of VS Code in the container, for example to forward ports on all addresses.
- A named volume without labels of another program (for example one made with `docker volume create`) can be mounted by any configuration that knows its name.
- For a Docker Compose build with Features, the user that the Dev Container CLI writes into its compose file is not checked.
- A symbolic link of the repository used as the build context of a single container is not resolved.
- With the checks off, a configuration can join the network of another container, use the volumes of other containers, and use the Docker socket, which controls every devspace and its token.

## Hardening your computer

The Dev Containers extension and VS Code keep some channels from the container to your computer open. Most of them cannot be switched off by a setting, and a firewall does not help: inside the container they are Unix sockets, and between the container and your computer most of them travel inside the connection of the window. What you can do is keep things of value away from the end of each channel on your computer, and have your computer ask before it gives something out.

**Git configuration, Git and Docker credentials, and the GitHub CLI.** Devspaces switches these off for its own containers. To make this the default for your other dev containers too, put this into your user `settings.json`:

```json
"dev.containers.copyGitConfig": false,
"remote.containers.copyGitConfig": false,
"dev.containers.gitCredentialHelperConfigLocation": "none",
"dev.containers.dockerCredentialHelper": false,
"dev.containers.githubCLILoginWithToken": false
```

The socket that answers credential requests stays open, and a program in the container that looks for it can still ask. On macOS, the Git credential helper `osxkeychain` gives out the passwords it stored without asking; on Windows and Linux, the usual credential helpers do too. On macOS you can make it ask: for the items that matter, open Keychain Access, select **Confirm before allowing access** in the item's **Access Control**, and remove `git-credential-osxkeychain` from **Always allow access by these applications**. Then answer each prompt with **Allow** or **Deny**, not **Always Allow**. When Git stores the password anew, repeat these steps.

**SSH agent.** This is the biggest exposure. The Dev Containers extension forwards your SSH agent into every container when one runs as VS Code starts, and no setting turns this off ([microsoft/vscode-remote-release#11413](https://github.com/microsoft/vscode-remote-release/issues/11413)).

- On Linux, start VS Code without an agent: quit VS Code, then start it with `env -u SSH_AUTH_SOCK code`. This affects every window.
- On macOS, VS Code always gets the agent of your login. Keep that agent empty (`ssh-add -D`), and do not use `AddKeysToAgent` or `UseKeychain` in `~/.ssh/config`, or `ssh-add --apple-load-keychain`. Set another agent (for example 1Password) with `IdentityAgent` in `~/.ssh/config`, not by exporting `SSH_AUTH_SOCK` in a shell startup file.
- On Windows, the agent is the service **OpenSSH Authentication Agent**, which keeps its keys across restarts. Keep it empty with `ssh-add -D`, or stop it while you do not need it (`Stop-Service ssh-agent` and `Set-Service ssh-agent -StartupType Manual` in an administrator PowerShell).
- Or have the agent ask (not with the Windows OpenSSH agent): `ssh-add -c` loads a key that needs your confirmation at each use (it needs an `ssh-askpass` program), and `ssh-add -t 1h` loads it for a short time. 1Password and Secretive can ask too; make sure they ask at each use.

**GPG agent.** It is forwarded when the container has `gpg` and your computer runs an agent. Use short cache times in `gpg-agent.conf` (for example `default-cache-ttl 60` and `max-cache-ttl 600`) and add `no-allow-external-cache`. On macOS, pinentry-mac of GPG Suite gives out a passphrase saved in Keychain without asking: switch saving off with `defaults write org.gpgtools.common DisableKeychain -bool yes`, then delete the saved passphrases (`security delete-generic-password -s GnuPG`, repeated until it finds none). Do not keep a key unlocked while a container that you do not trust is open.

**WSL and Wayland.** `"dev.containers.forwardWSLServices": false` stops forwarding the SSH and GPG agents of WSL (not the agent of your computer). `"dev.containers.mountWaylandSocket": false` stops mounting your Wayland display into the containers that the Dev Containers extension creates; Devspaces creates its containers without this mount.

**X11 display.** When `DISPLAY` is set for VS Code, the Dev Containers extension forwards your X11 display into the container, and a program there can see and type into the windows of that display. No setting turns this off ([microsoft/vscode-remote-release#8031](https://github.com/microsoft/vscode-remote-release/issues/8031)). On macOS, uninstall XQuartz if you do not need it, then log out and in. On Linux in a Wayland session, start VS Code with `env -u DISPLAY code --ozone-platform=wayland`. On an X11 desktop, only a separate user account or a virtual machine helps.

**Ports, browser, and clipboard.** With `"remote.autoForwardPorts": false` and `"remote.localPortHost": "localhost"` (the default) in your user settings, VS Code forwards fewer ports on its own, and only on localhost. No setting limits the opening of URLs; if this worries you, make a separate browser profile your default browser. No setting limits the clipboard either: do not copy secrets while a container that you do not trust is open.

**Everything else.** The only real boundary is a separate user account on your computer, or a virtual machine, for VS Code and Docker. On Linux, that account must not be in the group `docker`, which gives root rights on the computer and access to the containers of all users. Devspaces does not need that group there: it runs the devspaces of the account in the Lima VM of that account, which needs only the group `kvm`. With Docker Desktop, Enhanced Container Isolation (Business subscription) also hardens the container side.

## Stored data

- The repository lists (one per GitHub account) and the registry of devspaces in the global storage of the extension hold metadata only: repository names, URLs, dates, volume and image names, image digests, branch names, numbers of changes, and the user ID and login of the account of each devspace.
- The Docker CLI of Devspaces in `docker-cli/<version>/` of the global storage of the extension, only the program `docker` (`docker.exe` on Windows); Devspaces removes the folders of older versions when it downloads a new one.
- On Windows, after **Set Up Docker for Devspaces**: the WSL distribution `devspaces` with its virtual disk in `%LOCALAPPDATA%\nimblescape\devspaces\wsl\disk` (outside of the global storage of the extension, which is in the roaming profile). It holds your devspaces there, their images and their volumes, and in the memory of a running dev container its GitHub token, as any Docker engine does. The download of the `.wsl` file is in `download` next to it only until the distribution is registered (when Windows cannot start the VM of WSL yet, it stays there for the next setup). **Remove the WSL Distribution of Devspaces…** deletes the distribution and this folder; uninstalling the extension does not.
- On Windows, with the WSL distribution of Devspaces: the definition of its scheduled task that Task Scheduler took last, `%LOCALAPPDATA%\nimblescape\devspaces\task\task.xml`, and the log of the task in the distribution, `/var/log/devspaces-task.log`. They hold no secret.
- On macOS and Linux, with the VM of Devspaces: the folder of its scheduled task, `~/.nimblescape/devspaces/task`, with the program, its settings (`task.json`: the schedule, the time zone, and the paths of Lima and of the VM), the time of its last start, and its log; and the definition of the task (see **When.** above). They hold no secret.
- The IDs of the GitHub accounts that Devspaces offered once with its notification (see [Accounts](#accounts)), in the state that VS Code keeps for the extension on this computer.
- `computer.id` in the global storage of the extension: a random ID of this installation, not tied to you or to your GitHub account. The heartbeat records and the lists of images in use in the volume of the Monitor, and the label of a Monitor that keeps running, contain it, so that the Monitor can distinguish the computers that share an engine.
- The volume of the Monitor on each engine holds heartbeat records, locks, the image references in use, registry answers, the record of the last check of the helper image, and the extension lists of recent opens. It holds no secret, and no dev container mounts it.
- Devspaces collects no telemetry.
