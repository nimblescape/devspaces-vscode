# Requirements

This document lists what nimblescape Devspaces 2 must do. It is the normative text: the [README](../README.md), the [user guide](guide.md), [security.md](security.md), [architecture.md](architecture.md) and [remote-connection.md](remote-connection.md) describe how Devspaces does it today. Each requirement has an ID as its heading, so that code, tests, pull requests and the plan can link to it, for example [`R-ENG-002`](#r-eng-002). The plan of Devspaces is kept outside the repository and names these IDs for each open step.

**Contents:** [General](#general) · [Repositories and devspaces](#repositories-and-devspaces) · [Accounts](#accounts) · [Links](#links) · [Docker engines](#docker-engines) · [The VM of Devspaces](#the-vm-of-devspaces) · [Security](#security) · [Devspaces images](#devspaces-images)

## General

### R-GEN-001

**One click to code.** Devspaces opens a GitHub repository in its own dev container, a devspace, and connects the VS Code window to it. **Start** clones the repository into a Docker volume, builds the image, creates the container and connects the window. Git on the computer of the user is not needed.

### R-GEN-002

**No setup and administrator rights only once.** A student installs only VS Code, and VS Code installs Devspaces and the Dev Containers extension. Devspaces brings everything else that it needs, or sets it up without administrator rights and with as few questions as possible: the Docker CLI ([R-ENG-004](#r-eng-004)) and the VM of Devspaces ([R-VM-001](#r-vm-001)) without a question, and the SSH login ([R-ENG-003](#r-eng-003)) after one confirmation. The same strategy holds on every platform: administrator rights are needed once, for the installation of WSL on Windows and for the installation of QEMU with the access to `/dev/kvm` on Linux, each with one administrator prompt of the system; macOS needs none.

### R-GEN-003

**Platforms.** Devspaces runs in VS Code 1.125 or later (the Microsoft build) on Windows, also Windows Home, on macOS and on Linux, with accounts on github.com. GitHub Enterprise Server and GHE.com are not supported. It works with Docker Engine in its own VM on every platform ([R-VM-001](#r-vm-001)) and with Docker Engine on another computer over SSH ([R-ENG-002](#r-eng-002)), never with the Docker of the computer ([R-ENG-001](#r-eng-001)). Podman is not supported.

### R-GEN-004

**Say what it does.** The top of the README, which is also the page of the extension on the Visual Studio Marketplace, names each behavior of Devspaces on the computer of the user and links to [security.md](security.md): the GitHub sign-in and its scopes, when Devspaces works, Docker and the Dev Containers CLI, the registry logins, the installation of Docker after a confirmation, the SSH key, the VM of Devspaces (WSL 2 or Lima, with the administrator prompt for QEMU on Linux) and its scheduled task, the background container, the Docker context of [R-ENG-007](#r-eng-007) when its setting is on, the downloads and the network connections. A pull request that adds or changes such a behavior changes this list too.

### R-GEN-005

**Release.** The publisher is `nimblescape`, the extension ID is `nimblescape.nimblescape-devspaces-2`, and the display name is "nimblescape Devspaces 2": the display name carries the same number as the ID. A release follows the [release rules](../CONTRIBUTING.md#release-rules) and [Naming](../CONTRIBUTING.md#naming). Nobody publishes a version, creates a version tag or creates a GitHub release until Hannes asks for that release in his own words, and a release dry run needs his yes too. The ID stays. The display name changes only after the Marketplace team approved the new name in writing, and nobody tries a name by publishing it. The display name of the publisher does not change, and `contributes.configuration.title` stays set in `package.json`, so that the title of the settings does not change with the display name.

### R-GEN-006

**Development rules.**

- TypeScript 6.0.3, exact, and ESLint with the shared `eslint.config.mjs`; `npm run lint` runs in CI after the type check. These are the same in every nimblescape extension, and a move to another TypeScript version is one decision for all extensions together.
- The Node.js version is only in `.node-version`, on the major version of the Node.js of VS Code.
- CI builds and tests every change of the code on Linux, Windows and macOS. A change of documents only (`docs/` and Markdown files) runs no CI.
- Every pull request is reviewed in rounds until a round finds nothing serious, and is merged with a squash merge when CI passes. Nobody force-pushes, and nobody removes the work of others.
- The npm scripts `install-local` and `uninstall-local` install and remove the packaged extension in the local VS Code, as in every nimblescape extension.

### R-GEN-007

**Documents.** The documents use plain English for readers whose first language is not English: short sentences, no slang, no metaphors and no analogies. Every reference to a file, a line, an issue or a pull request is a link. The documents describe the code on `main`, and a pull request that changes a behavior changes the documents in the same pull request.

## Repositories and devspaces

### R-DS-001

**The list.** The view lists the repositories of the GitHub accounts of Devspaces ([R-ACC-001](#r-acc-001)) that have a Dev Container configuration (`.devcontainer/devcontainer.json`, `.devcontainer.json`, or `.devcontainer/<folder>/devcontainer.json`), grouped by owner. The settings `devspaces.owners` and `devspaces.repositoryGroups` limit and group the list. A row whose devspace does not run (Stopped, No container, Files missing) and a repository without a devspace show their name, their description and their icon in gray, and so do an owner, a group and a repository with several sources while no row below them has a running devspace; the first row, the row Sign in, the hints and the warning icon of Files missing keep their colors. A row counts as running while its devspace is Connected, Connected · other window, Running or Updating, while another container of the devspace runs, and while its state is not known. The gray is the theme color `devspaces.inactiveForeground`, which the user can change. Each window reads the list when it opens and then every hour by default; a refresh reads only the repositories that changed.

**Work that is not on GitHub yet.** A row whose devspace holds work that is not on GitHub yet shows it in every state: uncommitted files, unpushed commits and stashes as numbers in its description (for example `Running · 1 uncommitted · 3 unpushed`), the badge `↑` at its right edge, and a tooltip line that names each number. Each owner, group and repository with several sources above such a row shows the same badge, also while it is closed. A commit is unpushed when no remote-tracking branch contains it, also on a branch without an upstream; this is the rule of the check before **Delete**, and it uses the remote-tracking branches of the last fetch in the devspace. While the dev container runs, the numbers are the ones that the last refresh of the states read from it (when the view is shown, when the window gets the focus (at most every 15 seconds), and after an action; never in the background, and the VM is never started for it). While the dev container does not run, the numbers are the ones recorded at its last stop, and the tooltip says when they were counted. A devspace whose state is unknown or whose files are missing shows no numbers. VS Code shows the badge while `explorer.decorations.badges` is on (the default); a badge holds at most 2 characters, so it carries no number.

### R-DS-002

**Sources and the default image.** With `devspaces.defaultImage` set, every repository can start from that image, also a repository without a Dev Container configuration. Each source of a repository (each configuration, and the default image) is a devspace of its own, with its own row under the repository, and all sources can run at the same time. `devspaces.startWithDefaultImage` decides whether the default image is the first or the last source.

### R-DS-003

**Fast starts and safe updates.** On each Docker engine, the Monitor container `devspaces-monitor` keeps these up to date in its background run, on the schedule `devspaces.cacheUpdateSchedule` (default every day at 06:07): the images of the devspaces, the next image of each devspace (built in advance), the VS Code Server, the extensions and their dependencies, and the helper image of Devspaces (`devspaces-worker`); and it removes what no container uses ([R-DS-007](#r-ds-007)). The record of the check of the helper image is kept on the engine, and a window checks the helper image only when the Monitor has not done it, so that an open does not rebuild it. At the end of each run, the Monitor keeps a short report of the run on the engine, the last 7 runs: when it ran, whether it reached the network, and what it pulled, built, downloaded, linked, prepared and removed, and what failed, each with its count and the names of the first ones; runs in a row that did not reach the network share one report; the details stay in its log. Devspaces asks before it updates a devspace to a newer image (`devspaces.updateContainer`), and the files in the workspace are kept. The schedule allows at least 60 minutes between two runs, as a cron expression or as an interval of 60 to 1440 minutes. One check in the code serves the setting, the Monitor and the scheduled task of [R-VM-005](#r-vm-005), so that they cannot differ; an invalid value is reported in the log, and the default is used. On the VM of Devspaces and on the Docker of the computer, the Monitor ends 5 minutes after the last devspace there stopped, but never during its background run or while a retry of that run waits (up to the retry after 30 minutes), and the scheduled task starts it at the times of the schedule. On a remote host, the Monitor runs permanently and ends itself after 30 days without the use of a devspace there; with `devspaces.stopMonitorWhenIdle` (remote hosts only, default off) it ends when idle there too. Devspaces asks no question about the Monitor.

### R-DS-004

**Stops by itself.** A devspace stops 5 minutes after its last window closed, or after `devspaces.stopAfterMinutes` (default 10) without a sign of any window, unless it is kept running: **Keep Running When Closed**, **Close and Keep Running**, or `devspaces.stopOnClose` off.

### R-DS-005

**Back where you left off.** When VS Code restores the window of a devspace, Devspaces opens that devspace. When VS Code starts with an empty window, Devspaces opens a devspace again only when the window that was closed last was connected to it and the user did not stop it.

### R-DS-006

**Dropped: no update of VS Code before a start.** Devspaces does not update VS Code before a devspace starts, because VS Code has no stable API for its updates (only internal commands of its workbench). VS Code installs a waiting update itself, at its next restart. This ID is not used again.

### R-DS-007

**Clean engines.** The Monitor of each engine ([R-DS-003](#r-ds-003)) removes the objects of Devspaces that no container uses, in each background run, right after the check of the helper image: the earlier builds of the helper image (images of `devspaces-worker` without a tag), the helper tags `devspaces-worker:<hash>` that no running container used for 7 days (never the helper tag of the Monitor itself), the tags `devspaces-monitor:<hash>` whose helper tag is not on the same image, the older versions of the build image `devspaces-buildx`, the older base images of the helper image (only when no other image is built on them, no devspace uses them, and they have at most one tag), the stopped helper containers that are older than 10 minutes, and on the VM of Devspaces the build cache that no build used for 7 days. It never removes a devspace container, a volume or a network, never removes with force, and never removes an image that a container uses, also a stopped one. The Monitor is the only part of Devspaces that removes these images; the windows do not remove them. When a window opens its channel to an engine, it still removes the stopped helper containers that are older than 10 minutes, so that a Delete finds the volumes free.

### R-DS-008

**Workers on the current helper image.** After the helper image of an engine was built again (by its Monitor, or by a window of any computer), the worker of each window there moves to the new build, so that no worker keeps the earlier build for as long as its window is open ([R-DS-007](#r-ds-007) removes it once no container uses it). The answer of a heartbeat says when the worker runs from an earlier build of its helper tag. The window then starts a worker from the current build beside it, as work in the background: the helper image is only checked, never built, a login asks nothing, and on a remote engine (also the VM of Devspaces) the worker starts on a new connection of the relay. The operations from then on go to the new worker, and the earlier worker is closed once no operation runs on it. When the new worker cannot be started, the earlier worker stays, and the window tries again after one hour. The earlier connection of the relay keeps the Docker connections that run on it (for example the connection of the window of a devspace to its container) until they end; its container keeps the earlier build until then.

### R-DS-009

**The Monitor on the current helper image.** After the helper image of an engine was built again ([R-DS-003](#r-ds-003), or by a window), the Monitor moves to the new build by itself, at a time when nothing runs in it: no part of its background run, no automatic stop of a devspace, and no command of a window. It looks at most once a minute. It creates its successor `devspaces-monitor` from the new build, with the same script, settings and volumes, waits until the successor has started, and then ends; the successor removes the container of the earlier Monitor and, when no other container uses it, the earlier build. A failure keeps the running Monitor, and it tries again after one hour. A Monitor that is not running (it ended when idle) and was created from an earlier build is replaced by the next open of a window, which creates it from the current build. A window never creates the Monitor from an earlier build. The successor counts as the same Monitor: its start is no use of the engine for the end after 30 days without use ([R-DS-003](#r-ds-003)).

### R-DS-010

**One image for identical devspaces.** Devspaces whose builds have the same inputs use one devspace image, not one identical image each. This holds for a configuration that names an image (also the default image of [R-DS-002](#r-ds-002)) or a Dockerfile, while the host access checks are on. The inputs are the configuration as written and with its variables resolved (without `name`, `workspaceFolder`, `workspaceMount`, `runArgs`, `appPort` and `initializeCommand`, which are not part of the image), the image by the ID of the local image after the download, the Features with the digests that the registry gave in this open, the lockfile next to the configuration, and the version of the Dev Container CLI. For a Dockerfile, the inputs also hold its text, its path in the build context, the images of its `FROM` lines by the IDs of the local images, and the hash of the whole build context: the name, the type and the mode of each file, folder and link, the size and the content of each file, and the target of each link (not owners and times). The first build labels its image only with the hash of these inputs, the image key, and with no label of a devspace. A later build of another devspace with the same key adds its own tag to that image instead of a build, but only when a dev container that Devspaces created from the image has a build record with the same key: the label of the key alone can come from the Dockerfile of another repository. Each devspace keeps its own tag `<devspace>:<build number>`, and its dev container carries the labels and the build record of the devspace, with the key. A rebuild that the user asks for (**Rebuild**) always builds; a later build takes the newest image of its key. A Docker Compose configuration, an image that was built for one devspace (it carries the labels of that devspace), a Feature that is not in a registry, that names a digest, or whose digest the registry did not give in this open (the answer shows that the account can read the Feature), and a lockfile that cannot be read give an image of the devspace alone, as before. For a Dockerfile, also a build with `build.options` or `build.cacheFrom`, a variable that is not resolved, a build context outside of the repository or one that cannot be hashed (more than 10,000 entries or 64 MiB of files, an entry that is no file, folder or link, a setuid or setgid bit, or a change while it is read), and a Dockerfile that reads something that the key cannot name give an image of the devspace alone: a `FROM` with a flag or with an image that is not known, an image in `COPY --from`, `ADD --from` or `RUN --mount`, a file from the network with `ADD`, a secret or an SSH agent in `RUN --mount`, or another frontend than the Dockerfile frontend of Docker in the `syntax` directive. A devspace that goes to another image removes only its own tag, so the image stays while another devspace has a tag on it. The background prepare of the Monitor follows the same rule: the prepare of the first devspace builds the newer image as a shared image and records it in the volume of the Monitor, which no dev container mounts; the prepare of another devspace with the same key adds its own prepared tag to that image instead of a build, and each open then takes it by the key of the images as the open pulled them, without a new download or a build. The record of the prepare vouches for the image like a dev container does, because only Devspaces writes it. A shared image is built only from the inputs of its key: the configuration as Devspaces read it, the lockfile as Devspaces read it, which the build must find unchanged, and for a Dockerfile a copy of the build context that the build makes and checks against the hash of the key (a change after the key was computed builds an image of the devspace alone). A devspace image that was built for one devspace (before this rule, or without a key) and that is really identical to a shared image is merged by the Monitor when it is idle: the same layers and the same settings, apart from the labels of Devspaces. When all dev containers of that devspace are stopped and no operation holds the lock of the devspace, the Monitor removes the stopped dev container and the duplicate, gives the shared image the tag of the next build number of the devspace, and writes the build record of the devspace for that tag into its volume, because the shared image carries no build record. The next Start takes that record and creates the dev container from the shared image without a build, as after an update: the files of the workspace stay, changes outside it are lost, and the lifecycle commands run again. A running devspace is never touched; it is merged at a pass after it stopped. A devspace of Docker Compose is never merged.

### R-DS-011

**The newest version runs the Monitor.** Several computers with different versions of Devspaces can use one engine; the Monitor there runs the newest version. Each window stores its script (the script of the Monitor is the script of its worker) with its version of Devspaces and its helper tag in the volume of the Monitor at each open. When a window of a newer version opened, the running Monitor moves to that script by itself, at a time when nothing runs in it, as in [R-DS-009](#r-ds-009): it creates its successor with the newer script from the helper image of that version (once that image is on the engine), and then ends. A window never replaces a Monitor of a newer version with its own: it keeps a running one and starts a stopped one again. A window also keeps a running Monitor of an earlier version until it has moved, and works with it meanwhile. The commands of the Monitor take the input of the windows of earlier and later versions: a key of the input that the Monitor does not know is left out, and a new version of Devspaces adds only keys that a Monitor can do without. A Monitor of an extension before this rule (without the label of its version) is replaced as before.

## Accounts

### R-ACC-001

**Several GitHub accounts.** Devspaces uses every GitHub account of VS Code that the user allowed for Devspaces and that has a session with the scopes `repo` and `read:org`, and shows one list for all of them. It opens no sign-in dialog of VS Code without a click of the user, and each call to the sign-in names the account. An account that VS Code has and that Devspaces does not use yet is offered once; after that, only **Add GitHub Account…** offers it.

### R-ACC-002

**The account of a Start.** An existing devspace opens with the account that owns it; when two accounts have a devspace of the same source, the one used last opens. For a new devspace, only the accounts that can access the repository count, and the first of these rules that tells them apart decides: the highest permission (admin, maintain, write, triage, read, then unknown); the account whose login owns the repository; an account that is a member of the organization that owns the repository; the login that comes first in alphabetical order. **Start with Account…** creates a devspace for another account that can access the repository, and the existing devspace stays as it is. The tooltip of a row names the account, and the row of a devspace shows its login when Devspaces uses more than one account.

### R-ACC-003

**One account per devspace.** A devspace belongs to the account that created it. Its container holds only the token of that account, so Git and the GitHub CLI work there as that account. The token leaves the containers of an account when that account leaves Devspaces, and only then. **Remove Devspaces from This Docker Engine…** (the "…" menu of the repository view, the Command Palette, and the menu of each host row of the view "Docker Hosts", [R-ENG-008](#r-eng-008)) names the accounts and removes the devspaces of all accounts of Devspaces on that engine.

## Links

### R-LINK-001

**Open from a link.** A link `vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name` opens the devspace of that repository; when Devspaces is not installed, VS Code installs it first. Before a link creates a new devspace, Devspaces asks. For a repository of an account of Devspaces or of one of their organizations, **Always Open** in that question turns it off (setting `devspaces.confirmOpenFromLink`). For other owners, Devspaces always asks. When the user has devspaces of several sources of the repository, the link opens the one used last on the current Docker engine. The devspace opens in the window that VS Code gives the link only when that window is empty; otherwise it opens in a new window.

### R-LINK-002

**Course links.** A link `vscode://nimblescape.nimblescape-devspaces-2/course?repository=owner/name-<username>` opens the own repository of a student of a course. When the user is not signed in, Devspaces asks for the GitHub sign-in first. It puts the login of each account of Devspaces in place of `<username>` and opens the repository that exists with the account of that login, not with the account of the highest permission. When the repositories of two accounts exist, Devspaces asks which one to open. `<username>` may stand anywhere in the name, also more than once; a course link without it gets `-<username>` at the end of the name. For a student who is not a member of the organization of the course, the repository belongs to another owner, so Devspaces always asks before it creates the devspace ([R-LINK-001](#r-link-001)).

## Docker engines

### R-ENG-001

**The Docker of the computer.** Devspaces runs its devspaces in its own VM ([R-VM-001](#r-vm-001)) or on another computer ([R-ENG-002](#r-eng-002)), and never uses the Docker of the computer, on every platform: Docker Desktop and Docker Engine stay installed for the own work of the user, and Devspaces does not use or start them; devspaces that an older version made there are not moved. The choice of the Docker host (the first row of the repository view, the only place where the user chooses it, [R-ENG-008](#r-eng-008)) has no entry for the Docker of the computer; it offers the VM of Devspaces, or its setup while the VM does not exist. The view names the VM of Devspaces as the local Docker host, because it runs on the computer. While Devspaces uses its VM and the VM does not exist, for example after its removal outside of Devspaces, the view shows the setup of the VM, as before the first setup, and a link sets the VM up without a question. A computer that cannot run the VM does not meet the precondition of Devspaces, and Devspaces then never uses the Docker of the computer instead, because the devspaces need the isolation of the VM and the same processes on every platform: on a Linux without `/dev/kvm` (no virtualization of the processor), as on a Windows where WSL 2 cannot start its virtual machine ([R-ENG-005](#r-eng-005)), the view says why the computer cannot run devspaces and offers a remote host ([R-ENG-002](#r-eng-002)).

### R-ENG-002

**A remote host over SSH with one login.** Devspaces runs devspaces on Docker Engine on another computer that it reaches over SSH. It keeps its own list of hosts and never changes the current Docker context or `DOCKER_HOST`, so the Docker tools in the terminals of the user keep their target; only the setting of [R-ENG-007](#r-eng-007) creates a Docker context, and never for a remote host. Each window logs in to a host once (after a **Start**, VS Code starts the window again, and it logs in once more): the checks before the connection, the worker, the Docker connections of the Dev Containers extension and the Docker calls of Devspaces use that one login. A build of the helper image in the background waits for that connection and runs through it, without a login of its own. One exception is allowed: when the current helper image is missing on the host, for example at the first use of the host or after an update of Devspaces that changes the helper image, the open of a window builds it with one SSH login of its own before the login of the window, because the connection runs that image. This happens once per host and version of the helper image. The utilization page of a host ([R-ENG-009](#r-eng-009)) reads on the shell of the view "Docker Hosts" ([R-ENG-008](#r-eng-008)) and needs no login of its own while that shell is open. It needs one more login of the host while a connection of the relay holds the login of the window, because the page reads files of the host, which the connection of the relay does not reach; and while the page reads, a window that opens in a flow of the user logs in itself and leaves the shell to the page. The report of a resource ([R-ENG-010](#r-eng-010)) reads on the same shell, or through the connection of the relay while it is open, and needs no login of its own then. The host needs only an SSH server, Docker Engine that the account may use, and `sh`; Devspaces never installs or starts Docker there. A remote host serves one user, or a group whose members trust each other; the separation of students on one shared host is not a requirement now.

### R-ENG-003

**SSH logins without setup.** Devspaces uses the `ssh` of the computer, so the SSH config, `ProxyJump` and existing keys work. The user sets up nothing for Devspaces: no `ControlMaster`, no `MaxStartups` and no SSH agent. In a flow that the user started, each question of the login (an unknown host key with its fingerprint, a password, a passphrase or a code) appears in VS Code; the work in the background asks nothing. Devspaces keeps no answer, and keeps a host key only after the user accepted its fingerprint. After a login with a password, Devspaces offers once to create its own key `~/.ssh/devspaces_ed25519` without a passphrase and to add it to `authorized_keys` on the host. It never writes over another file in `~/.ssh` and never changes the SSH config.

### R-ENG-004

**The Docker CLI of Devspaces.** A computer needs no Docker. The window of a devspace in the VM of Devspaces or on another computer, and the Docker calls of Devspaces there, use a Docker CLI that Devspaces downloads from `download.docker.com` and checks against the size and the SHA-256 that its code pins. A daily workflow proposes a new pin as a pull request. Before a window of a devspace opens, Devspaces compares the Docker API versions of that CLI with those of the engine (`ApiVersion` and `MinAPIVersion`), and when they do not fit, it says so with both versions and what to do. When the download is not possible, the window uses the Docker CLI of the computer and says so.

### R-ENG-005

**Windows: the WSL distribution of Devspaces.** On Windows, the VM of Devspaces ([R-VM-001](#r-vm-001)) is its own WSL 2 distribution `devspaces`, also on a Windows with Docker Desktop ([R-VM-008](#r-vm-008)). The Docker setup of the view and a link ([R-LINK-001](#r-link-001)) check WSL and install WSL 2 first when it is missing, without a question of Devspaces (Windows asks for administrator permission); after the restart of Windows, the first window goes on with the setup, and with the link, by itself. Then Devspaces sets up the distribution, without a question and without administrator rights, from the `.wsl` file of its own image ([R-VM-002](#r-vm-002)) for the architecture of Windows, and uses it as a host through `wsl.exe`, without SSH, with the Docker CLI of Devspaces ([R-ENG-004](#r-eng-004)). The setup shows its progress, also of the download, and says before the download when WSL 2 cannot start its virtual machine (no restart after the installation of WSL, or no virtualization); a download that WSL could not register stays for the next setup. Devspaces starts the distribution again when WSL runs out of time to start it, which happens in a slow virtual machine. A link uses a distribution that Devspaces set up before as it is, and a distribution of an older version is not converted. The distribution is never the default distribution of WSL, and a distribution with that name that the user made is never changed or removed. Devspaces never writes `.wslconfig`, and removes the distribution only after a question.

### R-ENG-006

**The same processes on every engine.** Once a Linux system with Docker Engine is there, Devspaces runs the same processes on every engine: its Lima VM, its WSL distribution ([R-ENG-005](#r-eng-005)), and a remote host over SSH ([R-ENG-002](#r-eng-002)). Only the transport to the engine differs: the SSH of Lima to its VM (with the key that Lima made, as root, without a login of the user), `wsl.exe`, or the SSH login. No engine gets a build, a check or a tool of its own. The management of the VM of Devspaces ([R-VM-001](#r-vm-001)) is the one exception. So the helper image is built in a container on the engine with buildx (BuildKit) from a build image that Devspaces pins by its digest, whatever Docker CLI sends the calls.

### R-ENG-007

**Other Docker tools.** By default, Devspaces creates no Docker context, so the Dev Containers extension, the Container Tools extension and the `docker` command see no container, image or volume of the VM of Devspaces. The setting `devspaces.createDockerContext` (scope `machine`, default off) creates the Docker context `devspaces` for the engine of the VM; it never becomes the current context, and turning the setting off removes it. On macOS and Linux it points to the Docker socket of the Lima VM; on Windows it points to a named pipe of Devspaces and works only while a window of Devspaces is open. A Docker context gives full access, so the guide says to manage devspaces only with Devspaces: a deleted volume deletes unpushed work, and a container that another tool created has no labels and records of Devspaces. The view "Docker Hosts" ([R-ENG-008](#r-eng-008)) shows all objects in the VM and stops, starts and removes them without a Docker context, and the guide names it as the tool for them.

### R-ENG-008

**The view "Docker Hosts".** A view "Docker Hosts" below the repository view lists the Docker hosts of Devspaces: the VM of Devspaces first, also before its setup ([R-VM-010](#r-vm-010)), then each remote host of the list of Devspaces. Other Lima VMs and WSL distributions of the user are never shown. Under each host, it shows all containers, images, volumes and networks of the engine, and its build cache, so that the user also sees the other services of the host and can stop or remove them when the devspaces need more CPU, memory or disk space. In each group the objects of Devspaces come first: those with a label `nimblescape.devspaces.*`, the containers and volumes whose name starts with `devspaces-`, the build image that Devspaces pins, the base images that the build records of the devspaces of this computer name, the base image of the helper image, and the networks of Docker Compose of a devspace. Each of them says its purpose (a devspace with its repository, the Monitor, a worker, a batch helper, the helper image, a shared volume, and so on). A helper image is named by its tag `devspaces-worker:<hash>`, and a helper image without that tag, which a newer build took, is named `devspaces-worker (earlier build, <ID>)`, also while it still has the tag `devspaces-monitor:<hash>` of the Monitor. Every other object says "not of Devspaces", a container of Docker Compose also its service and project. Each row says the size of its object, each network its driver and the number of its containers, and each group the sum of its sizes, from `docker system df -v`, `docker network ls` and `docker image ls` (every tag of each image). The name, the description and the icon of an object that is not of Devspaces are violet, so that the user finds the other services of the host; an object that is not active is dimmed: a dimmed violet when it is not of Devspaces, gray when it is. Active is a container that runs (also paused or restarting), and an image, a volume or a network that a running container uses, read with `docker container inspect` of the running containers (at most 100 per call; the ID of the image, the volumes and the networks of each). The text "not of Devspaces" stays, for users who do not see the colors, and the tooltip says whether the object is active. The colors are theme colors that the user can change (`devspaces.hosts.notDevspacesForeground`, `devspaces.hosts.notDevspacesInactiveForeground`, `devspaces.inactiveForeground`). The row **Build cache** says the number of the records of the build cache of Docker, their size, and the space that their removal frees, as `docker system df` counts them. Devspaces reads a host only when the user opens it in the view or clicks Refresh, never in the background, and never starts the VM for a read: a stopped VM shows a row that starts it. Only the utilization page of a host reads it again and again, while the page is visible ([R-ENG-009](#r-eng-009)), and the report of a resource reads it when it opens or follows a click and at its Refresh ([R-ENG-010](#r-eng-010)). The reads and the actions of the view on a host share one login of the host (one `ssh`, or one `wsl.exe` on Windows), also on the VM of Devspaces, instead of one connection per Docker command, and the utilization page reads on the same login (only **Remove Unused Build Cache…** on a remote host without an open devspace of the window logs in on its own, so that it never runs on another buildx builder of the account there); that login closes 2 minutes after its last use, and while a devspace of the window is open on a remote host, they use its connection. Opening a remote host is a flow that the user started, so a password login may ask there ([R-ENG-003](#r-eng-003)). The objects of a devspace of this computer get the commands of the devspace: Stop, and Delete…, which checks the Git changes first. Every other running container gets **Stop**, and a stopped container that is not of Devspaces gets **Start** (Devspaces starts its own helpers itself). Every other object that does not run gets **Remove…**, after one question that names the objects, also for several selected rows; the question says when an object is not of Devspaces, because another program may need it. Devspaces never removes with force, so Docker keeps an image or a volume that a container uses. Just before it removes an image, Devspaces reads its tags and its containers again: it keeps an image that a container uses or that has a tag that the view did not show, and it never removes a tag that names another image since the read. Devspaces keeps a network that a container uses, also a stopped container, because Docker would remove it and the container could not start again; it reads the containers of the network just before the removal. It never removes the networks that Docker creates itself (`bridge`, `host`, `none`, and those of Docker Swarm). An action on the objects of the VM runs only while the VM runs, because a Docker call would start it. **Remove Unused Build Cache…** on the row of the build cache removes the records that no build uses (`docker builder prune --all`), after one question that says how much space it frees. A check mark shows the Docker host of Devspaces. The user chooses the Docker host of Devspaces only in the first row of the repository view: a click on a host row of the view "Docker Hosts" only opens or closes the row, and the menu of a host row has no command that uses the host, so that a look at the objects of another host never changes the host of the repository view and of **Start**. Only **Set Up** of the VM row, while the VM is not set up, makes the VM the Docker host of Devspaces after the setup, as the setup in the repository view does ([R-VM-010](#r-vm-010)). A click on an object row opens its report ([R-ENG-010](#r-eng-010)). The menu of a host row has **Show Utilization** (also as a button on the row, for the VM once it is set up and for each remote host, [R-ENG-009](#r-eng-009)), **Update All Images Now**, **Remove Devspaces from This Docker Engine…** ([R-ACC-003](#r-acc-003)) and, for a remote host, **Remove from the List**; the **+** in the title of the view adds a remote host.

### R-ENG-009

**The utilization of a Docker host.** **Show Utilization** on a host row of the view "Docker Hosts" ([R-ENG-008](#r-eng-008)) opens a page in the editor, one page per host, that only shows values and changes nothing. It shows the live use of the whole host: the CPU (busy, each CPU, the time that waits for the disk or that the hypervisor takes, the load, and the pressure of the kernel), the memory (used, available, file cache, swap, pressure, and the processes that the kernel ended because the memory ran out), the space of the file systems of the Docker data and, for the VM of Devspaces, the free space on the computer for the disk of the VM, and the running containers with their CPU (100 % is one CPU, as `docker stats` counts it), their memory without the inactive file cache (as `docker stats` counts it), their network, their disk reads and writes, and their processes. The page reads the sizes of the objects of Docker as the view does (`docker system df -v`) by itself, right after the first values of each start (the open, **Resume**, a show after the end of the samples) when the sizes are older than a minute, and then every 10 minutes while it reads (also after a failed read; after a read longer than its time limit, which ends the login of the samples, only after the next open, a new start of the host, or a **Refresh Sizes** that worked), and **Refresh Sizes** reads them at once. It reads every volume and uses the same login as the samples, so the samples can wait while it runs; the header says that it reads the sizes. The read by itself uses only a login of the host that is open (the shared shell, or the connection of the relay of an SSH host): it never asks for a password and never logs in itself, and it never runs on a VM that does not run. Then the page shows the disk use of Docker with what can be freed, the stopped containers, the largest volumes and images, and the networks, and each object and running container with the purpose and the color of the view. The page reads with one fixed shell script, one command on the shared shell of the host for each sample ([R-ENG-008](#r-eng-008)): the script reads only `/proc`, the cgroup files of the containers and the free space of the disks, the page runs only `docker ps` and `docker info` between two samples (the names of the containers and the data folder of Docker), and nothing writes a file or creates a container, an image or a volume on the host. A sample comes every 2 seconds on the VM and every 5 seconds on a remote host, less often when the host needs long for it. The page reads nothing while it is hidden, and its samples end 15 seconds after it is hidden; a show within these 15 seconds goes on with the same samples. It pauses after 2 minutes without the focus of the window and after 30 minutes without a click or a key on the page, and **Resume** goes on. The page never starts the VM of Devspaces and never keeps it running ([R-VM-004](#r-vm-004)): it logs in only to a VM that runs, a stopped VM shows **Start the VM**, the page reads the state of a stopped VM again (which starts nothing) while it is visible and reads its values when the VM runs again, and on Windows the samples end when the idle script of the VM ended, so that WSL can stop the distribution; when the VM started between the check and the login, the page ends its samples at once and shows that the VM went to sleep. On a remote host, the open of the page, **Resume**, **Retry**, **Start the VM** and **Refresh Sizes** are flows of the user, so a password login may ask there ([R-ENG-003](#r-eng-003)); a new start after a hide asks nothing. Each source is optional: without access to Docker on the host, the page shows the values with the short IDs of the containers instead of their names; a kernel without pressure values says so; a host that is not Linux, has no `/proc` or no `sh` says so and is not read again. A sample that fails ends the samples with the reason, and with **Retry** where a new try can help; nothing tries again by itself. On Windows, the page says that the totals include the other WSL distributions and Docker Desktop, because they share one Linux kernel.

### R-ENG-010

**The report of a resource.** A click on an object row of the view "Docker Hosts" ([R-ENG-008](#r-eng-008)), or **Show Report** in its menu, opens the report of that container, image, volume or network as a page in the editor, which only shows values and changes nothing; the focus stays in the view, so that the arrow keys go on to the next row, and `Enter` there opens its report. One page follows the clicks and shows the report of the last click; **Keep Open** keeps a page with its resource, and the next click opens a new page. Every object gets the facts of Docker (its inspect; for a volume also the containers that use it, with the place and the mode of their mount). An object that is not of Devspaces gets only these, and Devspaces never reads its content. Before them, the report of an object of Devspaces shows what it holds with the rule of Devspaces for each item: the store of VS Code (`devspaces-vscode`) each version of the VS Code Server and each extension, and which of them the next cleanup of the Monitor keeps or removes and why; the Monitor and its volume what the Monitor did in its last runs ([R-DS-003](#r-ds-003)), its next background run, its downloads and its other records; the cache of the workers its content. Devspaces reads these shared volumes with one short-lived container of a helper image that is already on the host: it never pulls, has no network, mounts only the volumes that exist and only read-only, and is removed at its end. The page reads when it opens, when it follows a click, and at **Refresh**, never in the background and never while it is hidden; the header says when the content was read. It reads on the login of the view ([R-ENG-008](#r-eng-008)), also through the connection of a devspace of the window that is open on the host, and the read is a flow of the user, so a password login may ask there ([R-ENG-003](#r-eng-003)). The page never starts the VM of Devspaces ([R-VM-004](#r-vm-004)): it reads the state of the VM first, and a stopped VM shows **Start the VM**. A read that fails says why, and the page keeps the content of the read before. The reports of the container and of the volume of the Monitor have **Show Log of the Monitor**, which opens the last 2000 lines of its log as a read-only document.

## The VM of Devspaces

### R-VM-001

**One Linux in a light VM on every platform.** Devspaces runs its devspaces in its own virtual machine: WSL 2 on Windows, also Windows Home ([R-ENG-005](#r-eng-005)), and [Lima](https://lima-vm.io) on macOS (Apple Virtualization) and on Linux (QEMU with KVM). Every VM runs the same image ([R-VM-002](#r-vm-002)) with Docker Engine; only the management of the VM differs: create, start, stop when idle, upgrade, remove, and the command that runs a program in the VM (`wsl.exe`, or `ssh` with the SSH configuration that Lima wrote for the VM). Devspaces downloads a Lima that its code pins by version and SHA-256 into a folder of the user, so macOS needs no administrator rights; on Linux, one administrator prompt installs QEMU and gives the user access to `/dev/kvm` ([R-GEN-002](#r-gen-002)). Devspaces never starts a VM with an emulated processor and never uses the Docker of a Linux without `/dev/kvm` instead: that computer does not meet the precondition, as on Windows ([R-ENG-001](#r-eng-001)). Devspaces creates the VM only for the first devspace, and the devspaces live on the disk of the VM.

### R-VM-002

**The image of the VM.** Devspaces builds one Debian 13 image of its own, as a `.wsl` file for WSL and as a disk for Lima, for amd64 and arm64, from one recipe: systemd, cloud-init, Docker Engine from the packages of Docker (`docker-ce`, `docker-ce-cli` and `containerd.io`), and the scripts of Devspaces. The files differ only in the kernel: WSL always runs the kernel of Microsoft. The files are an OCI package of the nimblescape organization on `ghcr.io`; Devspaces downloads them over HTTPS, without a Docker CLI, and checks the SHA-256 that its code pins. A daily workflow builds and tests the image every day, and pushes it and opens a pull request with the new pins only when the list of its packages changed. `ghcr.io` keeps every version that a published release of Devspaces pins, and the newest 5.

### R-VM-003

**Kernel check.** The kernel features that Docker Engine requires (the list "Generally Necessary" of Docker's `contrib/check-config.sh`) are checked in two places: in the daily workflow of the image, against the configuration of the Debian kernel of the image and against the configuration of the WSL kernel that Microsoft publishes, for amd64 and arm64, where a missing feature stops the pull request; and in the VM, at each start where the kernel version changed since the last check. Only a missing feature shows a message, with the missing features in the log.

### R-VM-004

**Stop when idle.** One idle script in the VM, the same in WSL and in Lima, checks every minute whether a devspace, the Monitor, a worker, a build container or the package upgrade ([R-VM-007](#r-vm-007)) runs, or whether a program is connected to Docker Engine (for example while it downloads an image before the first container), and stops the VM after two checks in a row with nothing running. On Windows, one hidden `wsl.exe` that is not a child of VS Code runs the script, and WSL stops the distribution when the script ends; in Lima, a systemd service runs it and powers the VM off. No other process on the computer keeps the VM running.

### R-VM-005

**Start at the update schedule.** A task of the user (Task Scheduler on Windows, without administrator rights; a launch agent on macOS; a systemd user timer on Linux) starts the VM of Devspaces, when there is one, and then the Monitor ([R-DS-003](#r-ds-003)) at the times of `devspaces.cacheUpdateSchedule`, in the time zone of the computer, and gives the Monitor the current schedule and time zone at each start. The task starts the VM 5 minutes after a time of the schedule. A time that the computer missed because it slept or was off runs once after the wake or the login, also on battery: on macOS and Linux 5 minutes after it, where an agent at login starts the VM only when a time was missed; on Windows 10 minutes after it, the wait of Task Scheduler for a time that was missed, and the task may run on battery and has no time limit. Devspaces never wakes the computer. When the setting changes, Devspaces writes the task again. Apart from this catch-up, nothing starts at login, and Devspaces asks no question about the Monitor; when a window is open at that time, the VM and the Monitor run already, and the task changes nothing.

### R-VM-006

**Memory and CPUs.** The Lima VM gets 4 GiB of memory and 4 CPUs by default, each at most half of the computer, and at least 1 CPU. The settings `devspaces.vmMemoryGiB` and `devspaces.vmCpus` (scope `machine`) change them for the next start of the VM; their description says "macOS and Linux only. On Windows, manage it via WSL.", and Devspaces ignores them on Windows. When the kernel of the VM ends a process because the memory ran out, Devspaces says so and names the memory setting.

### R-VM-007

**Updates.** The VM upgrades its packages itself (`apt-get upgrade`), at each start when the last upgrade that ended well is 20 hours old, and tries a failed one again after 6 hours, without a restart of Docker or of the running devspaces; the idle script waits for it. A new major release of Debian is installed in place by an upgrade script of Devspaces that CI tests: the VM is never replaced, because the devspaces live on its disk. Everything that Devspaces pins in its code (the image, Lima, the Docker CLI, the build image, and the Node.js version of the build) is checked every day by the workflow "Daily checks", which opens a pull request only for a new version; a new pin reaches the users with the next release. WSL and its kernel come from Microsoft.

### R-VM-008

**Windows with Docker Desktop.** WSL runs the distribution of Devspaces and that of Docker Desktop in one VM with one network stack. Devspaces uses its own distribution also on a Windows with Docker Desktop, and never Docker Desktop. A manual test on such a computer ([manual-tests.md](manual-tests.md)) checks that both run side by side, without a clash of ports or Docker sockets.

### R-VM-009

**Tests.** CI tests the VM where the runners of GitHub allow it: on Linux with KVM, the start of the image, the scheduled task with a time in the past, the update of the Monitor and the stop by the idle script after it, and the state, the stop and the removal of the VM of [R-VM-010](#r-vm-010). The runners of Windows have no WSL 2 and those of macOS no nested virtualization, so each step that changes the VM on Windows or macOS has a written list of manual tests ([manual-tests.md](manual-tests.md)).

### R-VM-010

**Manage the VM.** The row of the VM of Devspaces in the view "Docker Hosts" ([R-ENG-008](#r-eng-008)) shows its state (Not set up, Stopped or Running), which Devspaces reads without a start of the VM and without a download, and in its tooltip the memory and the CPUs of the VM (Lima) and the space of its disk on the computer. Its menu has the same commands on every platform: **Set Up** while there is no VM; **Start the VM**, the test of the host, which starts the VM without a change of the Docker host of Devspaces (the VM powers itself off again by [R-VM-004](#r-vm-004)); **Stop the VM…** (`limactl stop`, or `wsl --terminate devspaces`), which asks first while devspaces run there and names them; **Remove the VM…** (`limactl delete`, or `wsl --unregister devspaces`) and **Remove and Set Up the VM Again…**, each after a question, because they delete every devspace in the VM; and **Settings of the VM**, its memory and CPUs ([R-VM-006](#r-vm-006), macOS and Linux). Before a stop or a removal, the connections of the window to the VM end, also the samples of the utilization page of the VM ([R-ENG-009](#r-eng-009)), which reads again only after **Resume**. A Docker call to a VM that does not run, also to read its running devspaces, waits for a command of the user that starts it.

## Security

### R-SEC-001

**Host access checks.** Before a container is created, and again before `up`, Devspaces checks the final configuration and refuses what reaches into the computer or into another devspace (see [Host access checks](security.md#host-access-checks)). The user can turn off the checks of the first list for one repository, only in the user settings; the second list stays refused.

### R-SEC-002

**Token and registry logins.** Devspaces stores no token on the computer, and the GitHub token of the owner account is only in the memory of the container. Devspaces checks and pulls images and Features first without a login. It uses a registry login that Docker stored only when the registry refuses, does not find the image, or limits pulls without a login, only for that one check or pull, and never stores it. For `ghcr.io` without such a login, it uses the GitHub sign-in of the owner account of the devspace with the scope `read:packages`.

### R-SEC-003

**Docker pipes with an allow-list.** The Docker pipe of a window and the Docker pipe of the extension let through only the Docker requests on their allow-list and refuse every other request (see [The request filter](remote-connection.md#the-request-filter)). The allow-list of the extension has, for the view "Docker Hosts" ([R-ENG-008](#r-eng-008)), `POST /containers/<id>/stop` and `POST /containers/<id>/start` for **Stop** and **Start** of a container, `GET /networks`, `GET /networks/<name>` and `DELETE /networks/<name>` for its networks, and `POST /grpc` (a Docker CLI with buildx, as for the build) or `POST /build/prune` (without buildx) for **Remove Unused Build Cache…**; it has no request that creates a network or connects a container to one. The named pipe of the Docker context of [R-ENG-007](#r-eng-007) on Windows has no allow-list, because a Docker context gives full access. Only the user of the computer can open them.

### R-SEC-004

**Quiet and private.** Before the first devspace, Devspaces does no Docker work and creates no VM: it only reads its Docker host. The view "Docker Hosts" ([R-ENG-008](#r-eng-008)) reads a host only when the user opens it or clicks Refresh, and never starts the VM for a read. The utilization page ([R-ENG-009](#r-eng-009)) reads a host only while the page is visible and not paused, never starts or keeps the VM running, and writes nothing on the host. Devspaces collects no telemetry. In Restricted Mode, and for the settings that the guide marks *user only*, only the user settings count.

## Devspaces images

The dev container images of the courses are built in the repositories `majikmate/devcontainer-*` and published on `ghcr.io/majikmate`.

### R-IMG-001

**Releases.** Every image is built by the shared workflow `devcontainer-image.yml` of [devcontainer-core](https://github.com/majikmate/devcontainer-core). A nightly check in UTC releases a new image when an input changed or the newest image has pending Debian updates, and a new image of a lower layer releases the images above it in the same night. `ghcr.io` keeps the newest 5 releases of each image, and workflow runs older than 30 days are deleted.

### R-IMG-002

**Prompt.** The shell prompt in a devspace shows no `user@host`, as in a GitHub Codespace. Devspaces never sets the variable `CODESPACES`.

### R-IMG-003

**nimblescape extensions.** The image of devcontainer-base installs nimblescape PlantUML (in place of the PlantUML extension of jebbs), nimblescape Mindbug and nimblescape Comment Links. When the course extension of nimblescape Markdown is published, the image of devcontainer-classroom-web installs it too.
