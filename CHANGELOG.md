# Change log

Each section lists the changes of one released version. The release workflow
takes the section of a version as the notes of its GitHub release.

## 0.4.2

**The view Docker Hosts:** a new view below the repositories lists the VM of Devspaces first, then each remote host of the list of Devspaces. Open a host to see all its containers, images, volumes and networks, and its build cache. The objects of Devspaces come first in each group (also those of the Monitor, the workers and the helper image, and the shared volumes), each with its purpose; every other object says "not of Devspaces", a container of Docker Compose also its service and project. Each row shows its size, each network its driver and the number of its containers, and each group the sum of its sizes. Devspaces reads a host when you open it or click **Refresh**; while the view is visible, it checks the open hosts every 30 seconds with short lists without sizes and reads a host again when its objects changed. It never starts the VM to read it and never asks for a password for the update. The objects of a devspace of this computer have **Stop** and **Delete…** of the devspace; every other running container has **Stop**, so that you can stop the other services of a host when your devspaces need its CPU and memory, and a stopped container that is not of Devspaces has **Start**. These actions need the setting `devspaces.dockerHostsActions` (see **Settings of the view Docker Hosts** below). Every other object has **Remove…**, after one question, also for several selected rows. Devspaces never removes with force; it keeps a network that a container uses, and the networks of Docker itself. **Remove Unused Build Cache…** on the row of the build cache removes the records that no build uses on that host, never on another buildx builder that your environment names, after one question. A check mark shows the Docker host of Devspaces, which you choose only in the first row of the repository view: a click on a host row only opens or closes it; the menu of a host row has **Update All Images Now** and **Remove Devspaces from This Docker Engine…** for that host, and **Remove from the List** for a remote host. The **+** of the view adds a remote host.

**One login per host for the view Docker Hosts:** the reads and the actions of the view on a host (Stop, Start, Remove…, and Remove Unused Build Cache… on the VM) now share one login of the host, also on the VM of Devspaces, instead of one SSH or `wsl.exe` connection per Docker command. That login closes 2 minutes after its last use; while a devspace of the window is open on a remote host, the view uses its connection.

**The utilization page of a host:** **Show Utilization** on a host row of the view Docker Hosts (the VM of Devspaces once it is set up, and each remote host) opens a page in the editor with the live use of the whole host: its CPU, each CPU, the load and the pressure of the kernel; its memory and swap; the disk of the Docker data, and for the VM the free space on the computer for its disk; and the running containers with their CPU, memory, network, disk reads and writes, and processes, with the names, colors and purposes of the view. The page reads the sizes of the objects with `docker system df -v` by itself after its first values and then every 10 minutes, only on the login that it already has (it never asks for a password for it and never starts the VM for it), and **Refresh Sizes** reads them at once; it shows the disk use of Docker with what can be freed, the stopped containers, and the largest volumes and images. The page reads every 2 seconds on the VM and every 5 seconds on a remote host, only while it is visible: it pauses after 2 minutes without the focus of the window and after 30 minutes without a click or a key on it, and its readings end 15 seconds after it is hidden. Each reading is one command with a fixed script that only reads system files, on the same login of the host as the view; it writes nothing on the host. The page never starts the VM and does not keep it running, and **Stop the VM…**, **Remove the VM…** and **Remove and Set Up the VM Again…** pause it until **Resume**. A remote host with a password asks only when you open the page or click **Resume**, **Retry** or **Refresh Sizes**.

**The report of a resource:** a click on an object row of the view Docker Hosts (a container, an image, a volume or a network) opens its report in the editor, a page that only shows values. A report opens like a file of the Explorer: a click gives a preview tab with its title in italics, which the next click replaces, and a double click keeps the tab open. Every object shows the facts of Docker (for a volume also the containers that use it); an object of Devspaces also shows what it holds, with a tag that says what the rule of Devspaces does with each item: the store of VS Code each version of the VS Code Server and each extension, and which of them the next cleanup of the Monitor keeps or removes and why; the Monitor what it did in its last runs, its next background run and its other records; the cache of the workers its content; the objects of a devspace their devspace and owner, the dev container its build, whether the next Start creates it again, and the windows that use it now, the workspace volume the Git state that this computer recorded last (without a new read of Git), and the other volumes and the network what Delete does with them; a devspace image its build and each image and Feature it was built from against the registry now, a prepared image what changed against the build, a base image its version, the devspaces built on it and its older versions, the helper image and the build image the version of Devspaces that they serve, and a helper container when it ends. Devspaces reads the shared volumes with one short-lived container of a helper image that is already on the host, without a download, without a network and with the volumes read-only. The page reads when it opens and at **Refresh**, never in the background, and it never starts the VM; a report tab that VS Code opens again at its start reads only at **Refresh**. With the setting `devspaces.allowContainerLogs` on, **Show Log of the Monitor** on the reports of the Monitor and of its volume opens the last 2000 lines of its log as a read-only document, with the times of each line as `2026-11-12 22:07:25.606` in the time zone of your computer.

**Settings of the view Docker Hosts:** the view is read only by default. The setting `devspaces.dockerHostsActions` decides which actions it has: `disabled` (the default) shows the hosts and their objects, opens the report of an object at a click, and keeps **Refresh** and **Show Utilization**, but offers no action that changes a host, no command of the VM row, no **Start the VM** on its pages and no **+**; `contextMenu` puts the actions into the context menu of each row and the **+** into the menu **…** of the view; `icons` also shows every action as a button on its row, **Stop** included, and the **+** as a button of the title bar. The Command Palette and the repository view keep their commands. **Remove Devspaces from This Docker Engine…** is in the Command Palette, for the Docker host of Devspaces, and in the context menu of each host row of the view Docker Hosts, for that host; it is no longer in the menu **…** of the repository view. No action that removes or deletes something is a button of a row of the view Docker Hosts, also with `icons`: **Delete…**, **Remove…**, **Remove Unused Build Cache…**, **Remove from the List**, **Remove Devspaces from This Docker Engine…**, **Remove the VM…** and **Remove and Set Up the VM Again…** are only in the context menu of their row, and only while the new setting `devspaces.allowDestructiveActions` (default off) is on; while it is off, the view has none of them. The setting `devspaces.allowContainerLogs` (default off) allows **Show Log** of every container, in the menu of each container row and on the report of a container, also of a container that is not of Devspaces, and **Show Log of the Monitor**; it opens the last 2000 lines of the log as a read-only document, never starts the VM, and says so when the log driver of a container keeps no log. A worker, whose log driver is `none` because its input and output carry the connection to the window, writes a log of its own into the volume of the Monitor (its start, each operation with its result and time, the messages of the operations, and why it ended; never a parameter, a secret, a command or an output), and **Show Log** of a worker opens that log from any computer. While the setting is off, Devspaces reads no log of a container, and its Docker pipes refuse the log of every container. The setting `devspaces.dockerHostsSettingsButton` (default off) shows a gear **Docker Hosts Settings…** in the title of the view that switches every setting of the view in your user settings: the actions, the removals, the logs and the console button. The setting `devspaces.dockerHostsConsoleButton` (default off) shows **Open Console** on each host row: a terminal in VS Code with a shell on that host itself, over SSH on a remote host, through `wsl.exe` for the WSL distribution of Devspaces, and over the SSH of Lima for its VM. The console runs on your computer also in the window of a devspace, works as a terminal of your computer (echo, Ctrl+C, each line at the left edge), and Devspaces sets a new size of the terminal on the host. All four settings count only in your user settings.

**Colors in the views:** in the view Docker Hosts, the objects that are not of Devspaces are violet, so that you find the other services of a host, and the objects that are not active are dimmed: a dimmed violet when they are not of Devspaces, gray when they are. Active is a container that runs, and an image, a volume or a network that a running container uses. In the repository view, the rows without a running devspace are gray, and so are the owners, groups and repositories without one below them. The colors are theme colors that you can change in `workbench.colorCustomizations`.

**Work that is not on GitHub yet:** a row of the repository view now shows the work of its devspace that is not on GitHub yet in every state, also while the devspace runs: uncommitted files, unpushed commits and stashes as numbers, for example `Running · 1 uncommitted · 3 unpushed`, and the badge **↑** at the right edge of the row. The owner, the group and the repository with several sources above such a row have the badge too, so that a closed level does not hide it, and the tooltip names each number. A commit is unpushed when no remote branch contains it, also on a branch without an upstream. While a devspace runs, Devspaces counts again when the view is shown, when the window gets the focus, and after an action, in the same read as the branch; it never counts in the background. A stopped devspace shows the numbers of its last stop, and its tooltip says when they were counted. Before, the numbers showed only for a stopped devspace, at the end of the row text.

**Names of the helper images:** in the view Docker Hosts, the helper image is named by its tag `devspaces-worker:<hash>`, not by the tag `devspaces-monitor:<hash>` of the Monitor. An earlier build of the helper image, whose tag a newer build took, is named `devspaces-worker (earlier build, <ID>)` instead of `<none> (<ID>)` or `devspaces-monitor:<hash>`, and its tooltip says why it has no tag. The base image of the current helper image (`node:26-trixie-slim`) says **base image of the helper image** instead of **not of Devspaces**; the base image of an earlier helper image still says **not of Devspaces**.

**Update without a dialog:** the setting `devspaces.updateContainer` has a third value, `yes`, and it is the new default: when a newer image is available, a start updates the container of the devspace without a dialog, also a running one, which is stopped and created again. The progress says that the devspace is updated, and your files in the workspace are kept. A container that another window is connected to is never replaced. For a dialog first, set `notify` (**Continue** or **Cancel**, the default until now) or `ask` (**Update Now** or **Later**); a value that you set yourself stays.

**Node.js 26 in the helper image:** the helper image of Devspaces (`devspaces-worker`), which the workers and the Monitor run from, now starts from `node:26-trixie-slim`, the current LTS version of Node.js, instead of `node:24-trixie-slim`. Each Docker host builds the new helper image once, at the first use after the update. The extension itself still runs on the Node.js of VS Code.

**The labels of a devspace on its container:** the dev container of a devspace now carries the repository, the owner and the build record of its image as its own labels, not only through the labels of its image. An open that has no build record of the devspace, for example on another computer that uses the same Docker host, takes the build record from the container first. This prepares devspaces that share one image when their configuration and images are the same.

**One image for identical devspaces:** devspaces whose builds have the same inputs now use one image instead of one identical image each, for example the repositories of a course that all use the same configuration, or all devspaces of the default image. This holds for a configuration that names an image or a Dockerfile, while the host access checks are on. The inputs are the configuration (without its name, its workspace folder and mount, its `runArgs`, its `appPort` and its `initializeCommand`), the image, the Features with the digests that their registry gives, the lockfile, and the version of the Dev Container CLI; for a Dockerfile also its text and all files of its build context (their names, modes and contents), so only repositories with an identical build context share an image. The first devspace builds the image; each other devspace with the same inputs only adds its own tag to it, without a build, and starts faster. The background prepare of the Monitor does the same at night: it builds the newer image once, and the other devspaces with the same inputs get it as their prepared image without a build. Such an image is built only from the configuration and the `devcontainer-lock.json` as Devspaces read them (and from a checked copy of the build context of a Dockerfile), so a build of it does not update the `devcontainer-lock.json` of the repository. **Rebuild** always builds. A configuration with Docker Compose, with a Feature that names a digest or that is not in a registry, or with a Dockerfile that reads something outside of these inputs (for example an image in `COPY --from`, a file from the network with `ADD`, or a secret), still builds an image for its devspace alone. An earlier version of Devspaces on another computer that uses the same Docker host refuses the label of a shared image when it creates the container of such a devspace again; update Devspaces on every computer that uses the host. When the Monitor is idle, it also merges an image that was built for one devspace earlier and that is identical to such a shared image (the same layers and settings): when that devspace is stopped, the Monitor removes its stopped container and the duplicate image, and the next **Start** creates the container from the shared image without a build. The files of the workspace stay; changes outside the workspace folder are lost, and the lifecycle commands (for example `postCreateCommand`) run again, as after an update. A running devspace is never touched.

**A report of each run of the Monitor:** at the end of each background run, the Monitor of a Docker engine keeps a short report of the run on that engine, for the last 7 runs: when it ran, whether it reached the network, what it pulled, built, downloaded, linked, prepared and removed, and what failed, each with its count and the names of the first ones. The details of each step stay in the log of the Monitor.

**The Monitor cleans up:** the Monitor of each Docker engine now removes the objects of Devspaces that no container uses, in its background run: the earlier builds of the helper image, the helper images that no running container used for 7 days, the older versions of the build image `devspaces-buildx` and of the base image of the helper image, the stopped helper containers that are older than 10 minutes, and on the VM of Devspaces the build cache that no build used for 7 days. It never removes a devspace container, a volume or a network, and never an image that a container uses. The windows no longer remove helper images or build images themselves.

**Workers on the current helper image:** after the helper image of a Docker engine was built again (by the Monitor, or by another window or computer), each window there moves its worker to the new build: the heartbeat of the window finds that its worker runs from the earlier build, the window starts a worker from the current build in the background (on the VM of Devspaces and on a remote host, on a new connection, with a login that asks nothing), and it closes the earlier worker once no operation runs on it. So the earlier build is no longer kept by a worker for as long as the window is open, and the Monitor can remove it. When the new worker cannot be started (for example on a remote host whose login asks for a password), the earlier worker stays, and the window tries again after an hour. The connection of the window of a devspace to its container stays on the earlier connection until the window closes or reloads.

**The newest version runs the Monitor:** when computers with different versions of Devspaces use one Docker engine, the Monitor there runs the newest version. A window of a newer version stores its script in the volume of the Monitor, and the running Monitor moves to it by itself when nothing runs in it, as after a new build of the helper image. A window of an earlier version no longer replaces a newer Monitor: it keeps it and works with it. The commands of the Monitor leave out the parts of their input that they do not know, so windows of other versions work with it.

**The Monitor on the current helper image:** after the helper image of a Docker engine was built again, the Monitor there moves to the new build by itself, at a time when nothing runs in it (no background run, no automatic stop, no command of a window): it starts its successor from the new build with the same settings, and then ends; the successor removes the earlier Monitor and, when no other container uses it, the earlier build. A Monitor that ended when idle and was created from an earlier build is replaced by the next open, and a window always creates the Monitor from the current build. When the move fails, the Monitor keeps running and tries again after an hour. A window whose heartbeat comes while the Monitor moves, and a window that starts the Monitor at the same time as another window, now wait a few seconds and then use the Monitor that the other one started, instead of failing to start it.

**Remove Devspaces from This Computer…:** a new command in the Command Palette and in the **…** menu of the repository view removes Devspaces from this computer and then uninstalls the extension, after one question that names each part, the recorded changes of the devspaces that it deletes, and the devspaces that stay. It removes Devspaces from each remote Docker host of the list, with your devspaces there (the devspaces of other accounts and other computers stay); the VM of Devspaces with every devspace in it (never a WSL distribution `devspaces` that Devspaces did not set up); the line of the SSH key of Devspaces in `~/.ssh/authorized_keys` on each host where Devspaces added it, with a login that uses only that key and asks nothing, and then the key itself (the key and its line stay for a host where something of Devspaces stays); and the scheduled task, the Docker context `devspaces` and the folder of Devspaces outside of VS Code. When a host does not answer or a part cannot be removed, the other parts are removed, the log names what stays, and the extension stays installed so that you can run the command again, unless you choose **Uninstall Anyway**. Cancel stops it before the next part. A devspace that comes after the question is never deleted. See [Uninstall](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#uninstall).

**Cleanup after the uninstall:** at the next start of VS Code after Devspaces was uninstalled, Devspaces now removes its scheduled task, so that the VM of Devspaces or its WSL distribution no longer starts at the times of devspaces.cacheUpdateSchedule after the uninstall. It also removes its Docker context devspaces when it created it and it is not the current Docker context, and its folder with Lima (`~/.nimblescape/devspaces`, or `%LOCALAPPDATA%\nimblescape\devspaces` on Windows) when the VM of Devspaces is not in it. VS Code runs this once, without a window, and then deletes the files of Devspaces in its storage itself. It never deletes the VM of Devspaces, the WSL distribution or a devspace, and it never connects to a Docker engine or a remote host. The user guide says what stays after the uninstall, also the SSH key of Devspaces, and how to remove it.

**Manage the VM:** the row of the VM of Devspaces shows its state (Not set up, Stopped or Running) and, in its tooltip, its memory, its CPUs and the space of its disk. Its menu has **Set Up**, **Start the VM**, **Stop the VM…** (it asks first while devspaces run there and names them), **Remove the VM…** (after a question, because it deletes every devspace in the VM), and **Settings of the VM** on macOS and Linux. **Remove and Set Up the VM Again…** is in the context menu of the VM row and in the Command Palette, never a button. **Remove the VM…** is new on macOS and Linux; on Windows it is **Remove the WSL Distribution of Devspaces…**.

**Docker for Devspaces in its own VM on macOS and Linux:** on a computer without Docker, **Set Up Docker for Devspaces** in the view, the new command **Set Up Docker for Devspaces in Its VM…**, and a link to Devspaces create the VM of Devspaces with [Lima](https://lima-vm.io) and use it as the Docker host of Devspaces, without a question and without administrator permission: Devspaces downloads Lima and the disk of its VM with Debian 13 and Docker Engine, creates and starts the VM, and connects to it over the SSH of Lima. The VM uses Apple Virtualization on macOS, also when VS Code for Intel runs under Rosetta on a Mac with Apple silicon, and QEMU with KVM on Linux. On Linux without QEMU, the setup first installs QEMU in a terminal, where `sudo` asks for your password, and then goes on by itself. Devspaces starts the VM when it needs it, and the VM powers itself off when nothing runs there. The VM gets 4 GiB of memory and 4 CPUs, each at most half of the computer; the new settings devspaces.vmMemoryGiB and devspaces.vmCpus change them from the next start of the VM. When the VM runs out of memory and its kernel ends a process, a warning says so and names devspaces.vmMemoryGiB. The new setting devspaces.createDockerContext (off by default) creates the Docker context devspaces for the VM, so that the docker command and other Docker tools can see its containers, images and volumes; it never becomes the current Docker context. The view no longer offers to install Docker Desktop or Docker Engine on macOS and Linux. See [The VM of Devspaces](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-vm-of-devspaces-macos-and-linux).

**The Docker context on Windows:** the setting devspaces.createDockerContext now works on Windows too, for the WSL distribution of Devspaces: the Docker context devspaces points to a named pipe of Devspaces for your Windows user, which a window of Devspaces serves. It works while a window of Devspaces is open, and it starts the distribution when it does not run.

**Never the Docker of the computer:** Devspaces now runs devspaces only in its VM (on Windows its WSL distribution) or on a remote host of its list, on every platform, also when Docker Desktop or Docker Engine is installed, and it no longer reads the Docker context of the computer. Until the VM is set up or a remote host is chosen, the view shows **Set Up Docker for Devspaces**, and a link to Devspaces sets up the VM. The command **Use the Local Docker** is gone, and Devspaces no longer starts Docker Desktop on Windows. Devspaces that an older version made in the Docker of the computer stay there and are not moved; the view does not show them. When the host that Devspaces uses is removed from its list, Devspaces has no Docker host until you choose one or set up the VM.

**Back to the VM from a remote host:** while the VM of Devspaces does not exist, the choice of the Docker host (the first row of the view, and **Use a Remote Docker Host…**) offers its setup, which creates the VM and uses it: **Set Up Docker for Devspaces in WSL…** on Windows, **Set Up Docker for Devspaces in Its VM…** on macOS and Linux. Once the VM exists, the choice lists it as `wsl:devspaces` or `lima:devspaces`.

**The VM as the local Docker host:** the first row of the view now names the VM of Devspaces **Local Docker host: VM of Devspaces**, and the title of the view **Local VM of Devspaces**, not a remote host, because the VM runs on your computer. When Devspaces uses its VM and the VM no longer exists, for example after its removal outside of Devspaces, the view shows **Set Up Docker for Devspaces** again instead of the repositories, and a link sets the VM up again without a question.

**The helper image after a change of the Docker host:** after the setup of the VM of Devspaces, and after the choice of another Docker host, Devspaces builds its helper image on that host in the background, so that the first Start there does not wait for it. The log says when it starts and when it is ready.

**No installation or start of Docker on the computer:** Devspaces no longer has commands that install Docker Desktop or Docker Engine on your computer, or that start them (**Start Docker**), and it starts no Docker of the computer by itself. When the Docker host of Devspaces does not answer, the message offers **Try again**.

**Setup of Docker on Windows without questions:** the setup of the WSL distribution of Devspaces, from **Set Up Docker for Devspaces** or from a link on a computer without Docker, no longer asks "Set up Docker for Devspaces?": the click or the link is the decision, and the log names the download and the folder. **Install WSL 2** no longer asks either: it runs `wsl --install --no-distribution` in a terminal, Windows asks for administrator permission, and a message says to restart Windows afterwards. After the restart, the first VS Code window goes on with the setup of Docker by itself, and opens the link that needed it. Until Windows restarts, the setup says that the restart is missing, before any download. See [The WSL distribution of Devspaces](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-wsl-distribution-of-devspaces-windows).

**WSL in a virtual machine:** before the download, the setup checks that WSL 2 can start its virtual machine. When it cannot, the message says to restart Windows after the installation of WSL, or to turn on virtualization, also nested virtualization when Windows runs in a virtual machine. A download that WSL could not register for this reason stays, and the next setup uses it without a new download. When WSL runs out of time to start the distribution (`Wsl/Service/CreateInstance/ERROR_TIMEOUT`), Devspaces starts it again, up to 3 times, and it waits up to 2 minutes for the first start of the distribution after a restart of Windows, which takes more than 30 seconds in a slow virtual machine, and then up to 3 minutes for Docker there, which needs about 45 seconds to start in such a virtual machine.

**Progress of the setup:** the progress notification shows the megabytes of the download and the first start of the distribution, so that a long step does not look stalled.

**Windows on Arm:** the setup downloads the `.wsl` file for the architecture of Windows, also when VS Code runs as an x64 program on Windows on Arm.

**A damaged disk of the WSL distribution:** when Windows cannot read the virtual disk of the WSL distribution of Devspaces (`ERROR_FILE_CORRUPT`), WSL cannot start it. The message now says so and offers **Remove and Set Up Again**, which deletes the distribution with all devspaces in it and sets up a new one, without another question. See [The WSL distribution of Devspaces](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-wsl-distribution-of-devspaces-windows).

**The same build on every Docker engine:** Devspaces builds its helper image on every Docker engine (the VM of Devspaces, also its WSL distribution on Windows, and another computer over SSH) in the same way: in a short container of its build image `devspaces-buildx:<version>` there, with buildx (BuildKit) of Docker. Devspaces pulls the build image `docker/buildx-bin` once on each engine, in the version and image digest that its code names, and removes an older version of it. Before, the build used the classic builder of Docker, which runs each metadata step of the Dockerfile as a container and took one to two minutes for each such step in a slow virtual machine. When the build image cannot be pulled, for example when Docker Hub limits the pulls, Devspaces builds with `docker build` as before. **Remove Devspaces from This Docker Engine…** also removes the build image. See [The helper image](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/architecture.md#the-helper-image).

**Log without color codes:** the log of Devspaces shows the output of tools without the color codes of a terminal, for example the red marks of the classic builder of Docker around the error output of a build step.

**The WSL distribution from the image of the VM:** the setup of the WSL distribution of Devspaces downloads the `.wsl` file of the image of the VM of Devspaces from `ghcr.io` (Debian 13 with Docker Engine, the same system as the VM of Lima on macOS and Linux), checks it against the SHA-256 in the code of Devspaces, and registers it. It no longer downloads Debian from the list of WSL distributions of Microsoft and installs no packages, so the distribution needs no restart: systemd starts Docker at its first start. The VM upgrades its packages itself, also Docker Engine, about once a day while it runs; Devspaces no longer runs an upgrade from Windows. **Set Up Docker for Devspaces in WSL…** uses a distribution that Devspaces set up before as it is, without a question. A distribution that an older version set up stays as it is and gets no upgrade from Devspaces anymore: to get the new one, remove it with **Remove the WSL Distribution of Devspaces…** and set it up again.

**The WSL distribution stops when nothing runs there:** the WSL distribution of Devspaces now runs the idle script of the image of the VM, the same script as the VM of Lima: the hidden `wslg.exe` that a window starts there looks every minute whether a container runs, a program uses Docker Engine, or the VM upgrades its packages, and ends after two checks in a row at which nothing ran; then WSL stops the distribution, also while a window of VS Code is open. The idle session that each window held there is gone. The work of Devspaces in the background leaves the distribution alone in the minute after the end of the idle script, so that WSL can stop it. The idle script writes its checks to `/var/log/devspaces-idle.log` in the distribution.

**The background run at most once an hour:** the setting devspaces.cacheUpdateSchedule now needs at least 60 minutes between two runs: an interval of 60 to 1440 minutes, or a cron expression with at least 60 minutes between two of its times. A shorter value means the default, daily at 06:07, and a warning names it. A background run pulls images and builds the next images of the devspaces, so a shorter time only loads the registries and the computer.

**Retries of the background run:** a Monitor that ends when idle no longer exits while a background run that did not reach the network waits for its retry after 2, 5, 10, 20 or 30 minutes. So a computer that wakes up before its Wi-Fi or VPN is back still gets its run; a retry an hour later does not keep the Monitor.

**No question about the Monitor:** Devspaces no longer asks "Keep the Devspaces background container running on `<engine>`?". On a remote host, the Monitor keeps running, unless the setting devspaces.stopMonitorWhenIdle is on, which now applies to remote hosts only. On the WSL distribution of Devspaces and on the VM of Devspaces, the Monitor always ends 5 minutes after the last devspace there stopped, so that the distribution or the VM can stop too; a missed time of the schedule runs at the next start of a devspace there. On Windows, the work in the background no longer starts the WSL distribution of Devspaces for its Monitor, and Devspaces no longer adds the start entry `nimblescape Devspaces WSL devspaces`; an entry that an older version added stays until you turn it off in Task Manager (**Startup apps**). See [The background run](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-background-run).

**The VM starts at the times of the background run:** with the VM of Devspaces, and on Windows with the WSL distribution of Devspaces, a scheduled task of your user starts the VM or the distribution and the background container at the times of devspaces.cacheUpdateSchedule, also while VS Code is closed, so that the images of your devspaces are up to date at your next start: a launch agent on macOS, a systemd user timer on Linux, and a task of Task Scheduler on Windows, all without administrator permission. It starts the VM 5 minutes after a time of the schedule, never wakes the computer, and runs a time that the computer missed once after the wake or the login. The background container ends when it has done its work, and the VM powers itself off. On Windows, the task runs only while you are logged in, shows no window, and Task Scheduler runs a missed time 10 minutes after the wake or the login; the distribution stops about 2 minutes after the background container ended. Devspaces creates the task with the VM or the distribution and removes it when they no longer exist; the user guide says how to remove it by hand after an uninstall.

**No update of VS Code before a start:** a Start of a devspace no longer updates VS Code first while VS Code shows its button **Update**, and the setting devspaces.installVsCodeUpdateFirst is gone. VS Code has no stable interface for its updates. VS Code installs a waiting update itself at its next restart, as without Devspaces.

**Remote Docker host:** the window of a devspace on another computer reaches its Docker engine through a Docker pipe of Devspaces on your computer, and Devspaces carries those Docker connections, together with its helper container there, over one SSH login per window. Before, the Dev Containers extension started a new SSH login for each of its Docker calls, which an SSH server could refuse. The Docker calls of Devspaces itself on that computer use the same SSH login while it is open, without an SSH check before each operation, and so do its checks before that login starts the connection: the open of a window on another computer logs in to it once. A window that Open Recent kept from an earlier version still connects through its Docker context. See [Remote Docker host](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#remote-docker-host).

**Own list of remote hosts:** Devspaces keeps its own list of SSH hosts with Docker, and it no longer creates or switches Docker contexts. **Use a Remote Docker Host…** tests a host and then uses it without a question, and the `docker` command in your terminals keeps its Docker context. The list also shows the SSH hosts of your Docker contexts, and **Remove a Host from the List…** forgets a host. The window of a devspace always opens on the host of its devspace, without the question "Use `<host>` again?". **Ask Again Before Changing the Docker Host** and the "Don't Ask Again" buttons are gone. When the current Docker context of your computer reaches a host over SSH, the sidebar shows "Docker is set to `<host>` over SSH", Devspaces does nothing with Docker, and it offers that host once for its list.

**Docker CLI for remote hosts:** the window of a devspace on another computer runs the Dev Containers extension with a Docker CLI that Devspaces downloads from `download.docker.com` and checks against the size and SHA-256 in its code, and once it is there, Devspaces runs its own Docker calls on another computer with it too, in every window. Every computer connects with the same tested version, also when the Docker CLI of your computer is older or newer, and the Docker tools in your terminals keep their Docker CLI. The first such window downloads it once while it starts, and a notification shows the progress. When the download fails, the window uses the Docker CLI of your computer. When the Docker engine of the other computer is too old for this Docker CLI, or needs a newer one, Devspaces says so with both Docker API versions and what to do, before a window of a devspace there opens. Where a window uses the Docker CLI of your computer for another computer, Devspaces checks that the engine there accepts it too. See [Remote Docker host](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#what-to-know).

**Remote host without Docker on your computer:** without Docker, the Docker setup in the view offers **Use a Remote Docker Host…** next to the installation of Docker. On a computer without a Docker CLI, the command downloads the Docker CLI of Devspaces after you choose the host, and Devspaces then works with Docker on that host, without any Docker on your computer. **Use the Local Docker** shows the Docker setup again. See [Remote Docker host](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#set-up).

**SSH login without setup:** a remote host needs no SSH key and no host key that you accepted in a terminal before. When the SSH login to the host asks a question in a flow that you started (the test of **Use a Remote Docker Host…**, or a command such as **Start** with its progress notification), Devspaces asks it in VS Code: a dialog with the fingerprint of an unknown host key, which **Accept and Connect** keeps in your `known_hosts`, and an input box for your password, the passphrase of a key, or a code. Work in the background asks nothing. After a **Start**, the window of the devspace logs in to the host before it connects, and asks there too when the login needs a question. The test of a host now runs on one SSH login. See [SSH questions](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#ssh-questions).

**SSH key for the next logins:** after a login with your password to a remote host, Devspaces asks once whether to log in with a key next time. **Use a Key** creates the SSH key of Devspaces, `~/.ssh/devspaces_ed25519`, on your computer when it is not there yet, adds its public key to `~/.ssh/authorized_keys` of your account on the host on the same login, and tests it. Then every login of Devspaces to that host, also the work in the background and the Docker CLI, uses this key without a password. **Not for This Host** keeps the password for that host and is not asked again. See [A key for the next logins](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#a-key-for-the-next-logins).

**The WSL distribution of Devspaces (Windows):** a WSL distribution with the name `devspaces` and Docker Engine inside can be the Docker host of Devspaces, without Docker Desktop and without SSH. **Set Up Docker for Devspaces** in the Docker setup of the view (or **Set Up Docker for Devspaces in WSL…**) creates it for your Windows user without administrator permission: after one question with the downloads and the folder, it downloads the Debian file of the list of WSL distributions of Microsoft and checks its SHA-256, registers it with `wsl --install --from-file`, installs Docker Engine there from `download.docker.com` with systemd on, and then uses it. By default, the drives of Windows are not mounted there, and the start of Windows programs from there is off; these settings are no wall against root in the distribution (see [Security](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/security.md#remote-and-shared-engines)). **Remove the WSL Distribution of Devspaces…** deletes it after a warning. **Use a Remote Docker Host…** lists it as `wsl:devspaces` when it exists, also a distribution of that name that you made yourself, which Devspaces never changes. Devspaces reaches it with `wsl.exe` as root of the distribution, with the same relay, Docker pipes and Docker CLI of Devspaces as an SSH host. While a container runs there, Devspaces keeps the distribution running, also after VS Code closed, as Docker Desktop does, with `wslg.exe` of WSL, which opens no window. Its work in the background starts the distribution only when you answered **Keep Running** for its Monitor, and in the window of a devspace there; otherwise the view shows the devspaces there as stopped, with **Start**. With **Keep Running**, a start entry of your Windows user, `nimblescape Devspaces WSL devspaces`, starts the distribution and its Monitor when you log on to Windows; Devspaces removes it after **Stop When Idle** and with the distribution. The distribution is never the default distribution of WSL, so `wsl` without `-d` does not open it, and Devspaces warns when the WSL integration of Docker Desktop is on for it. About once a week, while the distribution runs, Devspaces upgrades its packages with `apt-get upgrade`, also Docker Engine, without a stop of your running devspaces: Docker runs the new version after the next start of the distribution, and the log of Devspaces shows the result. See [The WSL distribution of Devspaces](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-wsl-distribution-of-devspaces-windows).

**Docker setup on Windows:** Devspaces finds Docker Desktop that is installed for your user only, in `%LOCALAPPDATA%\Programs\DockerDesktop`. The installer of Docker Desktop selects this installation by default. Before, the view still showed **Install Docker** after the installation, and a link that you opened in the browser asked again to install Docker, until VS Code and the browser started again. **Start Docker** also starts Docker Desktop from this folder, and the Dev Containers extension, which connects the window to the devspace, uses the same Docker CLI. **Install WSL 2** runs `wsl --install --no-distribution`: WSL 2 without the Ubuntu distribution that `wsl --install` adds by default and that asked for a Linux user after the restart. Docker Desktop and the WSL distribution of Devspaces bring their own. Without administrator permission, the message says to ask an administrator of the computer to run this command.

**Only the needed Docker requests:** the Docker pipes of Devspaces for another computer let only the Docker requests through that their program needs. In the window of a devspace there, the Dev Containers extension can read, start the container, and run programs in it, but it cannot create, build or remove anything: **Rebuild Container** in such a window fails with a message of Devspaces. The Docker calls of Devspaces itself are limited to its reads, the build of its helper image, and **Remove Devspaces from This Docker Engine…**. A refused request gets an error, and the log of Devspaces names it. See [The request filter](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/remote-connection.md#the-request-filter).

## 0.1.0

The first version.

**Devspaces:** the view lists the GitHub repositories that you can access and that contain a Dev Container configuration, grouped by owner. **Start** opens a repository in its own dev container, a devspace, and connects the VS Code window to it. Devspaces clones the repository into a Docker volume, builds the image and creates the container on the Docker of your computer, or on Docker on another computer that you reach over SSH. Git on your computer is not needed. The setting devspaces.defaultImage names an image that every repository can start from. A repository with several sources (several configurations, or a configuration and the default image) has one child row per source, and each child row is its own devspace.

**Background container:** on each Docker engine, the container devspaces-monitor keeps the images of your devspaces, the VS Code Server and your extensions up to date, prepares the next image of a devspace in advance, and stops a devspace a few minutes after its last window closes, unless you keep it running. The first Start or Rebuild on an engine, or Update All Images Now there, asks whether it keeps running there, also while VS Code is closed. Stop When Idle turns on the setting devspaces.stopMonitorWhenIdle, so the Monitor ends 5 minutes after the last devspace stopped, on each engine from the next start of a devspace or Update All Images Now there; until then, a Monitor that keeps running goes on. A Monitor that keeps running ends itself after 30 days in which no devspace was used on its engine.

**Remove Devspaces from This Docker Engine…:** the command removes the Monitor, the helper containers and images, and the shared volumes of Devspaces from the current Docker engine, after a confirmation. A second confirmation shows the recorded Git changes of your devspaces on the engine and asks whether they are deleted too.

**Safe updates:** when a newer image is available, Devspaces tells you before it updates the container (setting devspaces.updateContainer). The files in the workspace are kept.

**Open from a link:** a link `vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name`, for example on a website, opens the repository in its devspace. Devspaces asks before a link creates a devspace.

**Switch and reopen:** **Switch Devspace…** and the status bar switch between your devspaces. When the window that you closed last was connected to a devspace, the next start of VS Code opens that devspace again.

**Remote Docker:** **Use a Remote Docker Host…** runs your devspaces on Docker on another computer that you reach over SSH. After you confirm, Devspaces creates a Docker context for it.

**Docker setup:** without Docker, the view shows the steps to install it: WSL 2 and Docker Desktop on Windows, Docker Desktop on macOS, and Docker Engine on Linux, each only after you confirm the commands. When the current Docker context cannot be read, the sidebar shows "Docker context cannot be read". When the `docker` command uses Podman, the sidebar shows "Podman is not supported".

**Security:** host access checks refuse configurations that reach into your computer, for example bind mounts, privileged mode or the Docker socket. Devspaces uses the GitHub sign-in of VS Code, stores no token, and collects no telemetry. It checks and pulls images first without a registry login. Before your first devspace, it does no Docker work. In Restricted Mode, only your user settings count. The top of the README and [Security](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/security.md#what-devspaces-does-on-your-computer) say what Devspaces does on your computer.
