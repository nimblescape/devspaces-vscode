# nimblescape Devspaces 2

Open your GitHub repositories in dev containers with one click, on your own Docker.

Devspaces lists the GitHub repositories that you can access and that contain a Dev Container configuration. **Start** opens a repository in its own dev container, a **devspace**, and connects the VS Code window to it. The containers run in a VM of Devspaces on your computer, with Docker Engine, or on Docker on another computer that you reach over SSH.

## What Devspaces does on your computer

- **GitHub sign-in.** Devspaces uses the GitHub sign-in of VS Code with the scopes `repo` (read and change the repositories that you can access, also the private ones) and `read:org` (read your organization memberships). Only for a private image on `ghcr.io`, it also asks for `read:packages`. Devspaces uses every GitHub account of VS Code that you allowed for Devspaces. VS Code keeps the sign-ins, and Devspaces saves no token on your computer. At each open from a VS Code window, Devspaces writes the token of the account that owns the devspace into the memory of the devspace, so that Git and the GitHub CLI work there; code in that container can use it.
- **When it works.** Devspaces starts with every VS Code window, also right after the installation.
  - Before your first devspace, Devspaces only reads its Docker host when VS Code starts. It never reads the Docker context of this computer, because it never uses the Docker of this computer. It does not contact the Docker engine, read registry logins, build its helper image, or start a helper container.
  - After your first devspace, each window can also check the Docker engine when it starts, and build the helper image: after an update of Devspaces that changes the helper image, and once a week, to check its base image for a newer version, when the Monitor of that engine did not check it within the week. While the view of Devspaces is visible, it reads the state of your devspaces from Docker. For an engine on another computer, these checks run `ssh`, and the helper image there is built in the background only through the SSH connection of a window to that computer, without an `ssh` login of its own.
  - When VS Code starts with an empty window and the window that you closed last was connected to a devspace, Devspaces opens that devspace again, unless you stopped it. When VS Code restores the window of a devspace, Devspaces opens that devspace first. This can start Docker Desktop and the container.
  - With the VM of Devspaces on macOS and Linux, and with the WSL distribution of Devspaces on Windows, a scheduled task of your user starts the VM or the distribution and its background container at the times of the setting `devspaces.cacheUpdateSchedule` (daily at 06:07 by default), also while VS Code is closed: a launch agent on macOS, a systemd user timer on Linux, a task of Task Scheduler on Windows. It never wakes the computer, and a time that it missed runs once after the wake or the login.
  - Each window where you are signed in reads the repository list of each of your GitHub accounts in Devspaces from GitHub when it opens, and then every hour by default. When VS Code has a GitHub account that Devspaces does not use yet, Devspaces asks once whether to use it.
  - A link `vscode://nimblescape.nimblescape-devspaces-2/open?repository=owner/name`, for example on a website, opens your devspace of that repository after VS Code asks whether Devspaces may open the link, unless you chose "Do not ask me again for this extension" there. Before a link creates a devspace, Devspaces asks too; for a repository of one of your accounts or of one of their organizations, "Always Open" in that question turns this question off. Opening a devspace from a link can start Docker Desktop and the container.
  - A course link `vscode://nimblescape.nimblescape-devspaces-2/course?repository=owner/name-<username>` does the same for your own repository of a course. Devspaces first asks for the GitHub sign-in if you are not signed in, puts the login of each of your accounts in place of `<username>`, and opens the repository that exists with the account of that login.
- **Docker and the Dev Containers CLI.** Devspaces runs the Docker CLI on your computer. On the Docker engine, the VM of Devspaces or Docker on another computer that you reach over SSH, its helper containers clone your repositories into Docker volumes, and build, create, start, stop and remove the containers of your devspaces with the Docker Engine API and the Dev Containers CLI. Devspaces builds its helper image the same way on every engine: in a container `devspaces-build-<id>` there, which runs buildx of Docker from the build image `devspaces-buildx:<version>` with the Docker socket of the engine, without network, and is removed after the build. Devspaces pulls that image once for each version from Docker Hub (`docker/buildx-bin`, by the digest in its code), and removes the tags of older versions. For another computer, Devspaces runs `ssh` to reach it and keeps it in its own list of hosts. On Windows, a WSL distribution of Devspaces with the name `devspaces` can be such a host: Devspaces then runs `wsl.exe` to run its commands there as root, without SSH. So that WSL does not stop it while something runs there, also after VS Code closed, a window starts `wslg.exe` of WSL (no window), which runs the idle script of the VM there: it looks every minute whether a container runs, a program uses Docker, or the package upgrade runs, and ends when nothing ran at two checks in a row; then WSL stops the distribution. **Set Up Docker for Devspaces**, or a link to Devspaces on Windows without that distribution, creates it without a question (the log names the download and the folder): Devspaces downloads the `.wsl` file of the image of its VM from `ghcr.io`, checks it against the SHA-256 in its code, and registers it for your Windows user with `wsl --install --from-file`; Docker Engine is in the image. About once a day, while the distribution runs, a service in the distribution upgrades its packages (`apt-get upgrade`, from Debian and `download.docker.com`); Devspaces runs no upgrade from Windows. To tell its own distribution from one that you made, it reads the folders of your WSL distributions from the registry of your Windows user (`reg.exe export`). It never creates or changes a Docker context, so the Docker tools in your terminals keep their target; only the setting `devspaces.createDockerContext` (off by default) creates the Docker context `devspaces` for the VM of Devspaces (on Windows through a named pipe of Devspaces that a window serves), which never becomes the current context, and turning it off removes it. The window of a devspace on another computer reaches that Docker through a Docker pipe of Devspaces on your computer (a socket that only your user can open, or a named pipe on Windows), which carries its Docker connections over the SSH login of Devspaces; the Docker calls of Devspaces itself use such a pipe too while that login is open. Before that login starts the helper container, Devspaces runs its checks on it: `docker` commands that only read, in a shell on the other computer. When that login asks for an unknown host key, a password, the passphrase of a key, or a code in a flow that you started (a command with its progress notification, or the test of a host), Devspaces sets `SSH_ASKPASS` of that `ssh` to a small helper in its storage, which asks you in VS Code over a pipe that only your user can open; it keeps no answer, and a host key is kept in your `known_hosts` only after you accept its fingerprint. Its work in the background asks nothing. That window runs the Dev Containers extension with a Docker CLI that Devspaces downloads once from `download.docker.com` and checks against the SHA-256 in its code, and once it is there, Devspaces runs its own Docker calls on the other computer with it too. On a computer without a Docker CLI, **Use a Remote Docker Host…** downloads it after you choose the host, so that computer needs no Docker. The Docker tools in your terminals keep their CLI.
- **Registry logins.** Devspaces checks and pulls an image or Feature of a devspace first without a login. It uses the login that Docker stored for its registry on your computer only when the registry refuses this or does not find the image, or when Docker Hub limits pulls without a login: it reads `~/.docker/config.json` and runs its `docker-credential-*` helpers. For `ghcr.io` without such a login, it uses the GitHub sign-in of the account of the devspace with `read:packages`. Devspaces gives the login of that one registry to its helper container only for one check or pull, for at most 8 registries in one open, writes each request to its log, and never stores the login. To build its helper image, Devspaces runs `docker pull` of its build image `docker/buildx-bin` (the Docker CLI of your computer then sends the Docker Hub login that Docker stored, if there is one, as for any pull), and of the public base image `node` before the build, with the same logins.
- **Docker installation.** Devspaces sets up Docker Engine in a VM of its own, also when Docker Desktop is installed, without a dialog: the click on **Set Up Docker for Devspaces**, or a link to Devspaces, is the decision, and the log names the downloads and the folder. It does not install, start or use Docker Desktop or Docker Engine of your computer. On Windows, it sets up its own WSL distribution, as described above, and first installs WSL 2 when it is missing, in a terminal of VS Code that you see, where Windows asks for administrator permission. On macOS and Linux, it creates the Lima VM of Devspaces in `~/.nimblescape/devspaces`: Lima from `github.com` and the disk of the VM with Debian and Docker Engine from `ghcr.io`, each checked against the SHA-256 in its code. Devspaces reaches the VM only over the SSH of Lima, starts it when it needs it, and the VM powers itself off when nothing runs there. On Linux without QEMU, the setup first installs QEMU from the package source of your distribution with `sudo` in a terminal of VS Code that you see, and adds your user to the group `kvm` when your user may not use `/dev/kvm`, which lets your user run virtual machines.
- **The view "Docker Hosts".** Below the repositories, the view **Docker Hosts** lists the VM of Devspaces and your remote hosts. It reads all containers, images, volumes and networks of a host and its build cache only when you open that host or click **Refresh**, never in the background, and it never starts the VM to read it. It stops or starts a container only after your click, and it removes an object only after your click on **Remove…** and one question that names the objects, and never with force; the objects of your devspaces are removed only with **Delete…**, which checks your Git changes first. In the row of the VM, **Stop the VM…** stops it (`limactl stop`, or `wsl --terminate devspaces` on Windows), and **Remove the VM…** deletes it with every devspace in it, each after a question ([The view Docker Hosts](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#the-view-docker-hosts)).
- **The utilization page.** **Show Utilization** on a host row opens a page with the live use of CPU, memory and disk of that host and of its running containers. It reads only while the page is visible and not paused (every 2 seconds on the VM, every 5 seconds on a remote host), on the same login as the view, with a fixed script that only reads system files (`/proc`, the cgroups), the free space, and the names of the containers from `docker ps`; it writes nothing on the host and never starts or keeps the VM running. The sizes of the objects (`docker system df -v`) are read only on a click on **Read Sizes** ([Utilization of a host](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#utilization-of-a-host)).
- **SSH key.** After a login with your password to a remote host, Devspaces asks once whether to log in with a key next time. Only after **Use a Key** it creates its own key `~/.ssh/devspaces_ed25519` without a passphrase on your computer, when it is not there yet, and adds its public key to `~/.ssh/authorized_keys` of your account on that host. Its later SSH logins to that host use this key. It never writes over another file in `~/.ssh` and never changes your SSH config. See [Security](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/security.md#remote-and-shared-engines).
- **Background container.** On each Docker engine, the container `devspaces-monitor` keeps the images of your devspaces, the helper image of Devspaces, the VS Code Server and your extensions up to date, builds the next image of a devspace in advance, removes older versions of those images that no container uses, removes the helper images, build images and stopped helper containers of Devspaces that no container uses (on the VM of Devspaces also the build cache that no build used for 7 days), and stops a devspace a few minutes after its last window closes, unless you keep it running. To build the next image, Docker runs the Dockerfile and the Features of the repository, also while no VS Code window is open. To add a newer VS Code Server to a running devspace, the Monitor runs a command in it, as `docker exec` does. On a remote host, this container keeps running, also while VS Code is closed, unless the setting `devspaces.stopMonitorWhenIdle` is on. On the WSL distribution of Devspaces and on the VM of Devspaces, it stops 5 minutes after the last devspace stops; on the VM, the scheduled task above starts it at the times of the schedule. Devspaces asks no question about it. A container that keeps running ends itself after 30 days in which no devspace was used on that engine. **Devspaces: Remove Devspaces from This Docker Engine…** removes it (see Uninstall below).
- **Network.** Devspaces and its helper containers connect to GitHub, to a remote Docker host over SSH, to the image registries of your Dev Container configurations and of the setting `devspaces.defaultImage`, to the update service of VS Code, to the Visual Studio Marketplace, to Docker Hub, Debian, Docker and npm for the helper image, to Docker for the Docker CLI of Devspaces (for the window of a devspace on another computer, or for a remote host on a computer without a Docker CLI), to `ghcr.io` for the image of the VM of Devspaces, to GitHub for Lima, and to the package sources of your system for QEMU on Linux; the VM itself connects to Debian and Docker for the upgrades of its packages. Each HTTPS request of the code of Devspaces, in VS Code and in its helper containers, sends the header `User-Agent: nimblescape-devspaces/<version>`. Other programs, such as Docker, Git and the Dev Containers CLI, send their own User-Agent. Only the Monitor asks the Visual Studio Marketplace: in its background run, for the extensions that the devspaces on its Docker engine used in the last 14 days, also the devspaces of other users of that engine. For each extension, it takes the newest release that works with the current VS Code Server, or the exact version when the extension is listed as `publisher.name@x.y.z`. It downloads only the files that its store does not have. Devspaces collects no telemetry. The code in a devspace can connect to any address.

[Security](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/security.md#what-devspaces-does-on-your-computer) describes each step and what Devspaces protects.

## Features

- **One click to code.** Devspaces clones the repository into a Docker volume, builds the image, creates the container, and connects the window. Git on your computer is not needed.
- **Fast starts.** A small container on each Docker engine, the Monitor, keeps images, the VS Code server, and your extensions up to date in the background, and prepares newer images before you need them.
- **Safe updates.** When a newer image is available, Devspaces tells you before it updates the container. Your files in the workspace are kept.
- **Stops by itself.** A devspace stops a few minutes after its last window closes, unless you keep it running.
- **Open from a link.** A link on a website opens a repository in its devspace. When Devspaces is not installed, VS Code installs it first ([Open from a link](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#open-from-a-link)). A course link opens the own repository of each student of a course, with the GitHub login of the student in its name ([Course links](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#course-links)).
- **Several GitHub accounts.** One list for all GitHub accounts of VS Code that you use in Devspaces. A new devspace uses the account with the highest permission on the repository, an existing devspace always its own account, and **Start with Account…** lets you choose ([Several GitHub accounts](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#several-github-accounts)).
- **Back where you left off.** When the window that you closed last was connected to a devspace, the next start of VS Code opens that devspace again.
- **Remote Docker.** Run your devspaces on a stronger machine over SSH. A remote host serves one user, or a group whose members trust each other.
- **Guard rails.** Host access checks refuse configurations that reach into your computer (bind mounts, privileged mode, the Docker socket, …). The GitHub token stays in the memory of the container only.
- **Docker setup.** Without Docker, the view walks you through installing it.
- **Docker Hosts.** One view shows the VM of Devspaces and your remote hosts with all their containers, images, volumes and networks and the build cache, those of Devspaces first with their purpose, each with its size; the other services of the host are violet, and what does not run is dimmed. Stop the other services of a host when your devspaces need its CPU and memory, remove what you do not need, also the helper containers and volumes and the unused build cache, and start, stop or remove the VM. **Show Utilization** shows how busy a host and each of its containers are now.

## Requirements

- VS Code 1.125 or later (the Microsoft build).
- Docker: on Windows, Docker Engine in the WSL distribution of Devspaces, which needs WSL 2.4.4 or later; on macOS and Linux, Docker Engine in the Lima VM of Devspaces, which needs QEMU and KVM on Linux. Devspaces never uses Docker Desktop or Docker Engine of your computer. On every platform, also Docker Engine on a computer that you reach over SSH; then your computer needs no Docker. Podman is not supported. This includes the package podman-docker.
- A GitHub account on github.com. Devspaces does not work with GitHub Enterprise Server or GHE.com.
- The Dev Containers extension. VS Code installs it with Devspaces.

## Getting started

1. Select the **Devspaces** icon in the activity bar.
2. Select **Sign in with GitHub**. Your repositories with a Dev Container configuration appear, grouped by owner (with a default image, also those without one).
3. Select **Start** on a repository, double-click it, or select it and press `Enter`. A repository with several sources (several configurations, or a configuration and a default image) has a child row per source, each its own devspace; a double-click on the repository starts its first child row. The first start takes a few minutes; later starts take seconds.

Switch between devspaces with **Devspaces: Switch Devspace…** or the status bar. On macOS, the key of the command is `Cmd+Alt+E`. On Windows and Linux, the command has no key, because on many Windows keyboards `Ctrl+Alt+E` types a character such as `€`. To set a key, open **Keyboard Shortcuts** (`Ctrl+K Ctrl+S`), search for `Devspaces: Switch Devspace`, select the row, press `Enter`, press your keys, and press `Enter` again.

## Main settings

| Setting | Default | |
|---|---|---|
| `devspaces.defaultImage` | `""` | An image that every repository can start from next to its configuration: a repository with a configuration gets a `default` row next to its configuration rows, its own devspace; a repository without a configuration starts from the image. `devspaces.startWithDefaultImage` puts the `default` row first (on) or last (off); a double-click on the repository starts its first row. |
| `devspaces.stopOnClose` | `true` | Stop a devspace 5 minutes after its last window closes. |
| `devspaces.updateContainer` | `notify` | At a start with a newer image: `notify` (Continue/Cancel) or `ask` (Update Now/Later). |
| `devspaces.cacheUpdateSchedule` | `7 6 * * *` | When the background updates run: a cron expression in your time zone, or minutes. |
| `devspaces.owners` | `[]` | Organizations and accounts to list. Empty: all. |
| `devspaces.repositoryGroups` | `[]` | Regular expressions that filter and group repositories by name. |

All commands, settings, and details are in the [user guide](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md).

## Security and privacy

**A repository that you open is code that you run.** Open only repositories that you trust. The host access checks are a guard rail against mistakes, not a sandbox; see [Security](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/security.md).

Devspaces uses the GitHub sign-in of VS Code, stores no token, and collects no telemetry.

## Uninstall

Before you uninstall Devspaces, run **Devspaces: Remove Devspaces from This Docker Engine…** (Command Palette, or the **…** menu of the view) on each Docker engine that you used. **Devspaces: Use a Remote Docker Host…** switches the engine. The command removes the container `devspaces-monitor`, the helper containers and images of Devspaces, its build image `devspaces-buildx`, and the volumes `devspaces-monitor`, `devspaces-worker-cache` and `devspaces-vscode`. It asks first, and it asks again before it deletes your devspaces on that engine. Then uninstall the extension in VS Code. The [user guide](https://github.com/nimblescape/devspaces-vscode/blob/main/docs/guide.md#uninstall) has the Docker commands that remove the same by hand, how to remove the VM of Devspaces and its scheduled task on macOS and Linux, and how to remove the Docker contexts that versions 0.1.0 and 0.2.0 created.
